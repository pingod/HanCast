## 1. 为什么需要它

**一句话威胁模型**：本机一旦在局域网里广告自己是 MediaRenderer，**同一网段的任何设备**都能对它发 `SetAVTransportURI` + `Play`，把任意 URL 的画面推到本机屏幕上——包括陌生人、误操作的家人、以及同一 WiFi 下不该有权限的设备。

HanCast 的处置方式是在 SOAP 动作入口加一道闸：

| 设备状态 | 处置 | 代码 |
|---|---|---|
| 已信任（trusted） | 直接放行，累加投屏次数 | `security/guard.py:212-218` |
| 已拉黑（blacklisted） | 直接拒绝，回 SOAP Fault | `security/guard.py:203-209`、`protocol/dlna.py:838-840` |
| 未知 | 弹窗等用户确认，超时默认拒绝 | `security/guard.py:236-238`、`:274-299` |
| Guard 已关闭 | 一律按 trusted 放行 | `security/guard.py:196-197` |

设计取向写在 `security/guard.py:1-12` 的模块 docstring 里：默认开启（`utils/config.py:205`），**超时默认拒绝**（`guard.py:7`）。也就是说，这是一个「无人值守即拒绝」的模型——用户不在电脑前时，陌生设备推不上来。

它同时解决「误投」：办公室/家里有多台电视和多台电脑时，弹窗让用户有机会在画面真的上屏之前叫停。

边界要说清楚：**Device Guard 只管「接收投屏」这条入站路径**，闸门挂在 `AVTransport_SetAVTransportURI` 上（`protocol/dlna.py:834-850`）。它不管：

- 本机作为控制点向外投屏（出站）；
- 屏幕投屏（本机当源）；
- 解析代理 `media/server.py` 上的 HTTP 请求；
- 观看页 `/r/<session_id>`（`screencast/httpd.py:232`）——**浏览器通道的观看链接没有 Guard，拿到链接就能看**。

### 2.3 事件与命令的载荷

事件 `cast_confirm_request`（`commands.py:1185-1190`），前端类型 `src/types/guard.ts:25-34`：

```json
{
  "request_id": "req_a1b2c3d4e5f6",
  "device": {"ip": "192.168.1.68", "udn": "uuid:...", "friendly_name": "客厅电视", "model_name": "..."},
  "timeout": 15
}
```

`request_id` 形如 `req_<uuid4 前 12 位>`（`guard.py:249`）。`timeout` 直接取当前配置值（`commands.py:1188`），所以前端倒计时与后端超时用的是同一个数——但两者的起点不同步，见 §8.6。

命令 `respond_cast_confirm`（`commands.py:1192-1197`）：

```json
{"request_id": "req_a1b2c3d4e5f6", "approved": true, "policy": "always"}
```

`policy` 缺省 `"once"`；注释里登记的合法值是 `"once" | "always" | "blacklist"`（`commands.py:1196`）。前端实际会发出第四种值 `"reject"`（`GuardConfirmModal.vue:14`），见 §8.4。

### 2.4 设备信息反查（三层降级）

`check()` 判定未知设备时、以及 `create_pending_request()` 建请求时，都会调 `_resolve_device_info()`（`guard.py:425-447`）把 IP 反查成 `{udn, friendly_name, model_name}`：

| 层 | 方法 | 耗时 | 位置 |
|---|---|---|---|
| ① | SSDP 缓存直达 | 0ms | `guard.py:476-490` |
| ② | SSDP 单播 M-SEARCH（对端 UDP 1900） | ~50ms–1s | `guard.py:492-580` |
| ③ | TCP 端口探测 `http://<ip>:<port>/description.xml` | ~1s | `guard.py:582-625` |

②③ 是**并行**发起、取最快成功的那个（`_resolve_parallel`，`guard.py:449-474`，`ThreadPoolExecutor` + `as_completed`，命中后 `cancel()` 其余），所以总耗时 ≈ 最慢单层而非两层之和。

- ① 的数据来自后台 SSDP 监听：设备发现回调 `commands.py:314-319` 把 `{udn, friendly_name, model_name}` 灌进 `update_ssdp_cache()`（`guard.py:138-162`）。
- ② 从 M-SEARCH 响应的 `USN` 里取 `uuid:` 段当 UDN（`guard.py:532-536`），USN 里没有就再抓 `LOCATION` 指向的 description.xml（`guard.py:538-556`）。
- ③ 的端口顺序按**历史成功率**排（`guard.py:587-592`），命中后计数 +1 并落盘（`guard.py:617-619`、`_save_port_stats` 在 `:671-678`）。候选端口 `COMMON_PORTS = [8080, 49152, 49153, 1900]`（`guard.py:40`）。
- description.xml 解析支持 `device-1-0` / `device-1-1` / 无命名空间三种写法（`_parse_description_xml`，`guard.py:627-669`）。
- 三层全失败时，请求仍会建出来，只是设备名回落成「未知设备」（`guard.py:252-260`）。前端对应文案 `guard.unknownDevice`（`src/locales/zh-CN.json:196`）。

注意 `guard.py:428` 的 docstring 写「三层降级架构」，但紧接着只列了 2 条（因为 ②③ 并行、被合并成一条描述）。层数口径以本节表格为准。

## 3. 信任名单

### 3.1 存在哪里

**不是后台参数**，而是配置文件里的独立一段：

- 文件：`<SETTING_DIR>/hancast_setting.json`（`utils/config.py:34`）
- 段名：`settings["device_guard"]`（`utils/config.py:211-214`）
- `SETTING_DIR`：Windows `%APPDATA%\HanCast`（`utils/config.py:23`）／macOS `~/Library/Application Support/HanCast`（`:25`）／Linux `~/.config/hancast`（`:27`）

默认值（`utils/config.py:202-209`）：

```json
{"enabled": true, "confirm_timeout": 15, "trusted_devices": [], "blacklisted_devices": []}
```

实际落盘由 `_save()`（`guard.py:689-697`）写，比默认多一个 `port_stats`：

```json
{
  "enabled": true,
  "confirm_timeout": 15,
  "trusted_devices": [
    {"udn": "uuid:9d2b1c00-...", "ip": "192.168.1.68", "friendly_name": "客厅电视",
     "policy": "trusted", "created_at": "2026-10-13T21:04:11",
     "last_seen_at": "2026-10-15T09:30:02", "cast_count": 7}
  ],
  "blacklisted_devices": [],
  "port_stats": {"8080": 3, "49152": 11, "49153": 0, "1900": 0}
}
```

字段定义在 `DeviceGuardEntry`（`guard.py:43-59`）；`created_at` / `last_seen_at` 是**本地时间**、无时区，格式 `%Y-%m-%dT%H:%M:%S`（`guard.py:699-701`）。前端类型镜像在 `src/types/guard.ts:2-10`。

### 3.2 设备身份怎么算

**主键是 UDN，IP 只是索引和兜底。** 三张表（`guard.py:91-93`）：

```
_trusted     : udn -> DeviceGuardEntry
_blacklisted : udn -> DeviceGuardEntry
_ip_index    : ip  -> udn          # 快速路径，避免每次都做三层反查
```

- 有 UDN 就用 UDN 当 key（`guard.py:396`、`:411`）。
- **拿不到 UDN 时退化成 `f"ip:{ip}"` 这个伪 UDN**（`guard.py:396`、`:411`）；启动加载时对历史数据也做同样修复（`guard.py:95-111`，注释「修复空 UDN：用 IP 作为 key」）。这意味着：**一台反查不到 description.xml 的设备，身份就退化成 IP**——它换 IP 就等于换了一台设备。
- 名字（`friendly_name`）**不参与身份判定**，只用于展示与落盘（`guard.py:400`、`:415`）。设备改名不会掉信任。
- 信任设备换 IP 时会被就地纠正：`check()` 反查到 UDN 命中信任表后 `entry.ip = caller_ip` 并落盘（`guard.py:226-232`），`_ip_index` 随之更新。
- `remove_device()` / `set_policy()` 都**同时接受 UDN 或 IP** 作为 key（`guard.py:322-344`、`:346-373`），前端传的是 `device.udn || device.ip`（`src/components/GuardDeviceList.vue:25`、`:30`）。

`check()` 的匹配顺序是：先按 IP 查 `_ip_index` 拿 UDN（`guard.py:200`），黑名单先于信任表判（`guard.py:202-218`）——**同一台设备同时在两张表里时，黑名单赢**。

### 3.3 增删改入口

| 操作 | 后端 | 命令 | 前端 |
|---|---|---|---|
| 加入信任 | `guard.py:395-408` `_add_trusted` | 由 `wait_for_confirm` 在 `policy == "always"` 时调用（`guard.py:292-294`） | 弹窗「始终允许」（`GuardConfirmModal.vue:21-23`） |
| 加入黑名单 | `guard.py:410-423` `_add_blacklisted` | 由 `wait_for_confirm` 在 `policy == "blacklist"` 时调用（`guard.py:295-297`） | **弹窗上没有这个按钮**，见 §8.4 |
| 移除 | `guard.py:322-344` `remove_device` | `remove_guard_device`（`commands.py:1206-1209`） | `GuardDeviceList.vue:25-27`、`:99` |
| 改策略（信任↔黑名单） | `guard.py:346-373` `set_policy` | `set_guard_policy`（`commands.py:1211-1215`） | `GuardDeviceList.vue:30-33`、`:85` |
| 读列表 | `guard.py:316-320` | `get_guard_devices`（`commands.py:1199-1204`） | `src/stores/guard.ts:51`、`src/api/commands.ts:1275` |
| 开关 / 超时 | `guard.py:375-391`（property setter 内直接 `_save()`） | `get_guard_settings` / `save_guard_settings`（`commands.py:1217-1229`） | `src/views/SettingsView.vue:74-81`、`:335-364` |

**没有「重命名」入口。** `DeviceGuardEntry.friendly_name` 只在 `_add_trusted` / `_add_blacklisted` 时写入，之后没有任何代码路径修改它（`set_policy` 只改 `policy`，`guard.py:365`）。设备改了名，列表里显示的还是当初那个名字，直到用户移除后重新授权。前端 `GuardDeviceList.vue` 也只有「移除」和「策略切换」两个动作（`:25-33`）。

`remove_device` 有一个细节：它会先按 UDN 删两张表（`guard.py:327-332`），再按 IP 从 `_ip_index` 反查 UDN 删一次（`guard.py:334-339`），最后 `_rebuild_ip_index()` 重建索引并落盘（`guard.py:341-343`、`:680-687`）。

## 4. 超时、并发与 SOAP 错误

### 4.1 超时

**默认 15 秒**，三处一致：

| 位置 | 值 |
|---|---|
| `security/guard.py:77` | `def __init__(self, config, confirm_timeout: int = 15)` |
| `utils/config.py:206` | 默认配置 `"confirm_timeout": 15` |
| `security/guard.py:1-12` docstring | 「15s 超时默认拒绝」 |

生效值以配置文件为准：`guard.py:88` 用 `guard_cfg.get("confirm_timeout", confirm_timeout)` 覆盖构造参数。前端 UI 给四个档位 10 / 15 / 30 / 60（`src/views/SettingsView.vue:357-360`），改动即落盘（`guard.py:388-391`）。

超时实现：`pending.event.wait(timeout=self._confirm_timeout)`（`guard.py:276`）。这是**在 HTTP 工作线程里同步阻塞**的（docstring `guard.py:275` 明说），也就是说这 15 秒内，处理该 SOAP 请求的那个线程被占住。超时后：

```python
if not approved:                                   # guard.py:283-285
    logger.info(f"Request {pending.request_id} timed out, rejected")
    return False
```

超时与用户点「拒绝」走的是同一条出口，日志能区分（`timed out, rejected` vs `denied by user`，`guard.py:284` / `:288`）。

无论哪种结果，`guard.py:279-281` 都会把 `_pending[request_id]` 与 `_ip_pending[caller_ip]` 清掉，所以超时后同一台设备再发一次请求会得到一个**新的** `request_id` 和一次新的弹窗。

### 4.2 并发请求

**没有队列。** 两层处置：

1. **同一 IP 去重**：`create_pending_request` 开头查 `_ip_pending`，命中就直接复用已有的 `PendingRequest`（`guard.py:240-245`，日志 `Reusing pending request for <ip>`）。所以一台设备连发多次 `SetAVTransportURI` 只会弹一次窗，多次调用共享同一个 `threading.Event`，用户一次选择同时放行/拒绝它们。
2. **不同 IP 不排队，前端直接拒掉第二个**：`src/stores/guard.ts:133-137`

   ```ts
   if (pendingRequest.value) {
     respondCastConfirm(event.payload.request_id, false, 'once')
     return
   }
   ```

   第二台设备的请求会被自动拒绝（回 `approved=false`），弹窗只服务第一台。后端此时仍会为它建一个 pending 记录并阻塞等 15 秒——但前端已经立刻回了 `false`，`event` 随即被 `set()`，`wait_for_confirm` 立刻返回 False（`guard.py:301-314` → `:287-289`）。

**推论**：两台设备同时投屏时，第二台必然失败，且失败原因对用户不可见（没有提示，只是弹窗没出现）。这是 §8.7 的一条已知边界。

另一个入口：`src/stores/guard.ts:128-132`——如果 `settings.enabled` 为假，前端**自动批准**（`respondCastConfirm(id, true, 'once')`）。这是双保险，因为后端 `check()` 在 disabled 时根本不会返回 `"pending"`（`guard.py:196-197`）；这条分支只在「后端认为开着、前端 store 里的 settings 是关的」这种不一致状态下才会走到。

### 4.3 拒绝时回给控制点的 SOAP 错误

**UPnP 错误码 701（`UPnPError` / `s:Client`）**，HTTP 状态码仍是 **200**。

路径：`AVTransport_SetAVTransportURI` 抛的是普通 `Exception`，文本分别是 `"Device blacklisted"`（`protocol/dlna.py:840`）和 `"Cast rejected by user"`（`protocol/dlna.py:849`）。`call()` 的通用异常分支按**文本包含**判定（`protocol/dlna.py:694-698`）：

```python
except Exception as e:
    error_msg = str(e)
    if "blacklisted" in error_msg or "rejected" in error_msg:
        logger.warning(f"Action {method} rejected: {error_msg}")
        return self._build_fault(701, error_msg)
    raise
```

`_build_fault()`（`protocol/dlna.py:722-735`）产出的报文结构：

```xml
<s:Envelope xmlns:s="http://schemas.xmlsoap.org/soap/envelope/">
  <s:Body>
    <s:Fault>
      <faultcode>s:Client</faultcode>
      <faultstring>UPnPError</faultstring>
      <detail>
        <UPnPError xmlns="urn:schemas-upnp-org:control-1-0">
          <errorCode>701</errorCode>
          <errorDescription>Cast rejected by user</errorDescription>
        </UPnPError>
      </detail>
    </s:Fault>
  </s:Body>
</s:Envelope>
```

`_build_fault` 的 docstring 写明了动机：**让控制端能读到 errorCode，而不是一个裸 HTTP 500**（`protocol/dlna.py:723`）。HTTP 200 + body 里带 Fault 是 UPnP 规范要求；`protocol/server.py:171-176` 对所有返回一律发 200 并带 `Content-Length`。

拒绝时还会把本机状态复位，**确保控制点后续轮询看到「无媒体」**：

```python
self.set_state('TransportState', 'STOPPED')      # protocol/dlna.py:847
self.set_state('TransportStatus', 'OK')          # protocol/dlna.py:848
```

注释在 `protocol/dlna.py:846`。少了这两行，控制点 `GetTransportInfo` 会读到一个残留的播放态，表现为「明明被拒了，手机上却显示正在投屏」。

另有一条独立的 Fault 路径：动作名不在 SCPD 里时回 **401**（`protocol/dlna.py:670-672`）；`SoapFault` 异常按自带的 `error_code` 回（`protocol/dlna.py:690-693`）。

### 4.4 与后台参数的关系

**Device Guard 的配置不在 `params.py` 登记表里。** `params.py` 存的是 `settings["advanced"]`（`params.py:1-10`），而 Guard 存 `settings["device_guard"]`（`utils/config.py:211-214`）。两套读写路径互不相干：改 Guard 配置不会触发参数表校验，改参数表也不会碰到 Guard。

`security/guard.py:25` 确实 `from ..params import get as param`，但全文件没有 `param(...)` 的调用点——**这是一个未使用的 import**。

顺带一条死参数：`params.py:119-123` 登记了 `discovery.guard_mx`（默认 1，范围 1–8 秒），名字像是 Guard 的 SSDP 超时，但**全仓没有任何读取点**；Guard 自己用的是模块常量 `SSDP_MX = 1`（`security/guard.py:37`）。改 `discovery.guard_mx` 不会有任何效果。

## 5. StopWarningBanner 与「电视没确认收到停止」

**先把归属说清楚：`StopWarningBanner` 属于停止链路，不属于 Device Guard。** 它不由 `cast_confirm_request` 触发，也不读 `device_guard` 配置。两者放在同一份文档里，是因为它们是**同一个设计原则**的两次落地：

> 本机这一侧做完了，不等于对端确认了。凡是无法确认的，都要如实告诉用户，不能假装成功。

- 投屏确认：**事前**——对端还没被允许，就由用户决定放不放行，拒绝时回一个明确的 SOAP 701（§4.3）。
- 停止链路：**事后**——本机已经拆完了，但电视是否收到 `Stop` 无法保证，于是把这件事显式回报出来。

### 5.1 停止链路的如实回报

`commands.py:589-625` 的 `_stop_cast` docstring 直接写明两条契约：

1. **先摘会话再发 SOAP Stop**：设备关机/切源/掉线时 `Stop` 必然抛错，若让它冒泡到命令循环，会话永远留在 `device_sessions` 里，用户点多少次都停不掉（`commands.py:593-594`、实现 `:489`）。
2. **本地会话释放了不等于电视真的停了**：`control_failed` 必须一路传到前端，否则「界面关了、电视还在播」会被当成一次成功的停止（`commands.py:596-597`）。

返回值（`commands.py:570-571`）：

```python
{"ok": True, "stopped": [...], "control_failed": [...], "reasons": {device_id: "..."}}
```

`reasons` 取自 `session.stop_error`，缺失时回落「停止指令未送达」（`commands.py:616`）。同时打一条 error 日志：`Cast stopped locally but device <id> did not confirm: <reason>`（`commands.py:616-619`）——**这是排查「停不掉」时的关键字**。

屏幕投屏的停止复用同一条链路：`screencast/manager.py:214-223` 调 `_stop_cast`，把 `control_failed` / `reasons` 原样透传（`manager.py:229`）；`_stop_cast` 自己抛异常时，也把当前设备记成失败并带上异常文本（`manager.py:220-223`）。设计说明在 `manager.py:227-228`：分片目录已删、HTTP 服务已停，电视顶多把缓冲播完；但 Stop 没送达时必须让前端知道。

### 5.2 前端呈现

`src/stores/screencast.ts:212-249` 的 `stop()`：

- **先摘设备身份再 `fetchStatus`**（`screencast.ts:216-217`）——`fetchStatus` 之后 state 已被重置，`device_id` 就没了；

## 6. 描述抓取绕过系统代理

### 6.1 问题

Guard 反查设备信息要抓 `description.xml`（§2.4 的第 ②③ 层）。这是**链路内 HTTP**——目标是局域网里的另一台设备，不是公网。如果它走了系统代理：

- macOS 的代理例外列表用 CIDR 写法时，**非豁免地址会被送进 `127.0.0.1:9565` 这类本地代理**；
- 代理一掉线（或压根不转发局域网地址），抓取失败；
- 三层反查全空 → 设备信息回落成「未知设备」（`guard.py:252-260`）、UDN 拿不到 → 身份退化成 `ip:<IP>`（`guard.py:396`）；
- 后果：**已经信任过的设备每次换 IP 都要重新弹窗**，用户看到的是「明明允许过了还在问」。

约定写在 `security/guard.py:29-31` 的注释里，并交叉引用 `ssdp._NO_PROXY`（即 `hancast_sidecar/ssdp.py:30`）。

### 6.2 修法

```python
_NO_PROXY = {"http": "", "https": ""}     # security/guard.py:32
```

三处 `requests.get` 全部带上 `proxies=_NO_PROXY`：

| 位置 | 用途 |
|---|---|
| `security/guard.py:541` | ② 层：USN 里没有 UDN 时抓 `LOCATION` |
| `security/guard.py:554` | ② 层：从 description.xml 取 UDN |
| `security/guard.py:598` | ③ 层：TCP 端口探测 `/description.xml` |

同一约定在别处也已落地：`protocol/dlna.py:31`（定义）、`:1007`、`:1157`；`ssdp.py:30`（定义）、`:646`、`:759`、`:1040`、`:1234`。

### 6.3 `96ab326` 的来历

提交 `96ab326`：`fix(security): 投屏来源描述抓取同样绕过系统代理`。

提交信息记录了一段发布事故：v2.2.11（`65ad943`「链路内 HTTP 绕代理」）打完 tag **之后**，本地又补了 `guard.py` 的这一处绕代理，但**没有随发布产物构建**。这个提交把它以独立提交落到 main，随下一版一起出包，**不重打 tag**。diff 内容就是新增 `_NO_PROXY` 常量 + 三处 `proxies=_NO_PROXY`。

## 8. 已知坑与边界

### 8.1 信任设备换 IP

- **能反查到 UDN 的话不会重新弹窗**：`check()` 的 `_ip_index` 未命中时会走三层反查（`guard.py:220-234`），UDN 命中信任表则就地更新 `entry.ip = caller_ip` 并落盘（`guard.py:226-232`），返回 `"trusted"`。
- **反查不到 UDN 就会重新弹窗**：身份退化成 `ip:<IP>`（`guard.py:396`、`:95-99`），换 IP 等于换设备。反查失败的常见原因：设备不响应单播 M-SEARCH、`description.xml` 不在 `COMMON_PORTS`（`guard.py:40`）里的任何端口上、或者 §6 的系统代理问题。
- **代价是一次同步阻塞**：反查发生在 SOAP 处理线程里，最坏约 1 秒（`guard.py:430`、`_resolve_parallel` 的 `timeout=1`）。这段时间控制点在等响应。

### 8.2 反查在一次弹窗里会跑两遍

`check()` 判定未知设备时调一次 `_resolve_device_info`（`guard.py:222`），紧接着 `create_pending_request` 又调一次（`guard.py:250`）。两次结果没有共享。第一层是 SSDP 缓存（0ms），所以缓存命中时无感；**缓存未命中时会连着做两轮并行网络探测**，最坏约 2 秒才开始弹窗。

### 8.3 黑名单命中不落盘

`check()` 命中信任设备时会 `cast_count += 1` 并 `_save()`（`guard.py:212-218`）；命中黑名单时只更新内存里的 `last_seen_at`（`guard.py:203-207`），**没有 `_save()`**。所以黑名单条目的「最后见到」时间永远是它被拉黑的那一刻，界面上看不出这台设备最近有没有又来敲过门。

### 8.4 「加入黑名单」这条策略路径从弹窗到不了

`wait_for_confirm` 里 `policy == "blacklist"` 会调 `_add_blacklisted`（`guard.py:295-297`），但这个分支要求 `pending.approved` 为真（`guard.py:287-289` 先判 `approved`，为假直接 return）。而弹窗只会发：

- `handleResponse(false, 'reject')` → `approved=false`，`policy='reject'`（`GuardConfirmModal.vue:14`）
- `handleResponse(true, 'once')` / `handleResponse(true, 'always')`（`:18`、`:22`）

结论：**没有任何 UI 路径能发出 `approved=true, policy='blacklist'`**，`guard.py:295-297` 这段从弹窗侧是死代码；`policy='reject'` 这个值也不在 `commands.py:1196` 登记的三种之内，它被原样写进 `pending.policy`（`guard.py:310`）然后因为 `approved=false` 提前返回、从不被读取。把设备拉黑的唯一办法是「允许一次」之后去设置页用 `GuardDeviceList` 的策略切换（§7.4）。

### 8.5 死 i18n key

`guard.deviceFrom`、`guard.once`、`guard.blacklist`（`src/locales/zh-CN.json:170`、`:171`、`:174`）在 `src/` 下没有任何引用——`grep -rn` 只命中语言文件自身。它们对应的正是 §8.4 里那条到不了的「加入黑名单」按钮和旧版弹窗文案。

同类：`screencast.dlnaNoPull`（`zh-CN.json:357`）、`screencast.dlnaLowBitrate`（`:358`）也没有引用——后端那两条结论是直接拼中文字符串写进 `_state["error"]` 的（`screencast/manager.py:359-361`、`:370-373`），没走 i18n。

### 8.6 前后端超时不同源

事件里带的 `timeout` 是**发事件那一刻**的配置值（`commands.py:1188`），前端用它起表（`guard.ts:32`）；后端 `wait_for_confirm` 用的是 `self._confirm_timeout`（`guard.py:276`）。两者数值相同，但：

- 起表时刻不同（事件经 JSON 行协议 → 壳层 → webview，有几十毫秒量级的传递延迟）；
- 若用户在弹窗期间改了超时设置，已弹出的那个请求仍按旧值走后端。

实际影响很小（两边都是默认拒绝），但**倒计时归零不等于后端已经拒绝**，日志口径以后端为准（`Request <id> timed out, rejected`）。

### 8.7 并发第二台设备静默失败

见 §4.2。前端自动拒绝第二个不同 IP 的请求（`guard.ts:133-137`），**没有任何用户可见提示**。同时投屏的场景（例如两台手机都想投）第二台必然失败，且失败原因只在后端日志里（`Request <id> denied by user`，`guard.py:288`）。

### 8.8 多网卡 / 隐私空间 / 网段变化

- `caller_ip` 直接取 TCP 连接的对端地址（`protocol/server.py:143`），**不经过 `_get_local_ip()` 那套网卡选择逻辑**（`commands.py:55-68`）。所以多网卡机器上，从哪块网卡进来的连接就用哪个源 IP 判定，`network_interface` 配置对 Guard 无影响。
- 设备身份只认 UDN/IP，**没有网段或 SSID 概念**。「公司网络信任、家里网络不信任」这种策略表达不出来——同一台电视在两个网段下是同一个 UDN，一次「始终允许」在两边都生效。
- ⚠️ 未验证：**「隐私空间 / 访客网络隔离」下 Guard 的行为，仓库里没有任何代码或测试涉及。** 可以确定的只有：如果客户端隔离导致反查（单播 M-SEARCH / TCP 探测）全部失败，设备名会退化成「未知设备」、身份退化成 `ip:<IP>`（§8.1）。隔离网络本身能否完成投屏属于 DLNA 可达性问题，不在 Guard 的判定范围内。

### 8.9 测试覆盖很薄

`hancast-backend/tests/` 下与 Guard 相关的只有 `test_guard_proxy_bypass.py`（43 行，只覆盖 §6 那一条）。**`check()` 的六个分支、`create_pending_request` 的同 IP 去重、`wait_for_confirm` 的超时/always/blacklist 分派、`remove_device` / `set_policy` 的 UDN 与 IP 双路匹配、`_parse_description_xml` 的三种命名空间，都没有单元测试。**

对比之下，屏幕投屏有 1001 行的 `test_screencast.py` 加 6 个端到端脚本。改 Guard 时请格外小心，并且优先补测试而不是靠手测。

### 8.10 关闭 Guard 的语义

`enabled = false` 时 `check()` 直接返回 `"trusted"`（`guard.py:196-197`），**信任/黑名单两张表仍保留在配置里**，重新打开后立即恢复生效。前端还有一层自动批准（`guard.ts:128-132`），但正常不会走到（后端已经不返回 `"pending"` 了）。

关闭 Guard 意味着局域网内任何设备都能无条件把画面推到本机——这是 §1 威胁模型的完全敞开状态。设置页的开关文案（`guard.enable`「启用投屏确认」）没有把这个后果写出来。

### 8.11 Guard 只挂在一个 SOAP 动作上

闸门在 `AVTransport_SetAVTransportURI`（`protocol/dlna.py:834-850`）。`Play` / `Stop` / `Pause` / `SetVolume` 等其它动作**不做 Guard 检查**（`protocol/dlna.py:673-699` 的通用分派里没有第二处 `check()`）。

正常控制点总是先 `SetAVTransportURI` 再 `Play`，所以这条闸门够用。但一个**跳过 SetAVTransportURI 直接发 `Play`** 的控制点不会被拦——不过它也没有可播的 URI，实际影响取决于此前是否已有会话。这属于设计取舍而非缺陷，但值得知道边界在哪。

### 8.12 与屏幕投屏的耦合点

两条链路共享的是**基础设施**，不是配置：

| 共享物 | 位置 |
|---|---|
| 配置文件与目录 | `utils/config.py:23-34` |
| 日志与模块标签（`hancast.guard` → 「投屏确认」） | `utils/logger.py:114-127`（`:122`） |
| 事件通道 `protocol_io.emit_event` | `commands.py:1190`（Guard）、`screencast/manager.py:469`（屏幕投屏） |
| `_get_local_ip()`（屏幕投屏拼 URL 用；Guard **不用**） | `commands.py:55-68` |
| `_stop_cast` 的如实回报（两边都用） | `commands.py:589-625` |
| `params.py` 后台参数 | 屏幕投屏大量使用；**Guard 一项都不用**（§4.4） |

`commands.py:295` 的 `cleanup()` 顺序是先 `screencast.cleanup()`；Guard 没有需要清理的运行时资源（pending 记录随进程消失，两张表是每次改动即落盘的）。
