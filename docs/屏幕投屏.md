## 1. 目标场景与两个出口

「屏幕投屏」把本机屏幕（或某个窗口所在的屏幕区域）编码成 **HLS 直播流**，再由一个内建 HTTP 服务分发出去。两个出口共用**同一份**编码产物，只在分片粒度和消费方上有差别（`screencast/manager.py:12-14`）。

| 出口 | target 值 | 消费方 | 默认分片 | 交付方式 |
|---|---|---|---|---|
| DLNA 通道 | `dlna` | 电视 / 大屏渲染器 | 2 秒（`params.py:43`） | SOAP `SetAVTransportURI` + `Play` 把 m3u8 URL 交给电视，电视自己来拉 |
| 浏览器通道 | `browser` | 手机 / 任意浏览器 | 1 秒（`params.py:43`） | 给用户一条 `/r/<session_id>` 观看链接，页面内 hls.js 播放 |

选择「1 秒 vs 2 秒」的原因：浏览器可以承受更激进的切片，电视端分片越小、请求越密，老渲染器容易跟不上（`screencast/httpd.py:1-12` 的延迟下限说明：浏览器 1 秒分片端到端约 1–3 秒，电视 2 秒分片约 3–6 秒）。

### 1.1 DLNA 通道链路

│                                                                  │

关键代码位：`screencast/manager.py:372-383`（拼 m3u8 URL、构造 DIDL、调 `session.play`）；推流失败的两类异常分别处置在 `manager.py:384-391`。

观看页模板：`screencast/www/index.html`。第 72-76 行把后端注入的 `__SESSION_ID__` 拼成**同源相对路径** `/hls/<sid>/live.m3u8`；第 171-201 行是 hls.js 分支（含重试上限与「投屏已结束」的 404 处理）；第 162-169 行是 Safari 原生 HLS 分支；第 203-205 行是两条路都不可用时的兜底文案。声音起播策略（自动播放策略下的带声试播 → 静音兜底 → 「点击开启声音」按钮）在 86-140 与 151-156，见 §2.6。

### 1.3 会话隔离

每次 `start()` 生成一个 6 位十六进制会话号（`manager.py:177`：`secrets.token_hex(3)`），分片目录是 `<临时目录>/hancast_screencast_hls/<session_id>/`（`manager.py:46-48`、`manager.py:361`）。**URL 随会话变化**是刻意的：复用同一目录会让上一轮的 `live.m3u8` 残留，电视拉到的是已被删除分片的死播放列表（`capture.py:57-58`、`httpd.py:282-284`）。

### 2.1 五个阶段

### 2.2 采集源选择

`source` 的形态（`manager.py:88`、`ffmpeg_manager.py:1040-1042`）：

```json
{"type": "screen", "id": "desktop"}
{"type": "screen", "id": "screen:0,0,1920,1080"}
{"type": "window", "id": "window:0x12F0AB", "title": "Chrome · Google Chrome"}
{"type": "window", "id": "win:1234", "title": "Chrome · Google Chrome", "screen_no": 1, "crop": [x,y,w,h], "crop_norm": [fx,fy,fw,fh]}
```

- 缺省即「整个屏幕」：`manager.py:104-106`，`source` 为空时补 `{"type":"screen","id":"desktop"}`。
- Windows 窗口源的 id 是 `window:0x<hwnd>`（窗口句柄，`:770`；标题只作显示用），启动时按句柄换算成窗口矩形去抓屏幕区域（见 §3.3）；macOS 仍是 `win:<num>` + 比例裁剪（`:463`）。
- 「整个屏幕」在多屏机器上抓的是**所有显示器的并集**，前端为此专门给出提示文案（`src/locales/zh-CN.json:216`），并且实测过并集尺寸 4000×2571 这种奇数高度会被 x264 拒绝初始化（`ffmpeg_manager.py:602-604` 的 `_list_monitors` docstring、`ffmpeg_manager.py:976-981`）。
- 指定某块显示器：`_list_monitors()`（`ffmpeg_manager.py:599-667`）产出 `screen:x,y,w,h`，Windows 上翻译成 gdigrab 的 `-offset_x/-offset_y/-video_size`（`ffmpeg_manager.py:1032-1037`）。**非 Windows / 非 macOS 直接返回空表**（`ffmpeg_manager.py:618-619`）。
- 指定窗口：见 §3。macOS 上窗口＝「抓它所在的屏再按几何裁」，且裁剪坐标必须是**此刻**的，所以 `start()` 会先 `refresh_window()` 重算一次（`manager.py:109-113`）。

### 2.3 编码与切片参数（契约）

`capture.py:89-124` 是唯一决定编码参数的地方，每一项都有明确理由：

| 参数 | 值 | 为什么 | 证据 |
|---|---|---|---|
| `-profile:v -level` | `main` / `42` | 电视解码器普遍只认 Main；High 的 8×8 变换在老渲染器上直接拒播，表现为「换个分辨率就黑屏」 | `capture.py:91-93` |
| `-g` | `fps × segment_seconds` | HLS 只能在关键帧处切片。分片降到 1 秒而 GOP 还是 2 秒，切片点照样两秒一个，降延迟完全落空 | `capture.py:95-98`；测试 `tests/test_screencast.py:482` `test_gop_follows_segment_length` |
| `-r` | `fps` | 输入设备帧率失控时按目标帧率 CFR 封顶（macOS avfoundation 实测能让 raw 管道冲到 5000fps） | `capture.py:99-100`、`ffmpeg_manager.py:1051-1055` |
| `-x264-params` | `scenecut=0:open_gop=0:repeat_headers=1` | 屏幕内容几乎每帧都像「场景切换」，默认策略会在每次切窗口时插 IDR，HLS 于是切出几百毫秒的碎分片，电视解析器直接放弃。固定 + 闭合 GOP + 重复 SPS/PPS 让每个分片能独立起解 | `capture.py:101-105` |
| `-max_muxing_queue_size` | `screencast.muxing_queue_size`（默认 1024） | 屏幕帧到达是突发的（切窗口/滚动），默认 10 帧复用队列溢出后 FFmpeg 报 `Error queuing more packets` 并退出，表现为投屏中途断流 | `capture.py:113-115` |
| `-hls_flags` | `delete_segments+independent_segments+temp_file` | `temp_file` 先写 `.tmp` 再改名，否则客户端可能在半截播放列表上拿到没有 `#EXTM3U` 结尾的内容并判定流损坏 | `capture.py:119-121` |
| `-pix_fmt` | `yuv420p` | 兼容性 | `capture.py:94` |
| `-tune` | `zerolatency` | 直播低延迟 | `capture.py:90` |
| 音频 | `-c:a aac -b:a 128k -ar 48000 -ac 2`，无声时 `-an` | 有音频输入才写 aac | `capture.py:107-110`；测试 `tests/test_screencast.py:505` |

缩放滤镜：`build_scale_filter()`（`ffmpeg_manager.py:1020-1033`）

```
scale=<w>:<h>:force_original_aspect_ratio=decrease:force_divisible_by=2
```

`decrease` 保证比上限小的源不被放大重编码；`force_divisible_by=2` 是唯一兜底——x264 拒绝奇数尺寸（`width not divisible by 2` 后整个编码进程退出），而桌面尺寸经常就是奇数（Windows 显示缩放会给出 1917×1081 这类值）。宽高为 0 时回落到后台参数 `screencast.max_width` / `screencast.max_height`（默认 1920×1080，`params.py:70-75`）。

### 2.4 一条真实拼装出来的命令行

下面是按 `capture.py:78-124` 的拼接顺序、代入默认参数（`params.py` 中 `browser_segment_seconds=1`、`playlist_size=6`、`muxing_queue_size=1024`、`x264_preset=veryfast`）与前端默认画质（`ScreenCastPanel.vue:26-29`：1280×720 / 15fps / 2M）后**实际会组装出的参数序列**，场景为 Windows + 浏览器通道 + 整屏 + 麦克风 + WASAPI 环回：

```bash
ffmpeg -hide_banner -loglevel error -nostdin \
  -f gdigrab -framerate 15 -i desktop \
  -f dshow -i "audio=麦克风阵列 (Realtek(R) Audio)" \
  -f s16le -ar 48000 -ac 2 -i pipe:0 \
  -filter_complex "[1:a]aformat=sample_fmts=s16:sample_rates=48000:channel_layouts=stereo[m0];[2:a]aformat=sample_fmts=s16:sample_rates=48000:channel_layouts=stereo[m1];[m0][m1]amix=inputs=2:duration=longest:dropout_transition=0:normalize=0" \
  -vf "scale=1280:720:force_original_aspect_ratio=decrease:force_divisible_by=2" \
  -c:v libx264 -preset veryfast -tune zerolatency -profile:v main -level 42 \
  -b:v 2M -pix_fmt yuv420p -g 15 -r 15 \
  -x264-params scenecut=0:open_gop=0:repeat_headers=1 \
  -c:a aac -b:a 128k -ar 48000 -ac 2 \
  -max_muxing_queue_size 1024 -f hls -hls_time 1 -hls_list_size 6 \
  -hls_flags delete_segments+independent_segments+temp_file \
  -hls_segment_filename "%TEMP%\hancast_screencast_hls\a1b2c3\seg%03d.ts" \
  "%TEMP%\hancast_screencast_hls\a1b2c3\live.m3u8"
```

macOS + DLNA 通道 + 指定窗口 + 仅系统声音（Audio Tap），差异部分：

```bash
ffmpeg -hide_banner -loglevel error -nostdin \
  -use_wallclock_as_timestamps 1 -f avfoundation -framerate 15 -i 1:none \
  -f avfoundation -i :2 \
  -vf "crop=trunc(iw*0.520833/2)*2:trunc(ih*0.416667/2)*2:trunc(iw*0.239583):trunc(ih*0.291667),scale=1920:1080:force_original_aspect_ratio=decrease:force_divisible_by=2" \
  -c:v libx264 -preset veryfast -tune zerolatency -profile:v main -level 42 \
  -b:v 2M -pix_fmt yuv420p -g 30 -r 15 \
  -x264-params scenecut=0:open_gop=0:repeat_headers=1 \
  -c:a aac -b:a 128k -ar 48000 -ac 2 \
  -max_muxing_queue_size 1024 -f hls -hls_time 2 -hls_list_size 6 \
  -hls_flags delete_segments+independent_segments+temp_file \
  -hls_segment_filename "/tmp/hancast_screencast_hls/a1b2c3/seg%03d.ts" \
  "/tmp/hancast_screencast_hls/a1b2c3/live.m3u8"
```

阅读这两条样例时需要注意：

- **日志里的真实形式是单行**：`logger.info(f"[ScreenCast] HLS cmd: {' '.join(cmd)}")`（`capture.py:135`），不带 shell 引号；上面为了可读性做了换行并补了引号。要看真命令，去日志里搜 `HLS cmd:`。
- 会话号 `a1b2c3`、临时目录、设备名都是示例值；**参数序列与顺序**才是代码保证的部分。
- `crop=` 里的六个比例数字是示例（真实值由 `_window_entry` 按当时窗口几何算出，`ffmpeg_manager.py:445-473`）；表达式**格式**由 `build_crop_filter`（`ffmpeg_manager.py:476-490`）决定，`trunc(iw*fw/2)*2` 的写法是为了保证裁出来是偶数。
- `-g` 与 `-hls_time` 必须同源：`-g = fps × segment_seconds`（`capture.py:98`）。上面 Windows 例是 15×1=15，macOS 例是 15×2=30。
- macOS 例里只有一路音频（仅系统声音）时**不会**出现 `-filter_complex`，两路才有（`ffmpeg_manager.py:1141-1145`）。
- `-vf` 出现在**所有** `-i` 之后，这不是风格问题，见 §7.2。

### 2.5 HTTP 分发

服务：`screencast/httpd.py`，`aiohttp` 跑在独立线程（`httpd.py:84-128`）。

| 路由 | 处理函数 | 说明 |
|---|---|---|
| `GET /r/{session_id}` | `httpd.py:237-253` | 观看页。会话不在册 → 404 文本「投屏已结束或地址无效」；在册则读 `www/index.html`，替换 `__SESSION_ID__` 与 `__PLAYER_CONFIG__` 后返回 |
| `GET /static/{filename}` | `httpd.py:255-262` | 观看页静态资源（`hls.min.js` 等）。`basename` + 扩展名白名单双重限制 |
| `GET /hls/{session_id}/{filename}` | `httpd.py:277-307` | 播放列表与分片。目录穿越由 `_safe_hls_path`（`httpd.py:266-275`）拦 |

端口：默认 **8765**（`httpd.py:32`），启动时先试 8765、被占用则退回随机端口（`httpd.py:84-128` 的 `for try_port in (port, 0)`），实际端口从 `site._server.sockets[0].getsockname()[1]` 读回。因此**URL 里的端口不一定是 8765**，前端一律用后端返回的 `watch_url` / `url`。

MIME 与响应头（`httpd.py:291-306`）：

```
.m3u8 → application/vnd.apple.mpegurl
.ts   → video/mp2t
其它  → application/octet-stream
Cache-Control: no-cache, no-store
transferMode.dlna.org: Streaming
contentFeatures.dlna.org: DLNA.ORG_OP=01;DLNA.ORG_CI=0;DLNA.ORG_FLAGS=01700000000000000000000000000000
```

两个 DLNA 头是必需的：渲染器靠它们区分「边下边播」和「先下完再播」，缺 `transferMode` 的直播播放列表会被部分电视当普通文件缓冲，表现为控制器收到 `Play` 却迟迟等不到拉流请求（`httpd.py:300-306`）。`Cache-Control` 必需：直播列表每秒重生成，缓存会让观众看到过期分片（`httpd.py:297`）。

**关于 CORS：这个 HTTP 服务不发任何 CORS 头。** 全仓 `Access-Control-Allow-Origin` 只出现在 `media/server.py:491`（那是解析代理，不是投屏服务）。浏览器通道之所以不需要 CORS，是因为观看页与流同源、页面里用的是相对路径（`www/index.html:72-76`），不会触发跨源预检。**跨源嵌入观看页（例如把 `/r/<sid>` iframe 进别的站点）会因为拿不到 CORS 头而失败。**

拉流证据：`_note_pull` / `_note_miss`（`httpd.py:194-226`）统计 `pulls`（`.m3u8` 命中次数）、`misses`（要的文件不在，含未注册会话与已删除分片）、`clients`（独立客户端，上限 64）。`viewers()`（`httpd.py:186-193`）只统计 `screencast.viewer_window_seconds`（默认 15 秒）窗口内拉过播放列表的独立客户端。

DLNA 起流校验消费这份证据：`manager.py:348-380` 的 `_verify_dlna_pull` 在 `screencast.dlna_verify_seconds`（默认 12 秒）内轮询，

- `pulls > 0 且 misses >= 6` → 报「{设备} 跟不上当前码率（多个分片已被删除），请降低分辨率或码率后重试」（`manager.py:358-364`）；
- `pulls > 0` → 记一条 info 后收工（`manager.py:365-369`）；
- 窗口内一次都没拉到 → 报「{设备} 在 N 秒内没有拉取播放列表：请确认电视与本机在同一网段、允许 HanCast 接收局域网连接，或换较低分辨率重试」（`manager.py:370-380`）。

设计动机写在 `manager.py:349-351`：电视不会把「播不出来」回报给控制器，黑屏时「根本没拉到」和「拉到了但解码不了」的处置方式完全不同，只能靠本机侧的拉流证据区分。契约测试：`tests/test_screencast.py:839-886`（`TestDlnaVerify`）。

### 2.6 播放侧

浏览器观看页的播放器配置由后端注入（`httpd.py:47-56` `player_config()`）：

```python
max_latency = max(param("player.live_max_latency_duration_count"),
                  param("player.live_sync_duration_count") + 1)
```

**`liveMaxLatencyDurationCount` 必须严格大于 `liveSyncDurationCount`**，否则 hls.js 构造函数直接抛错、播放页白屏；`max()` 这层夹逼就是防用户把两个后台参数配成非法组合（`httpd.py:47-56`）。

`www/index.html:171-201` 的 hls.js 分支在注入配置之上再叠一层固定默认：`enableWorker:true`、`manifestLoadingMaxRetry:4`、`manifestLoadingRetryDelay:1000`、`levelLoadingMaxRetry:4`、`fragLoadingMaxRetry:4`；遇到 404 直接显示「投屏已结束」而不是无限重试。

**声音起播（v2.3.14）**：浏览器的自动播放策略只放过免手势的**静音**起播，而 `<video>` 上写死 `muted` 会让观看页永远不出声——这就是 v2.3.13 及以前「浏览器通道没声音」的根因，现在 video 元素不再硬编码 `muted`（`index.html:58`）。起播流程（`index.html:86-140`）：

1. `tryStart()`（`:117-140`）先直接 `play()` 试带声起播——Safari 允许自动播放时能直接出声、完全无感；被拒则走 `fallbackToMuted()`（`:110-115`）退回静音起播并亮出「点击开启声音」按钮（`showVideo()`，`:151-156`）；
2. 1.2 秒保险丝（`:132-139`）：个别引擎的 `play()` 被拦下时既不 resolve 也不 reject，画面还没起来就切静音路径，不让用户干等；
3. 按钮点击或原生控件解除静音都算手势，`volumechange`（`:95-100`）收到 `!muted` 即收起按钮；已定性为静音起播的会话重连时直接走静音（`needManualSound`，`:90`），不重复挨拒。

音频从起播即随流拉取，不是「先静音再补」——观看到按钮点亮后出声，HLS 时间轴不中断。验收：`tools/verify-watch-page-sound.mjs`（真实 Chromium 双 pass：无手势必须看到静音起播 + 按钮，点击后 `volumechange` 解除）。

电视侧没有播放代码——它只是一个 HLS 客户端。HanCast 能观测到的只有 §2.5 的拉流证据。

## 3. 平台采集差异

### 3.1 三平台一览

| 能力 | Windows | macOS | Linux |
|---|---|---|---|
| 整屏采集 | `gdigrab -i desktop` | `avfoundation -i <idx>:none` | **Wayland**：随包 helper `hancast-wlgrab` 出 BGRA 帧 → `-f rawvideo -i pipe:0`（`ffmpeg_manager.py:1113-1121`）；**X11 会话**：`x11grab -i $DISPLAY`（`ffmpeg_manager.py:1122-1130`） |
| 指定显示器 | `-offset_x/-offset_y/-video_size`（`ffmpeg_manager.py:1086-1091`） | 按 `screen_no` 选设备索引（`ffmpeg_manager.py:1092-1108`） | Wayland 下逐块 `wl_output` 列出，id 形如 `wl:DP-2`（`wlgrab.py:194-221`、`ffmpeg_manager.py:629-635`）；X11 会话仍是空列表 |
| 指定窗口 | **按窗口矩形抓 desktop 区域**：`GetWindowRect`/`DWMWA_EXTENDED_FRAME_BOUNDS` 换算 `-offset_x/-offset_y/-video_size`（`ffmpeg_manager.py:1063-1076`） | **不存在窗口输入**，抓所在屏 + `crop`（`ffmpeg_manager.py:1109-1112`） | ✗ 未实现（`_list_windows` 无 Linux 分支；Wayland 下也拿不到窗口级句柄） |
| 麦克风 | `-f dshow -i audio=<名>` | `-f avfoundation -i :<idx>` | `-f pulse -i <source 名>`，没落到具体设备时回落 `default`（`ffmpeg_manager.py:1228-1242`） |
| 系统声音 | WASAPI 环回 → sidecar 采 PCM → `-f s16le -i pipe:0` | CoreAudio Audio Tap（14.2+）或 BlackHole | `<sink>.monitor` 镜像源，`-f pulse` 直接抓（`ffmpeg_manager.py:1221-1238`、枚举见 `pulse.py:111-148`） |
| 多路混音 | `amix`（`ffmpeg_manager.py:1193-1194`） | `amix`（`ffmpeg_manager.py:1209-1213`） | `amix`（麦克风 + monitor 开两个 `-f pulse` 输入，`ffmpeg_manager.py:1230-1233`） |

Linux 现状一句话（v2.3.19 起）：**Wayland 走随包 helper、X11 走 x11grab，显示器与音频都能选**。仍然没有的是窗口级抓取——Wayland 的合成器协议压根不暴露「给我一个窗口句柄让我抓」这种能力（screencopy 的单位是 output，不是 window）。

### 3.2 macOS

**窗口枚举**：`ffmpeg_manager.py:355-406` `darwin_windows()`，用 ctypes 直接调 CoreGraphics（`CGWindowListCopyWindowInfo`），不引 pyobjc。

- 系统窗口按 owner 过滤：`_CG_SYSTEM_OWNERS = {"WindowManager"}`（`ffmpeg_manager.py:241`、用于 `:390`）。
- **没有「屏幕录制与系统音频」权限时，系统会静默去掉 `kCGWindowName`**，窗口标题退化成 App 名（`darwin_windows` docstring，`ffmpeg_manager.py:355` 起）。前端把这个情况写进了提示文案：「macOS 未授予『屏幕录制』权限时窗口标题会显示为『（无标题）』，此时只能按所有者识别」（`src/locales/zh-CN.json:226`）；标签拼装逻辑在 `ffmpeg_manager.py:460-461`。
- 读 `CGWindowBounds` 里的数值必须走 `_cf_num`（`ffmpeg_manager.py:299-311`）：`kCFNumberDoubleType` 是 6 而不是 12，按 SInt128 读会越界写，结果是所有 bounds 变成 `5e-315`、枚举出 0 个窗口。
- 显示器枚举 `darwin_displays()`（`ffmpeg_manager.py:314-352`）要把 CoreGraphics 的 y-up 坐标翻成窗口坐标系（`top: -b.y`），并带上 Retina 缩放比。

**窗口→采集参数**：`_window_entry()`（`ffmpeg_manager.py:445-473`）同时产出像素版 `crop` 与**比例版** `crop_norm`，真正下发给 ffmpeg 的是比例版（`build_video_input` 优先取 `crop_norm`，`ffmpeg_manager.py:1041-1042`）。原因写在 `ffmpeg_manager.py:467-472`：avfoundation 送进 `crop` 滤镜的坐标系是它**实际采集的那块缓冲区**，而缓冲区尺寸在不同机器上不保证等于算出来的像素尺寸（HiDPI / 缩放分辨率下差 2 倍），像素版会裁到错位的一块。比例版与缓冲区尺寸无关，只要长宽比一致即可，偶数尺寸交给后面的 `scale`。

**屏幕设备索引不固定**：`avfoundation_screen_indexes()`（`ffmpeg_manager.py:170-216`）动态枚举。曾经固定用 `1`，在装有 OBS Virtual Camera 的机器上抓到的是摄像头（docstring，`ffmpeg_manager.py:170` 起）。探测失败时回落索引 1 并打 warning（`ffmpeg_manager.py:1047-1050`）。

**系统声音（Audio Tap）**：`screencast/macos_tap.py`。avfoundation 只认「输入设备」，而系统声音是**输出**，所以必须自己造一个输入设备：

```
AudioHardwareCreateProcessTap  ──► 一个进程级 tap（抓取全局立体声，排除自己）
        +
AudioHardwareCreateAggregateDevice ──► 名为「HanCast 系统声音」的聚合输入设备
        (uid: com.hancast.system-audio)
        ▼
avfoundation 里多出一个可选设备  ──► ffmpeg -f avfoundation -i :<idx>
```

- 设备名与 UID：`macos_tap.py:28-29`。
- 可用性判定：`supported()` = `hasattr(_CA, "AudioHardwareCreateProcessTap")`，即 **macOS 14.2+**（`macos_tap.py:182-186`）。
- `setPrivate: 0` 是整件事的关键（`macos_tap.py:340-344`，`argtypes=[ctypes.c_int8]` 因为 arm64 的 BOOL 是 int8）：默认建出来的是**私有环回**，而 ffmpeg 是另一个进程，于是 avfoundation 里永远看不到它。
- 排除自己的进程：`_self_pids` / `_self_process_objects`（`macos_tap.py:211-236`）。排除列表要的是 `AudioObjectID` 而不是 unix pid，传 pid 会得到 `'!obj'`；不排除的话自己投出去的音频会形成回音。
- 残留聚合设备清理：`_stale_aggregate()`（`macos_tap.py:301-311`）。聚合设备是系统级的，进程退出后设备仍留在系统里，表现为一个永远静音的假设备，且同 UID 二次创建报 `'nope'`。`ensure_device()`（`macos_tap.py:385-415`）会先清残留；`destroy_device()`（`macos_tap.py:418-432`）在停止/清理时销毁，进程被强杀时的残留由下一次 `ensure_device` 兜底（`macos_tap.py:426`）。
- 索引会变：Audio Tap 设备是枚举时现建的，avfoundation 索引跟着其他设备增减走。界面存的是用户当时看到的索引，`start()` 会按名称换成本次枚举到的真实索引（`manager.py:147-154`），测试见 `tests/test_screencast.py:924` `test_macos_tap_index_is_refreshed_at_start`。
- 14.1 及以下：只列物理设备，装了 BlackHole 的用户照旧可选（`ffmpeg_manager.py:866-867`、`ffmpeg_manager.py:1128-1133`）。BlackHole 需要用户自己在「音频 MIDI 设置」里把系统输出路由进去。
- 麦克风权限：见 §7.4。

### 3.3 Windows

**显示器 / 窗口枚举**：`_list_monitors()`（`ffmpeg_manager.py:599-667`）、`_list_windows()` + `_castable()`（`ffmpeg_manager.py:669-776`）。窗口用 `EnumWindows`，可投性判据全部来自实测（`_castable` docstring，`ffmpeg_manager.py:708` 起）：

- 必须有 `WS_CAPTION` 或 `WS_THICKFRAME`；
- 排除 `WS_EX_NOACTIVATE` / `WS_EX_TOOLWINDOW`（否则列表里会混进 `com.han.hancast-siw` 这类 16×16 的壳窗口、`CHeadBarWindow` 之类的输入法条）；
- 排除 `DWMWA_CLOAKED`：**另一个虚拟桌面上的窗口对 gdigrab 不可见（BitBlt 全黑）**；
- 排除位于 `-32000,-32000` 的窗口（最小化 / `WinDisplay` 之类）。

**窗口捕获（v2.3.14 起不用 gdigrab 窗口模式）**：列表里每条窗口的 id 是句柄 `window:0x<hwnd>`（`:784`，标题只作显示），起流时 `build_video_input`（`ffmpeg_manager.py:1034-1134`，窗口分支 `:1063-1070`）用 `_parse_window_hwnd`（`:72-86`）解出句柄、`_window_capture_rect`（`:87-159`）算出此刻矩形，翻译成 `-offset_x/-offset_y/-video_size` 抓 desktop。为什么换掉 gdigrab 的 `-i title=`：它内部是 `GetDC(hwnd)`+BitBlt，DWM 时代对 GPU 合成的窗口（浏览器 / Electron 这类）只能抓到黑帧（实测同窗口 hwnd 模式 20KB 纯白 PNG vs 同矩形区域模式 1.4MB 完整画面），且 `FindWindowW` 精确匹配标题、标题一变就 I/O error。矩形口径：优先 `DWMWA_EXTENDED_FRAME_BOUNDS`（去掉 `GetWindowRect` 含的 8px 隐形 resize 边框——实测 2576×1408 → gdigrab 有效区 2560×1392；客户区 900×620 → 884×581，少掉的 16×39 是边框+标题栏）；最小化先 `SW_RESTORE` 并等 0.15s；置前是尽力而为（前台锁会让 `SetForegroundWindow` 失败，失败照常抓，`:127-128`）；别的虚拟桌面（`DWMWA_CLOAKED`）、已关闭、矩形过小（宽或高 <80）都判不可用，起流报「选中的窗口已关闭或不可见（最小化/其它虚拟桌面），请刷新窗口列表重选」（`:1068-1070`）。gdigrab 抓的仍是**屏幕上的那块矩形**：别的窗口压在它上面时，投出去的就是压着它的那个（不置顶时同一份代码两轮亮度 235 vs 45）。全部实测记录在 `tools/probe-win-window-picker.py:9-18`（另见 `:285-288`）。旧格式 `window:<标题>` 的请求仍走 `-i title=<标题>` 兜底（`:1076-1083`）。前端提示文案把「压着它」这条讲清楚了（`src/locales/zh-CN.json:226`）。

**dshow 设备枚举与「分段头解析」**：`_list_audio_devices()`（`ffmpeg_manager.py:793-911`）。`ffmpeg -list_devices true -f dshow -i dummy` 的输出解析有两条坑：

1. **新版 ffmpeg 不再打印 "DirectShow audio devices" 这条分段头**——那条字符串压根不在 exe 里（用 `findstr` 验过，见 `ffmpeg_manager.py:801-808` 的注释）。所以主判据是设备行尾部的 `(audio|video|none)` 后缀：`r'"(.+)"\s*\((audio|video|none)\)\s*$'`（`ffmpeg_manager.py:818`）；只有解析不到后缀时才回落到分段头模式（测试 `tests/test_screencast.py:118` `test_windows_falls_back_to_dshow_section_header`）。
2. **"Alternative name" 行也带引号**，在分段头格式下会伪装成设备混进来，必须显式排除（`ffmpeg_manager.py:828-830`）。

**编码**：Windows 上 `ffmpeg -list_devices` 的输出可能是 cp936 而不是 UTF-8，直接 `decode()` 会得到空枚举结果，所以所有子进程输出走 `_run_utf8()`（`ffmpeg_manager.py:39-49`）。

**系统声音**：WASAPI 环回，见 §4.2。

**多屏并集**：`_list_monitors` docstring 记录了实测 4000×2571（奇数高度，x264 拒绝初始化），这是 `force_divisible_by=2` 存在的直接原因。

### 3.4 Linux（v2.3.19：Wayland 改走随包原生 helper）

**为什么要改**：v2.3.18 及以前，Linux 不分会话一律 `-f x11grab -i $DISPLAY`。Hyprland/sway 的 XWayland 是 `-rootless` 起的，**原生 Wayland 窗口不在 X 的窗口树里**，于是 x11grab 连得上、帧率正常、投出去的每一帧却是空的 root window——纯黑，日志一个字都不报。2026-10-17 在 CachyOS + Hyprland 0.56.2 量化：同一时刻 `x11grab` 采到的帧 `signalstats.YAVG=16.03`（黑），`grim` 走 wlroots screencopy 采到 44.28。ffmpeg n9.0.2 的 `-demuxers` 里没有任何 Wayland 屏幕输入（只有 x11grab / kmsgrab / fbdev），pipewire 抓取那条路要 portal，官方构建也没编——所以只能自带原生 helper，见 §7.2。

**helper**：`linux-capture/`（Rust，`wayland-client` + `wayland-protocols-wlr`），产物 `hancast-wlgrab`，随包进 `/usr/lib/HanCast/`（与 sidecar exe 同级）。协议是 `zwlr_screencopy_manager_v1` 的 SHM 路径（grim / wf-recorder 同一套），接口写在 `wlgrab.py:17-25` 的模块 docstring：

```
hancast-wlgrab list                    → stdout 一行 JSON 数组（每块 wl_output 的 name/description/宽高/scale/x/y）
hancast-wlgrab capture [--output N] [--fps N] [--x --y --width --height] [--cursor]
    stdout：每帧 width*height*4 字节的紧凑 BGRA，无分隔
    stderr：首行 HDR {…}（真实缓冲区宽高、stride、y_invert…），结束 DONE n 帧，失败 ERR <原因>
退出码：0 正常 / 2 参数错 / 3 连不上合成器 / 4 首帧抓不到 / 5 合成器给的格式不是 ARGB/XRGB
```

**sidecar 侧的三段接线**：

1. **探测**：`wlgrab.find_helper()`（`wlgrab.py:124-155`）按候选路径顺序（`HANCAST_WLGRAB` 环境变量 → cwd → sidecar exe 同级 → resources 层 → 开发目录，`wlgrab.py:54-84`）**真的 exec 一次 `list`** 并解析 JSON 才算可用。这条是 v2.3.17 随包 mpv 那个坑的直接教训：**存在性证明不了运行时能跑**，所以「文件在但跑不起来」要把逐个候选的死因原样带出来（`wlgrab.py:144-151`）。结果进程级缓存一次，屏幕列表缓存 3 秒（`wlgrab.py:44-46`、`list_outputs` `:166-183`）。
2. **枚举**：`monitor_entries()`（`wlgrab.py:194-221`）把每块 `wl_output` 变成前端 `screens` 里的一条 `wl:<名字>`；主屏认「坐标原点那块」（`_primary_index` `:186-191`），拿不到就退化成第一块。`desktop_title()`（`:224-232`）把 Wayland 下「整个屏幕」的语义写成「投主显示器 DP-x」——Wayland 没有「所有显示器的并集」这个东西，让用户按 Windows 的经验理解这一项就会投错屏。
3. **起流**：`capture.start_hls()`（函数 `capture.py:51`，Wayland 门在 `:77-107`）在 Linux + 非窗口源 + `WAYLAND_DISPLAY` 存在时先拉起 `WlGrabSession`；**拿不到 helper 或 helper 起不来就直接失败并说明原因，绝不退回 x11grab**（退回就等于把「黑屏」这个原始故障再发一遍）。首帧尺寸取 helper 的 `HDR`，不用 `list` 的 mode（缩放屏上两者差 scale 倍，`-video_size` 差一个字节整条流就读歪成斜纹，`wlgrab.py:248-254` 的类 docstring）。helper 的 stdout 作为 FFmpeg 的 stdin 输入 0（`capture.py:187-200`），FFmpeg 起来后父进程立刻关掉自己那份读端，否则 helper 退出时 FFmpeg 收不到 EOF、停止投屏变成等满超时（`capture.py:196-200`）；看门狗会检查 helper 是否还活着（`capture.py:367`），`stop()` 收尾时先收 FFmpeg 再收 helper（`capture.py:436-440`）。

**X11 会话照旧**：`WAYLAND_DISPLAY` 不存在时 `wayland_session()` 为假（`wlgrab.py:49-51`），命令仍走 `x11grab`（`ffmpeg_manager.py:1122-1130`），行为与 v2.3.18 一致。

**音频**：`_list_audio_devices()` 在 Linux 上不再返回空表，改走 `pulse.list_input_devices()`（`ffmpeg_manager.py:807-813`、`pulse.py:111-148`），详见 §4.6。

**前端**：Wayland 会话但 helper 不可用时，面板在「捕获源」正下方摆一条错误（`ScreenCastPanel.vue:273-276`，文案 `screencast.wlgrabMissing` / `wlgrabHint`，`src/locales/zh-CN.json:248-249`），并且**「开始投屏」按钮置灰**（`ScreenCastPanel.vue:64-75`）——这条存在的理由是：那种情况下投出去必然黑屏，让用户点下去只会得到一句「投屏正常但没画面」。

⚠️ 未实现：Linux 的窗口枚举/窗口抓取（Wayland 协议不提供窗口级 screencopy）、X11 会话下的单显示器选择（`_list_monitors` 在非 Wayland 分支返回空，`ffmpeg_manager.py:629-635`）。

## 4. 音频链路

### 4.1 混音：aformat 规整 + amix

多路音频必须先规整再混：`_mix_filter()`（`ffmpeg_manager.py:1135-1153`）

```
[1:a]aformat=sample_fmts=s16:sample_rates=48000:channel_layouts=stereo[m0];
[2:a]aformat=sample_fmts=s16:sample_rates=48000:channel_layouts=stereo[m1];
[m0][m1]amix=inputs=2:duration=longest:dropout_transition=0:normalize=0
```

- **为什么先 `aformat`**：`amix` 要求各输入的采样率、声道、采样格式一致，而 dshow 麦克风给的是设备原生格式（44.1k 单声道很常见），WASAPI 环回又跟着渲染设备走（48k 立体声），直接串起来混音图建不起来，FFmpeg 报 `Input formats not supported`（`ffmpeg_manager.py:1070-1073`）。
- **为什么 `normalize=0`**：默认归一会把两路各砍一半音量，实测人声明显发虚（`ffmpeg_manager.py:1080-1082`）。
- **为什么 `duration=longest:dropout_transition=0`**：任一路掉线不能让整条混音停摆或突变音量。
- **标签必须用真实输入序号**：视频占输入 0，音频从 1 起（`capture.py:81-82` 传 `input_offset=1`）。`take()` 每追加一个输入就把当前序号记成 `[N:a]` 并自增（`ffmpeg_manager.py:1105-1110`）。标签指向无音频流的视频输入会让 FFmpeg 启动失败（`ffmpeg_manager.py:1091-1093`）。

各平台的音频输入拼装见 `build_audio_input()`（`ffmpeg_manager.py:1086-1156`）：

| 场景 | 参数 |
|---|---|
| Windows 麦克风 | `-f dshow -i audio=<名>`（`:1113-1114`） |
| Windows 系统声音（环回） | `-f s16le -ar <rate> -ac <ch> -i pipe:0`（`:1117-1121`） |
| Windows 系统声音（dshow 立体声混音，罕见） | `-f dshow -i audio=<名>`（`:1122-1124`） |
| macOS 麦克风 | `-f avfoundation -i :<idx>`（`:1146-1147`） |
| macOS 系统声音 | `-f avfoundation -i :<idx>`（`:1148-1150`） |
| macOS 双路 | 两个 `-f avfoundation -i :<idx>` + `amix`（`:1141-1145`，avfoundation 单输入只支持一个音频设备） |
| Linux 麦克风 | `-f pulse -i default`（`:1154-1155`） |
| 都不勾 | 返回 `[]` → 编码侧写 `-an`（`capture.py:109-110`） |

### 4.2 Windows 系统声音：WASAPI 环回与「零字节饿死」

`screencast/loopback.py`。上游 FFmpeg 到 9.0 都没有 WASAPI 输入设备（ticket #9408 仍开着），所以环回必须由 sidecar 自己采成 s16le PCM，从 stdin 灌给 ffmpeg（`loopback.py:1-18` 模块 docstring、`ffmpeg_manager.py:1118-1121`）。

```
┌── sidecar 进程 ─────────────────────────────────────────┐
│  LoopbackStream                                         │
│   pyaudiowpatch (PortAudio/WASAPI)                      │
│     frames_per_buffer=1024 (≈21ms)                      │
│        │                                                │
│        ▼  loopback-pump 线程 (_pump_loop, :169-184)      │
│   Queue(maxsize=64) ── _offer 满了丢最旧 (:186-196)       │
│        │                                                │
│        ▼  read() (:198-209)                             │
│     有数据 → 原样返回                                     │
│     无数据 → _pad() 按单调时钟补静音 (:211-222)            │
│        │                                                │
│        ▼  _feed_loopback 线程 (capture.py:219-256)       │
│     proc.stdin.write(...)                               │
└───────────────────────┬─────────────────────────────────┘
                        ▼  -f s16le -i pipe:0
                    FFmpeg 子进程
```

**「零字节饿死」问题**：环回端点在**没人出声**时不提供数据。实测记录在 `loopback.py:1-18`：Windows .68 上 FxSound 端点 2.00 秒读到 380928 字节（≈ 实时 384000），而「扬声器 (Realtek(R) Audio)」环回在没人出声时 `read()` **直接卡住**。卡住的后果是 stdin 一个字节都不写，FFmpeg 的 `pipe:0` 输入饿死——画面正常、音频轨道停滞，HLS 的交织器反过来把视频也憋住。

**修法（按单调时钟补静音）**：`_pad()`（`loopback.py:211-222`）

```python
expected = int((time.monotonic() - self._started) * self._bytes_per_sec)
owed = expected - self._delivered
if owed < self._align:
    return b""
n = min(owed, self._chunk_bytes * MAX_PAD_CHUNKS) // self._align * self._align
```

- 用**单调时钟**算「到目前为止本该交付多少字节」，欠多少补多少，不依赖设备回调的节奏；
- `MAX_PAD_CHUNKS = 4`（≈85ms，`loopback.py:40`）是单次补静音的上限：**补太长会让音频冲到视频前面，HLS 的交织器反过来把视频憋住**（`loopback.py:36-40` 的注释）；
- `read()` 先 `self._q.get(timeout=POLL_SECONDS)`（0.05 秒，`loopback.py:36`），拿不到才走 `_pad()`（`loopback.py:198-209`），所以真数据和补白之间不会打架。

契约测试：`tests/test_screencast.py:537-714`（`TestLoopbackOwnership`），其中 `:605` `test_starved_device_still_feeds_realtime_silence` 直接锁住「设备不出数据时仍按实时速率交付静音」这条行为；该测试类的 docstring 里保留了 .68 上 v2.2.22 / v2.2.23 的现场证据（0.42 秒停滞、`0xc0000005` / `ntdll.dll`）。

**跨线程关流会崩**：PortAudio 的 C 调用不可并发、`close()` 不可重入，别的线程去 close 就是踩已释放的 stream（实测 `0xc0000005`，`loopback.py:133-137`、`capture.py:349-351`）。因此**关流权归采集线程**：`_release()`（`loopback.py:224-230`）只由 pump 线程调用，`stop()` 只是把请求交给它并 `feeder.join(timeout=2)`（`capture.py:327-359`）。测试：`tests/test_screencast.py:625` `test_close_is_executed_by_the_pump_thread_only`、`:643` `test_stop_leaves_the_wedged_stream_to_the_pump`。

**环回必须在 FFmpeg 之前打开**：`capture.py:137-146`。设备被别的程序独占、或者用户在选完之后把输出切走了，都要在这一步就说清楚（错误文案「系统声音采不起来：输出设备可能已被切换或独占…」），而不是留下一个没声音的会话。

**喂料线程早退要留证据**：`_feed_loopback`（`capture.py:282-320`）在写 stdin 出异常时记异常类型、`rc = proc.poll()` 与 stderr 提示（`capture.py:305-309`）。背景是 .68 上偶发「起流 0.3 秒后」就断，没有这条日志根本查不下去。

### 4.3 「当前出声」这条标记怎么来的

Windows 上每块**渲染设备**各有一条自己的环回镜像，只有对应当前默认输出的那条才真能抓到声音；选到闲置的那块，画面正常但投出去没声音（前端提示文案 `src/locales/zh-CN.json:230`）。

判定方式是**「是不是系统默认输出端点」这个布尔标记，不是靠名字猜**：

- `loopback_devices()`（`loopback.py:55-94`）枚举时把默认端点排在第一位并打上 `default=True`。排序是必要的：机器上挂着 HDMI / 虚拟声卡时，PortAudio 列表的第一位往往是一块没在出声的喇叭。
- `resolve(name)`（`loopback.py:97-111`）按名字找回设备，找不到回落 `devices[0]`。
- 标记随设备条目一路上抛：`ffmpeg_manager.py:856-860` 把 `default` 透传进 `audio_inputs`。
- 前端渲染成后缀：`ScreenCastPanel.vue:90-98`，`hasLoopbackMirror` 为真时给 `d.default` 的条目拼上 `t('screencast.defaultOutputSuffix')`，即「（当前出声）」（`src/locales/zh-CN.json:229`）。
- 同一处也负责显示 `screencast.loopbackTip`（`ScreenCastPanel.vue:360`），提醒用户换了输出设备（拔插耳机、切蓝牙）后要关掉面板重开以刷新列表。

契约测试：`tests/test_screencast.py:701` `test_live_loopback_flagged_and_sorted_first`、`:709` `test_default_lookup_failure_keeps_the_list`。验收脚本 `tools/verify-win-screencast-tone-content.sh` 也明确要求「系统设备按 `default` 标记选，不按名字选」。

### 4.4 开录前的静音闸门

勾了麦克风却拿不到声音是最难自查的一类故障：没有录音权限时系统不报错也不弹窗（macOS 尤其如此），设备照样枚举得到，只是采回来的每个样本都是 0，画面流畅、毫无异常。所以 `start()` 在开录前**试采一秒**：

- `audio_input_silent(device, seconds=1.0)`（`ffmpeg_manager.py:913-952`）跑一次 `-t 1 -ar 48000 -ac 1 -c:a pcm_s16le -f wav -`，解析 WAV 里的 PCM 样本。返回值是三态：`True`（全静音）/ `False`（有信号）/ `None`（**测不出来**，例如读到的数据 `len(data) < 8000`）。
- 只有 `is True` 才拦（`manager.py:129-134`）；`None` 不拦——测不出来不等于没声音。`audio_input_silent()` 在 Linux 上走 `-f pulse -i <源名>`（`ffmpeg_manager.py:949` 起）。
- 拦截文案按平台给三条不同的授权路径（`manager.py:135-147`）：Linux 说「先在声音设置里确认这条输入没被静音，再看 pactl/沙箱（flatpak 启动时可能拿不到麦克风）」，macOS 说「系统设置 → 隐私与安全性 → 麦克风」，Windows 说「设置 → 隐私和安全性 → 麦克风」。v2.3.19 之前这里只有一句 macOS 文案，Linux 用户被拦下时看到的是不相干的系统设置路径。
- 另一道前置闸门是 `_missing_audio_devices()`（`manager.py:180-220`）：勾了声学设备、系统里却找不到它，直接说清楚，而不是静默降级成 `-an`（`manager.py:124-129` 的注释记录了以前静默降级的后果：用户以为在收声，实际每一帧都是哑的）。枚举本身不可用时返回 `None` 放行——「别拦住投屏」（`manager.py:218`）。Linux 这里还有一个新变化：v2.3.19 起 `_list_audio_devices()` 不再依赖 FFmpeg（`ffmpeg_manager.py:809-813`），所以「设备列得出来、缺的是 FFmpeg」这种情形不会再被误判成「没有麦克风」。

契约测试：`tests/test_screencast.py:170` `test_audio_input_silent_reads_wav_pcm`、`:948` `test_mic_without_signal_blocks_start`、`:913` `test_system_audio_without_device_rejected`。

### 4.6 Linux 系统声音：抓输出总线的 monitor 镜像（v2.3.19）

PipeWire 给**每条输出节点自带一个 `<sink>.monitor` 源**，抓它就等于抓「此刻真正出声的那条总线」——和 Windows 的 WASAPI 环回、macOS 的 Audio Tap 是同一件事，**代价是不用装任何虚拟声卡、也不用引任何 Python 依赖**：`ffmpeg -f pulse -i <sink>.monitor` 直接吃。

枚举走本机 CLI 三层拼装（`pulse.py:8-17` 的模块 docstring 记录了为什么不能只用一层）：

| 层 | 命令 | 拿什么 |
|---|---|---|
| 权威清单 | `pactl --format=json list sources` | 有哪些输入源（`pulse.py:121`） |
| 可读名字 | `pw-dump` | `node.description`——**PipeWire 在 pactl 的 JSON 里把 `description` 一律写成字符串 `"(null)"`**，不补这一层用户看到的就是 `alsa_output.usb-…analog-stereo.monitor`（`pulse.py:74-98`） |
| 「当前出声」 | `pactl info` | Default Source / Default Sink，用来打 `default` 标记（`pulse.py:55-71`） |

三条必须留住的判据：

1. **`default` 不是装饰**。每块输出各有一条 monitor，闲置那块（例：没在出声的 HDMI）采得到数据但永远是静音——和 §4.3 的 Windows 病情一模一样。所以列表把默认那条排最前（`pulse.py:146-147`），前端拼上「（当前出声）」后缀（`ScreenCastPanel.vue:113-122` + `src/locales/zh-CN.json:232`），Linux 的提示文案也另写一份（`screencast.loopbackTipLinux`，`zh-CN.json:234`）。真机对照：默认输出的 monitor 在播 660Hz 测试音时 RMS −16 dB 到 −24 dB，闲置 HDMI 的 monitor 是 −91 dB。
2. **pactl 的 stderr 是噪音不是失败**。它在 PipeWire 上会打 `Invalid ASCII character: …`（它自己的 JSON 转义不认多字节），解析只吃 stdout；`capture_output=True` 分两路收（`pulse.py:36-52`）。
3. **monitor 的 `kind` 是 `system`**。`list_input_devices()` 按名字尾缀 `.monitor` 判定并打 `monitor: True`（`pulse.py:134-144`），`_list_audio_devices()` 把它并进 `audio_inputs`，前端的「系统声音」下拉靠这个字段过滤（`src/stores/screencast.ts` 的 `systemDevices`）。缺了这条，那两个下拉就是空的——这正是用户报的「麦克风、系统声音页都不可用」。

混音与 Windows/macOS 同一条路：麦克风 + monitor 开两个 `-f pulse` 输入再 `amix`（pulse 一个输入只认一个源，`ffmpeg_manager.py:1221-1233`）；勾选了麦克风却没落到具体设备时回落 `default`，不改 v2.3.18 之前「勾麦克风=收 default」的行为（`ffmpeg_manager.py:1239-1242`）。

纯 ALSA（没有 pactl）拿不到系统声音：`_pulse_session()` 直接返回假，列表为空，前端文案 `screencast.noSystemSoundLinux` 会写清楚装 `pipewire-pulse` / `pulseaudio` 二选一即可（`zh-CN.json:231`）。

`start()`（`manager.py:82-169`）按顺序过闸门，任何一步失败都直接返回可读的 `error`：

                          + 「启动失败: {e}」                        (manager.py:158-163)

`_start()`（`manager.py:344-427`）的实际动作顺序：

1. `target=dlna` 时先校验 `device_id` 与设备在线（`manager.py:347-353`）；
2. `httpd.start()` + `register_session()`（`manager.py:355-359`）——失败即返回，不会留下半个会话；
3. 建会话独占目录并起 FFmpeg（`manager.py:361-370`）；
4. 拼 `m3u8_url`（`manager.py:372-373`）；
5. DLNA：构造 DIDL（`build_didl_item(m3u8_url, HLS_MIME, f"{device.display_name} 屏幕投屏")`，`manager.py:380-381`）→ `session.play(...)`（`manager.py:383`）。
   - `ControlUrlUnavailable` / `RendererUnresponsive` → 先 `_stop_cast` 释放电视，再原样回传异常文本（`manager.py:384-386`）；
   - 其它异常 → 同样先释放，再回「电视拒绝播放（…），可换较低分辨率/码率后重试」（`manager.py:387-391`）；
   - 成功后起 `screencast-dlna-verify` 守护线程做拉流校验（`manager.py:402-405`）。
6. 浏览器：拼 `watch_url`（`manager.py:408`）并返回宽高帧率。

FFmpeg 就绪判定：起流后最多等 8 秒，且要求 `getmtime(m3u8) >= started_at`（`capture.py:215-232`）。两种失败各有文案——「FFmpeg 提前退出（退出码 N）」+ stderr 提示，或「HLS 输出超时未生成（屏幕捕获失败，可能是窗口不存在/权限未授予）」+ 提示。

`stderr` 提示由 `_stderr_hint()`（`capture.py:337-352`）按标记串匹配给出：`not divisible`、`Failed to`、`Invalid argument`、`Permission denied`、`No such file`、`Cannot open`、`Device or resource busy`；保留尾部 40 行（`capture.py:25` `_STDERR_TAIL`）。`_drain_stderr`（`capture.py:326-336`）必须一直读——**不读满 64KB 管道会把 FFmpeg 卡死**。

### 5.3 停止

`stop()`（`manager.py:242-246`，实际动作在 `_stop_requested()` `manager.py:247-274`）**幂等**：没在跑也走一遍 `_teardown()` 并返回 `{"ok": True, "already_stopped": True}`（`manager.py:248-251`）。测试 `tests/test_screencast.py:982` `test_stop_is_idempotent`。

DLNA 通道下停止分两步：先 `handler._stop_cast(...)` 摘电视（`manager.py:258-267`），再 `_teardown()` 拆本机。`_stop_cast`（`commands.py:522-560`）的 docstring 明确了顺序理由：**先摘会话再发 SOAP Stop**，且 `control_failed` 必须一路传到前端。`_stop_cast` 抛异常时，把当前设备记成失败并带上异常文本（`manager.py:264-267`）——不能因为电视失联就让用户停不掉本机。

返回值 `{ok, control_failed, reasons}`（`manager.py:273`）；`manager.py:271-272` 的注释写清了语义：分片目录已删、HTTP 服务已停，电视顶多把缓冲播完；但 Stop 没送达时必须让前端知道，否则用户以为「停止」＝电视已经回到待机。

契约测试：`hancast-backend/tests/test_stop_cast_delivery.py`（159 行）锁住停止链路的三条契约；端到端脚本 `tools/verify-dlna-stop-chain.py` 要求**渲染器自报** `PLAYING → STOPPED`（只看本机状态会骗人）。

### 5.4 异常提前退出

FFmpeg 进程死掉或卡流由 `_watch` 线程发现（`capture.py:353-387`）：

- 进程退出 → 「屏幕捕获进程已退出（退出码 N）」；
- `m3u8` 的 mtime 超过 15 秒没动 → 「屏幕捕获已停止输出（画面卡住）」。

回调进 `manager._on_capture_error()`（`manager.py:471-498`），顺序很关键：

```python
self._teardown()          # 先拆
self._state["error"] = msg  # 再写错误
```

因为 `_teardown` 里的 `_reset` 会清空 `error`，**先写后拆的话前端拿不到失败原因，只剩一个「不知道为什么不投了」的黑屏**（`manager.py:491-496`）。之后如果通道是 dlna，还要主动 `_stop_cast` 释放电视，否则电视继续拉一条死流、前端也起不了下一次（`manager.py:493-494`）。测试：`tests/test_screencast.py:1014` `test_capture_error_frees_dlna_channel`。

### 5.5 端口释放与会话注销

`_teardown()`（`manager.py:499-528`）的契约写在 docstring 里：**幂等，且任何一步失败都不能挡住其余步骤**——这一步冒异常的话，用户点「停止投屏」就永远没有回应（注释直接记了曾真的发生过：会话注销抛 `TypeError` 冒到命令循环）。步骤：

```
capture.stop()          → 异常只记 warning                     (manager.py:506-511)
httpd.unregister_session(sid) → 异常只记 warning               (manager.py:514-518)
rmtree(hls/<sid>)       → ignore_errors=True                   (manager.py:519)
httpd.stop()            → 没有会话就把服务停下来，下次 start
                          才能拿回固定端口 8765                  (manager.py:520-524)
_release_tap()          → 仅 macOS，销毁自建 Audio Tap 设备      (manager.py:525, 529-542)
_reset()                → 清空状态                              (manager.py:526, 543-556)
```

两个曾经真实踩过的坑：

1. `unregister_session` 里 `sessions` 是 **set**，`pop(id, None)` 会抛 `TypeError` → 表现是「点了停止没反应」；改用 `discard`（`httpd.py:168-175`，注释在 `:170-171`）。
2. `httpd.stop()` 必须停掉 `run_forever`，否则线程存活、下次 `start()` 被 `is_alive()` 短路，端口拿不回来（`httpd.py:130-154`，注释在 `:143-144`）。

进程退出兜底：`commands.py:288-306` 的 `cleanup()` **先**调 `screencast.cleanup()`；`manager.cleanup()`（`manager.py:331-343`）依次 `stop()` → `httpd.stop()` → `_release_tap()`，其中最后一步是兜底：没有会话时 `stop()` 会提前返回、走不到 `_teardown`，环回/聚合设备就漏释放了（`manager.py:341-342`）。

### 5.6 状态事件如何到前端

统一出口是 `_emit()`（`manager.py:557-563`）：`protocol_io.emit_event("screen_cast_state_changed", self.status())`，走 Sidecar ↔ 壳层的 JSON 行协议（stdout）。`_emit` 自己吞异常，只记 warning——状态推送失败不该把业务线程带崩。

触发点：启动成功（`manager.py:204`）、停止（`manager.py:270`；按设备停 `manager.py:287`、会话被媒体投屏接管时 `manager.py:301`）、拉流校验出结论（`manager.py:446`、`:463`）、观众数变化（`manager.py:465-470`，由 httpd 事件循环线程回调）、采集异常（`manager.py:497`）。

`status()`（`manager.py:313-323`）在快照之上补三样：

- `viewers`：**只有 `target == "browser"` 才实时刷新**（`manager.py:316-317`）；
- `pull`：拉流证据 `{pulls, misses, clients, last}`（`manager.py:318-321`）；
- `ffmpeg`：`ffmpeg.check()` 结果（`manager.py:322`）。

前端监听在 `src/stores/screencast.ts:285-300`；`ScreenCastPanel.vue:406-426` 渲染「投屏中」徽标（`:407-411`，观众数在 `:411`）与邀请链接（`:414-421`），`:429-430` 在停止态仍展示 `lastError`，`:434` 挂 `StopWarningBanner`。

### 5.7 `close()` 只等 0.5 秒这条修复的来龙去脉

提交 `73a8345`，改动只有一行：`loopback.py:241` 的 `self._pump.join(timeout=1.0)` → `join(timeout=0.5)`。

推理链条（提交信息与 `loopback.py:224-243` 的注释一致）：

1. 环回正常交付时，采集线程在**一个 chunk（≈21ms）内**就从 `read()` 返回；
2. 于是 `join(1.0)` 唯一会真等满的场景，恰恰是「端点没数据、`read()` 一直阻塞」——也就是 §4.2 里刚修好的那条饿死路径；
3. 结果：设备越安静，每次点「停止投屏」都要白等满一秒；
4. 把超时压到 0.5 秒，正常路径照样瞬间返回，病态路径的等待减半。注释同步到新架构：**关闭权在采集线程，不在喂料线程**（跨线程 close 会踩已释放的 stream，实测 `0xc0000005`，见 §4.2）。

这条修复与前一条（`c97ff52` 按单调时钟补静音）是同一个现场的连续两步：先让安静端点不再饿死管线，再让「等一个安静端点」不再拖慢停止。

### 5.8 FFmpeg 依赖：检测已有，缺失时按需下载（v2.3.11）

**历史一句**：FFmpeg 曾经随包——`bundle.resources` 里挂 `ffmpeg/*`，CI 从 `eugeneware/ffmpeg-static` 的 `b6.1.1` 下静态单文件、Windows 改名 `ffmpeg.exe`。v2.3.11 起全部删除：它是一个用户机器上普遍已装、且体积按平台各异（几十 MB 起）的外部依赖，随包只让安装包变大，换来的还是用户没法自己升级的那一份。现在改为**检测本机已装的 FFmpeg，确实没有时让用户自选**（自己装 / 让程序下载）。

检测顺序（`ffmpeg_deps.status()`，`utils/ffmpeg_deps.py:189-252`；`ffmpeg_manager.check()` 只是把 `_configured()` 的返回值递进去，`ffmpeg_manager.py:518-530`）：

| 层 | 来源 | 判据 |
|---|---|---|
| ① 手动指定 | 设置/弹窗里填的路径（`screencast.ffmpeg_path`） | 路径本身 `-version` 跑不通就**降级继续找**并打 warning（`ffmpeg_manager.py:513-516`），不让一个失效配置把功能锁死 |
| ② 系统已装 | `search_dirs()` = `PATH` + 平台常见目录（`ffmpeg_deps.py:104-117`）；Windows 还要往 winget 包目录里下钻一层 `bin/`（`_walk_dirs()`，`:120-139`） | 逐个候选跑 `-version`（`read_version()`，`:142-162`，30 秒结果缓存 `:36`） |
| ③ 本程序下载的那份 | `<SETTING_DIR>/bin/`（`managed_dir()`，`:51-53`） | 同上；命中则 `source="downloaded"` |

「文件在」不等于「能用」——每一层都必须真跑出 `-version` 才算命中，这是 ②③ 顺序里最容易被忽略的一条：装坏了的 exe、平台不匹配的构建，都会被跳过并继续往下找。

手动指定那条还有个配套行为：指了 ffmpeg 而系统里找不到 ffprobe 时，会去**同目录**取那份 ffprobe 当搭档（`ffmpeg_deps.py:219-225`），因为 gyan/BtbN 这类包都是两个二进制同目录分发。已知边界：`set_ffmpeg_path` 只能设不能清（§5.1），但失效路径会在 `_configured()` 里被降级掉（`ffmpeg_manager.py:513-516`），所以不会被一个旧配置永久锁住。

必需/可选是两条清单（`:43-44`）：`REQUIRED=("ffmpeg",)`、`OPTIONAL=("ffprobe",)`。ffprobe 之所以只是可选——macOS 那条 ffmpeg-static 产物**只有一个 ffmpeg 二进制**，缺 ffprobe 不该拦住屏幕投屏，它只影响 `media/parser.py` 的时长探测（那里用 `probe_path() or "ffprobe"`）。

`status()` 的返回同时是弹窗的数据源：`ok / path / version / source / items[] / missing[] / optional_missing[] / managed_dir / platform / arch / install_commands[] / download / error`。`install_commands()`（`:178-188`）按平台给可复制的命令：Windows `winget install --id Gyan.FFmpeg -e` / `choco install ffmpeg -y`，macOS `brew install ffmpeg` / `port install ffmpeg`，Linux `apt install ffmpeg` / `dnf install ffmpeg`。

下载走后台任务表 + 轮询，理由和 §2 的解析异步化同一个：归档几百 MB，而 Rust 侧 `COMMAND_TIMEOUT = 60s`（`src-tauri/src/sidecar.rs:18`）等不起。

- `start_download()`（`:448-469`）拿锁起线程**立刻返回**任务句柄；
- `download_status()`（`:470-474`）给前端轮询，阶段 ∈ `connecting / downloading / extracting / verifying / done / failed`；`_download_archive()`（`:355-397`）每 0.4 秒汇报 `received/total/percent/speed/elapsed`；
- 源按 `(sys_platform, machine)` 选（`_SOURCES`，`:264-296`）：win32/amd64 → gyan.dev `ffmpeg-release-essentials.zip`，win32/arm64 → BtbN，darwin arm64 与 x86_64 → ffmpeg-static `b6.1.1` 的 `.gz`，linux x86_64/aarch64 → johnvansickle `tar.xz`；
- 体积闸门 `MAX_ARCHIVE_BYTES = 512MB`（`:32`）拦 Content-Length 撒谎的响应；解压只按 **basename** 匹配想要的名（`_wanted_names()`/`_extract()`，`:398-447`），不照归档里的路径落盘，且落盘 `chmod 0o755`；
- 收尾必须 `verifying` 再跑一次 `-version`，跑不起来报的是「下载并解包成功，但这个 ffmpeg 跑不起来……多半是当前平台用不了这份构建」（`_run_download()`，`:480-520`），归档无论如何用完即删。

失败时给用户看的是**底层异常原文**：`format_error()`（`:308-324`）沿 `__cause__`/`__context__` 逐层收集、去重、用 ` ← ` 连接（最多 3 段），所以弹窗里出现的是 `连接下载源失败（https://…）— ConnectionError: …` 这种能据以判断的句子，而不是一句「下载失败」。

前端两个入口（第 20 个组件 `src/components/FfmpegDepsModal.vue`）：

1. 面板底部「打开依赖」按钮——`ScreenCastPanel.vue:198-201`，只在 `!sc.ffmpegOk` 的错误条里出现；旧的「手填 ffmpeg 路径」输入框已由弹窗接管（手填仍在，位置在弹窗里，`FfmpegDepsModal.vue:74-` 的 `onSetManual` 走 `set_ffmpeg_path`）。
2. 打开面板时自动提示一次——`ScreenCastPanel.vue:43-50`：`list_screen_sources` 回来带 `ffmpeg.ok=false` 就自动弹，`depsPrompted` 保证每次开面板只弹一次，关掉不再追着弹。

弹窗四个动作分别落在：`打开安装目录` → Rust `open_ffmpeg_dir`（前端**不传路径**，由 Rust 读 Sidecar 报告里的 `managed_dir` 并 `create_dir_all`，避免前端拿到一个不存在或不属于本程序的目录）；`重新检测` → `ffmpeg_status(refresh=true)`；复制安装命令 → `install_commands`；`下载并继续` → `ffmpeg_download_start` 后 store 每 1s 轮询 `ffmpeg_download_status`轮询本体 `pollDownload()`（`src/stores/screencast.ts:109-124`），起表在 `startFfmpegDownload()` 的 `setInterval(pollDownload, 1000)`（`:134`），面板重开时由 `resumeDownloadPolling()` 续表（`:155-170`、`:161`），`done` 时立刻带 refresh 重报一次（`:116`），`onUnmounted` 停表（`:310-314`）。

**验收结果（v2.3.11，产物层 + Windows 真机）**——三层检测与下载分支都在**装好的产物**上命中过，两个脚本是判据来源：

- `tools/accept-macos-artifact.sh 2.3.11` → ALL PASS。本轮加进去的判据是：整个 `.app` 里 `ffmpeg`/`ffprobe`/`ffmpeg.exe` **零命中**（v2.3.10 的产物里有两份）、`ffmpeg_status`/`ffmpeg_download_start`/`ffmpeg_download_status` 注册在打包的 `commands.py` 里、`ffmpeg_manager.py` 里 `_get_base_path`/`_find_in_program_dir` 两个函数名已不存在、产物内 29 个 sidecar 源文件逐个与 `git show v2.3.11:…` 比 sha256（含新增的 `utils/ffmpeg_deps.py`；清单口径 `tools/accept-macos-artifact.sh:35-44`，整轮 88 条 PASS）。同一脚本还用一次性 `HOME` + `PATH=/usr/bin:/bin` 起**打包 sidecar** 跑完检测链：② 命中 `/opt/homebrew/bin/ffmpeg`（9.0.2，`source=system`）→ 真下载 `b6.1.1` 的 `ffmpeg-darwin-arm64.gz`，阶段 `downloading → extracting → done` → 落盘那份 `-version` 跑得出（6.0）→ 复检按「系统已装 > 自下载」归位 `system` → `set_ffmpeg_path` 之后 `manual` 且 `ok=True` 不破。
- `tools/verify-ffmpeg-detect.ps1`（真机探针，驱动 `.68` 上装好的 `hancast-sidecar.exe`；三种环境都跑在一次性沙盒里，不碰用户的 winget 安装与真实设置）：`-TempAppData` → ② 命中 `…\Microsoft\WinGet\Links\ffmpeg.exe`（8.1.2-full_build，`source=system`，ffprobe 同目录一起认）；`-TempAppData -BarePath`（PATH 削到只剩 `C:\Windows`）→ 弹窗数据源本体 `ok=False` / `missing=FFmpeg` / `optional=FFprobe` / 两条 `install_commands` / `download.available=True kind=zip` + 错误原文；再带 `-SeedDownloaded <一份真 ffmpeg>` → ③ `source=downloaded`。**`.68` 单独用 `-TempAppData` 就已经命中 system**，而 `_extra_dirs()` 读的 `LOCALAPPDATA` 那时被指进沙盒、那条通道是废的——所以命中来自进程 PATH，这台机器的 PATH 本来就带着 `Links`。要造「本机没有 ffmpeg」**必须同时削 PATH**，只重定向目录不够。（这不推翻 `_extra_dirs()`：winget 的 `Packages/<带版本号>` 目录从来不在 PATH 里，`Links` 也常常要重开终端才刷新，探针是 ssh 子进程、并不等于 GUI 冷启动那份 PATH。）

两个口子按原样记着，别当成已验：① Windows 那条 gyan zip 只验到「开始流 + 进度真实」（600 秒走了 11.0 MB / 114.8 MB，~18 KB/s），**没跑到 `done`**；zip 的解包与 `-version` 收口只有 `tests/test_ffmpeg_download_e2e.py` 的本地 HTTP 源证据。② 从 ≤2.3.10 升级的机器上 `screencast.ffmpeg_path` 常仍指向**旧的随包目录**，而 NSIS 卸载不清理残留文件——`.68` 实测就停在这里：①层优先命中 6.1.1 那份旧 ffmpeg，系统新装的 8.1.2 反而不参与，且不会自动纠正（只在文件消失后降级）。

## 7. 平台限制与已知坑

这一节列的是**做不到**或**容易做错**的事，每条都附证据。

### 7.1 FFmpeg 没有 WASAPI 输入，PortAudio 环回是硬依赖

- 事实：上游 FFmpeg **到 9.0 都没有 WASAPI 输入设备**，ticket #9408 仍开着。证据：`screencast/loopback.py:1-18` 模块 docstring；`hancast-backend/pyproject.toml:23-26`（注释「FFmpeg 没有 WASAPI 输入（ticket #9408 未合并）」+ 依赖 `pyaudiowpatch>=0.2.12.9; sys_platform == 'win32'`）。
- 后果：Windows 系统声音**必须**由 sidecar 自己用 PortAudio 采成 s16le PCM，再从 `-f s16le -i pipe:0` 灌进 ffmpeg（`ffmpeg_manager.py:1118-1121`）。这条路径带来 §4.2 的全部复杂度（补静音、跨线程关流、喂料线程诊断），也带来一个额外依赖 `pyaudiowpatch`（仅 win32）。
- 不要用 dshow 的「立体声混音」替代：绝大多数机器的驱动根本没注册这个设备（`ffmpeg_manager.py:851-853`）。代码里保留了 dshow 分支（`ffmpeg_manager.py:1122-1124`）只是给极少数有这个设备的机器兜底。

### 7.2 有些 FFmpeg 能力任何版本都没有，只能自己做原生辅助

三类，都不是「升级 ffmpeg 就能解决」：

1. **macOS 没有窗口输入**。`ffmpeg_manager.py:233-235` 的注释明确：FFmpeg avfoundation **从 6.1 到 master 都没有窗口输入**。所以 macOS 的「指定窗口」只能实现为「抓它所在那块屏 + `crop`」（`ffmpeg_manager.py:1109-1112`）。这带来两个用户可见的语义差别：
   - 别的窗口压在目标窗口上面时，投出去的是**压着它的那个**（前端提示 `zh-CN.json:226` 已明说）；
   - 窗口移动/关闭/最小化后必须重新选择，`start()` 前会强制重算几何（`manager.py:109-113`、`ffmpeg_manager.py:778-791`）。
2. **macOS 系统声音不是输入设备**。avfoundation 只认输入设备，系统声音是输出（`macos_tap.py:1-13`）。HanCast 的做法是用 ctypes 直接调 CoreAudio 造一个聚合输入设备（`macos_tap.py:328-370`），**不引新依赖**（不用 pyobjc、不用装 BlackHole）。这就是「原生辅助」的形态：能力在系统 API 里，ffmpeg 拿不到，只能自己在进程外造一个 ffmpeg 能看见的设备。
3. **Linux/Wayland 抓屏：ffmpeg 任何版本都没有这个输入**（v2.3.19）。`ffmpeg -hide_banner -demuxers` 在 n9.0.2 里只有 `x11grab` / `kmsgrab` / `fbdev`，没有 wayland，pipewire 那条（`-f pipewire`）官方构建也没编。而 `x11grab` 在 Hyprland/sway 上抓的是空的 root window——**投屏启动成功、帧率正常、每帧纯黑、日志干净**，这是它比「报错」更贵的地方（判据与量化见 §3.4）。所以走第三个原生 helper：`linux-capture/`（Rust + `zwlr_screencopy_manager_v1`，grim/wf-recorder 同一套协议）把 BGRA 帧写进 stdout，ffmpeg 用 `-f rawvideo -i pipe:0` 接上，后面整条 HLS 管线与 Windows/macOS 完全共用。kmsgrab 不考虑：它要 DRM master，与合成器抢独占，桌面环境下起不来。

顺带一条同类限制：**Windows 环回设备是每块渲染设备一条镜像**，只有默认输出那条真能抓到声音（§4.3），ffmpeg 侧没有任何机制帮你选对。**Linux 的 monitor 源一模一样**（§4.6）。

### 7.3 adhoc 签名与 macOS TCC

- 事实：macOS 15+ 把「本地网络」做成 TCC 权限，**按代码身份判定**。CI 不签名时主程序只有 Rust 链接器写的 adhoc 签名（`Identifier=HanCast-<16位hex>`、`flags=0x20002(adhoc,linker-signed)`），**同一个 bundle id 每次构建换一个身份**，NetworkAgent 认不出它就静默拒绝组播（`sendto 239.255.255.250` → `Errno 65`），连弹窗都没有、TCC.db 里也不留记录。证据：`src-tauri/Info.plist:5-20` 的注释块、`.github/workflows/build.yml:421-428` 的注释块。
- A/B 实测（同一台机器、同一份字节，2026-10-13）：产物原样 → 心跳日志 `通道 broadcast`；`codesign --force --deep -s -` 重签 → `通道 multicast`（24 条）+ 入站 200。证据：`.github/workflows/build.yml:426-427`。
- 因此 CI 在**打 dmg 之前**必须重签，并断言签名 Identifier == `com.han.hancast`、且不带 `linker-signed` 标志：`.github/workflows/build.yml:429-450`（签名 `:439`、校验 `:440`、Identifier 断言 `:441-445`、linker-signed 断言 `:446-449`）。签完再动 bundle 会让签名失效，所以顺序不能换（`.github/workflows/build.yml:428`）。dmg 也不复用 `tauri build --bundles dmg`，因为它会重跑 cargo 重建 `.app`，把上一步的修复覆盖掉（`.github/workflows/build.yml:452-456`）。
- 声明本身也是双份的，缺一不可：只写 `NSLocalNetworkUsageDescription` → 单播/入站通、组播仍 `Errno 65`；再补 `NSBonjourServices=["_upnp._tcp"]` 才有 `通道 multicast`（`src-tauri/Info.plist:9-13`）。实际出货的三个 key：`NSLocalNetworkUsageDescription`（`:21-22`）、`NSBonjourServices`（`:23-26`）、`NSMicrophoneUsageDescription`（`:35-36`）。
- 引入这条的提交是 `bd847da`（v2.2.13 停止链路如实回报 + NSBonjourServices）；`src-tauri/Info.plist:14` 的注释记了「2.2.13 就是这么翻车的」——光有 plist 不够。

⚠️ 未验证：**「每次发版都要重新授予『屏幕录制』和『麦克风』」这一说法在本仓找不到直接证据。** 仓内的 adhoc/代码身份证据（`src-tauri/Info.plist:14-19`、`.github/workflows/build.yml:421-428`）覆盖的是**本地网络**权限与签名 Identifier 不稳定，A/B 实测记录的也是组播通道，不是屏幕录制/麦克风的 TCC 重新弹窗。按同一套「TCC 按代码身份判定」的机制推断，屏幕录制/麦克风授权理论上会受同样影响，但仓库里没有对应的实测记录或断言，所以不下结论。

### 7.4 麦克风权限：声明齐全也可能恒静音

`src-tauri/Info.plist:27-34` 把这条坑写得很完整：

- 缺 `NSMicrophoneUsageDescription` 的后果**不是「弹窗询问被拒」，而是根本不弹**：TCC 直接判「拒绝且不再提示」；
- ffmpeg 作为子进程从 App 继承这条授权，抓到的音频**恒为静音**，而设备照样枚举得到（枚举不过是以 "Microphone" 开头的字符串），于是用户看到的是「选了麦克风但投出去没声音」；
- 声明只是前提：**TCC 在第一次真正访问音频时才写库，而 ffmpeg 自己不会触发弹窗**。

所以前端在勾选麦克风时先用 webview 走一次 `getUserMedia({audio:true})` 把授权拿到，再让 ffmpeg 接手：`ScreenCastPanel.vue:151-166`（`ensureMicAccess`）、`:146` 的注释、`:165` 的 watch、`:168` 的 onStart 前置；被拒时 `:343` 给「重试授权」按钮，文案 `screencast.micDenied`（`zh-CN.json:233`）。后端还有 §4.4 的静音闸门作为最后一道防线。

⚠️ 未验证：**出货的 `Info.plist` 里没有 `NSAudioCaptureUsageDescription`**（全文只有 §7.3 列的三个 key，`src-tauri/Info.plist:21-36`），而 `tools/run-macos-tap-probe.sh:5-8` 明确要求探针跑在一个带 `NSAudioCaptureUsageDescription` 的 `.app` bundle 里，并记录「裸 python 跑的话 `CreateProcessTap` 返回 noErr 但零条流」。两者是否意味着**出货 App 的 Audio Tap 也需要这条声明**、还是「麦克风声明已足够覆盖 Audio Tap」，仓库里没有结论性证据（`src-tauri/Info.plist:27` 只写了一句「ScreenCaptureKit 采系统声音同样要求这条声明」，指的仍是 `NSMicrophoneUsageDescription`，而 HanCast 用的是 Audio Tap 不是 ScreenCaptureKit）。

### 7.5 `-vf` 必须排在所有 `-i` 之后

- 症状：选了麦克风或系统声音就投不起来，ffmpeg 报 `Option vf cannot be applied to input url audio=…` 并 EINVAL 退出。
- 原因：ffmpeg 把 `-i` **之前**的选项判给「下一个输入」，夹在中间的 `-vf` 会落到麦克风输入上。
- 证据：`ffmpeg_manager.py:1000-1003`（docstring，含「2026-10-14 .68 实据」）、`capture.py:85-88`（拼接处的注释与实现）。
- 修复提交：`68bbb29`（v2.2.23）。
- 回归防线：`tests/test_screencast.py:422` `test_video_filter_sits_after_all_inputs`；`tools/verify-screencast-audio-order.cmd` / `.ps1`（旧实现必须 FAIL）；`tools/verify-win-screencast-audio-live.cmd`（在已发布产物上断言看不到这条错误串）。

同类的「选项归属」坑还有 gdigrab 的 `-framerate`：它是**输入选项**，必须排在 `-i` 前面，不给的话 gdigrab 默认 1fps，窗口投屏变成幻灯片（`ffmpeg_manager.py:1019-1021`）。

### 7.6 分片目录必须会话独占

复用同一目录会让上一轮的 `live.m3u8` 残留，电视拉到的是已被删除分片的死流（`capture.py:57-58`）。两处防护：`start_hls` 开头整体 `rmtree` 再 `makedirs`（`capture.py:109-111`，测试 `tests/test_screencast.py:510` `test_old_session_dir_is_wiped`）；`_handle_hls` 先查会话是否在册，不在册直接 404 而不是「目录存在就给」（`httpd.py:282-284`）。

### 7.7 观看页响应不能把 charset 写进 content_type

aiohttp 禁止 `content_type` 里带参数，charset 要用 `charset=` 单独传；写在一起会让这两个错误分支在**真正被触发时**抛 `ValueError` 变成 500（`httpd.py:239-247`）。测试类 `tests/test_screencast.py:778-837`（`TestWatchPageResponses`）的 docstring 直接写了「这两条错误分支曾经因为 content_type 带 charset 直接 500」，覆盖 `:788` 停止后观看页 404 而非 500、`:794` 未注册会话的 HLS 404、`:807` 已注册会话正常服务。

### 7.8 观众数文案与实现不一致

前端邀请提示写「最多支持 20 人同时观看」（`src/locales/zh-CN.json:250`），而后端 `viewers` 的实现上限是 **64** 个独立客户端（`httpd.py:198`、`:205`），且 `viewers()` 统计的是 `viewer_window_seconds`（默认 15 秒）窗口内拉过播放列表的客户端数（`httpd.py:186-193`），并非并发连接数。**没有代码强制 20 这个上限。** 这句话应理解为产品口径而非技术限制。

### 7.9 `viewers` 对 DLNA 通道不刷新

`status()` 只在 `target == "browser"` 时才实时取 `viewers`（`manager.py:316-317`）。DLNA 通道下 `viewers` 恒为 0（`manager.py:74` 初始化），即便电视确实一直在拉流——拉流证据在 `status()["pull"]` 里，不在 `viewers` 里。排查电视黑屏时看 `pull`，不要看 `viewers`。

### 7.10 采集与分发的固有延迟

延迟下限就是分片粒度（`httpd.py:1-12`）：浏览器 1 秒分片端到端约 1–3 秒，电视 2 秒分片约 3–6 秒。想再低只能减小分片，代价是请求变密、慢客户端 `misses` 上涨（`manager.py:440-447`）。`tools/verify-watch-page-live.mjs` 用真实 Chromium + CDP 量的是**实际画面运动与延迟**，不是接口返回值——`status` 说 running 只代表进程还在（`tools/verify-win-screencast-dwell.sh` 的立项理由同样是这条）。

### 7.11 其它已知边界

- **FFmpeg 依赖发现顺序**：手动指定 → 系统已装（`PATH` + 平台常见目录）→ 本程序下载到 `<SETTING_DIR>/bin/`（`utils/ffmpeg_deps.py:189-252`，`check()` 在 `ffmpeg_manager.py:518-530`，`set_path()` 在 `:537`）。自 v2.3.11 起**不再随包**，曾经夹在中间的「随包 `ffmpeg/` 目录」那一层连同 `_get_base_path()` / `_find_in_program_dir()` 一起删了。找不到时前端弹「需要下载运行依赖」（`FfmpegDepsModal.vue`，见 §5.8），手填路径的入口也在那里面。
- **`_run_utf8`**：Windows 上 ffmpeg 子进程输出可能是 cp936，直接 decode 会得到空枚举（`ffmpeg_manager.py:39-49`）。所有枚举都必须走它。
- **sidecar 的 stdin 是协议管道**：`_spawn` 默认把子进程 stdin 设为 `DEVNULL`，只有喂环回时才开管道（`capture.py:205-217`，注释在 `:210-212`：sidecar 的 stdin 正是与 Tauri 之间的 JSON 行协议管道）。误把 ffmpeg 接到 sidecar 自己的 stdin 上会直接破坏协议。
- **`discovery.guard_mx` 是死参数**：登记在 `params.py:119-123`（默认 1，范围 1–8 秒），但全仓只有这一处出现，没有任何读取点。Device Guard 自己用的是模块常量 `SSDP_MX = 1`（`security/guard.py:37`）。改这个参数不会有任何效果。

### 7.12 rawvideo 的选项名是 `-pixel_format`，不是 `-pix_fmt`

Wayland 那条路的输入是 `-f rawvideo -pixel_format bgra -video_size WxH -i pipe:0`（`ffmpeg_manager.py:1113-1121`）。`-pix_fmt` 是**编码器/滤镜**的说法，写在 rawvideo 输入前面时 ffmpeg 只当未知选项丢掉，然后按默认 `yuv420p` 去解释那串 BGRA 字节——结果是满屏斜纹雪花，而且**不报任何错**。回归防线：`tests/test_screencast_wayland.py::TestWaylandVideoInput::test_uses_pixel_format_not_pix_fmt`（断言参数串里根本不出现 `-pix_fmt`）。

同一条路上另一半的尺寸陷阱：`-video_size` **必须来自 helper 的首帧 `HDR`**，不能来自 `list` 报的 wl_output mode（`wlgrab.py:248-254`）。缩放屏（scale=2）上 screencopy 的缓冲区是逻辑尺寸的整数倍，`-video_size` 差一个字节整条流就整体读歪，症状与上面那条一样是雪花而不是报错。

### 7.13 Wayland 没有「所有显示器的并集」这一项

screencopy 的抓取单位是**一块 output**（`zwlr_screencopy_manager_v1` 一次 `capture_output` 只对一块屏），不存在 Windows/macOS 那个「把两块屏拼成一张 4000×2571 大图再抓」的东西。所以：

- 「整个屏幕」在 Wayland 下**语义就是主显示器**，标题必须写清楚（`wlgrab.py:224-232` 产出「整个屏幕（Wayland 只能整块整块地投，这里投主显示器 DP-2）」）；
- 多屏机器上还得更显式地列出 `wl:DP-2` / `wl:DP-3` 让用户直接点（`wlgrab.py:194-221`），前端提示文案走 `screencast.screenTipWayland`（`zh-CN.json:222`）；
- 主屏认「坐标原点那块」（Hyprland 把主屏摆在 0,0），认不出来就退化成第一块（`wlgrab.py:186-191`）——不能返回「没有主屏」，否则列表里没有 `primary`，前端的缺省选择逻辑（`ScreenCastPanel.vue:136-140`）会退回 `desktop` 而和用户看到的顺序不一致。

### 7.14 随包二进制：存在性 ≠ 可运行
