## 1. 目标场景与两个出口

「屏幕投屏」把本机屏幕（或某个窗口所在的屏幕区域）编码成 **HLS 直播流**，再由一个内建 HTTP 服务分发出去。两个出口共用**同一份**编码产物，只在分片粒度和消费方上有差别（`screencast/manager.py:12-14`）。

| 出口 | target 值 | 消费方 | 默认分片 | 交付方式 |
|---|---|---|---|---|
| DLNA 通道 | `dlna` | 电视 / 大屏渲染器 | 2 秒（`params.py:43`） | SOAP `SetAVTransportURI` + `Play` 把 m3u8 URL 交给电视，电视自己来拉 |
| 浏览器通道 | `browser` | 手机 / 任意浏览器 | 1 秒（`params.py:37`） | 给用户一条 `/r/<session_id>` 观看链接，页面内 hls.js 播放 |

选择「1 秒 vs 2 秒」的原因：浏览器可以承受更激进的切片，电视端分片越小、请求越密，老渲染器容易跟不上（`screencast/httpd.py:1-12` 的延迟下限说明：浏览器 1 秒分片端到端约 1–3 秒，电视 2 秒分片约 3–6 秒）。

### 1.1 DLNA 通道链路

```
┌──────────────────────── Sidecar (Python) ────────────────────────┐
│                                                                  │
│  采集源(屏幕/窗口) ──► FFmpeg 子进程 ──► hls/<session_id>/         │
│       gdigrab            libx264           live.m3u8             │
│       avfoundation       + aac             seg000.ts …           │
│       x11grab                                                    │
│                              │                                   │
│  WASAPI 环回 / Audio Tap ────┘ (系统声音以 PCM 从 stdin 灌入)      │
│                                                                  │
│  ScreenCastHttpd :8765 ── GET /hls/<sid>/live.m3u8 ──────────────┼──► 电视
│      (aiohttp, 独立线程)   GET /hls/<sid>/segNNN.ts              │    (渲染器)
│                                                                  │
│  DeviceCastSession.play(m3u8, "application/vnd.apple.mpegurl")   │
│      └── SOAP SetAVTransportURI + Play ─────────────────────────►│──► 电视
└──────────────────────────────────────────────────────────────────┘
        │ screen_cast_state_changed (JSON 行协议)
        ▼
   壳层 (Rust/Tauri) ──► 前端 ScreenCastPanel.vue
```

关键代码位：`screencast/manager.py:290-299`（拼 m3u8 URL、构造 DIDL、调 `session.play`）；推流失败的两类异常分别处置在 `manager.py:300-315`。

### 1.2 浏览器通道链路

```
┌──────────── Sidecar ────────────┐          ┌──── 观众设备 ────┐
│ FFmpeg ──► hls/<sid>/live.m3u8  │          │  浏览器          │
│                 segNNN.ts       │          │   │              │
│ ScreenCastHttpd :8765           │          │   ▼              │
│   GET /r/<sid>      ────────────┼──────────┼─► index.html     │
│       (注入 __SESSION_ID__ /    │          │   (www/)         │
│        __PLAYER_CONFIG__)       │          │   │              │
│   GET /static/hls.min.js ───────┼──────────┼─► hls.js         │
│   GET /hls/<sid>/live.m3u8 ─────┼──────────┼─► 同源相对路径拉流 │
│   GET /hls/<sid>/segNNN.ts ─────┼──────────┼─►                │
└─────────────────────────────────┘          └──────────────────┘
```

观看页模板：`screencast/www/index.html`。第 61-65 行把后端注入的 `__SESSION_ID__` 拼成**同源相对路径** `/hls/<sid>/live.m3u8`；第 102-132 行是 hls.js 分支（含重试上限与「投屏已结束」的 404 处理）；第 89-100 行是 Safari 原生 HLS 分支；第 134-136 行是两条路都不可用时的兜底文案。

`watch_url` 的构造在 `manager.py:328`，形如 `http://<本机 IP>:<port>/r/<session_id>`。本机 IP 由 `commands.py:38-51` 的 `_get_local_ip()` 决定：优先用户配置的 `network_interface`，否则 UDP 连 `8.8.8.8` 取出口地址，全失败回落 `127.0.0.1`。

### 1.3 会话隔离

每次 `start()` 生成一个 6 位十六进制会话号（`manager.py:157`：`secrets.token_hex(3)`），分片目录是 `<临时目录>/hancast_screencast_hls/<session_id>/`（`manager.py:46-48`、`manager.py:279`）。**URL 随会话变化**是刻意的：复用同一目录会让上一轮的 `live.m3u8` 残留，电视拉到的是已被删除分片的死播放列表（`capture.py:53-54`、`httpd.py:280-281`）。

## 2. 整条流水线

### 2.1 五个阶段

```
[1] 采集源选择        [2] FFmpeg 命令构造      [3] 切片         [4] HTTP 分发        [5] 播放

                       capture.start_hls()     -g = fps × N
```

| 阶段 | 代码位置 | 职责与契约 |
|---|---|---|
| 采集源枚举 | `ffmpeg_manager.py:486-508` `list_sources()` | 返回 `{screens, windows, audio_inputs, ffmpeg, platform}`；屏幕枚举失败不阻断（返回空表） |
| 视频输入参数 | `ffmpeg_manager.py:897-956` `build_video_input()` | 按平台选 gdigrab / avfoundation / x11grab，返回 `(输入参数, 视频滤镜串)` |
| 音频输入参数 | `ffmpeg_manager.py:978-1048` `build_audio_input()` | 返回 `[]` 表示不采声；多路时尾部追加 `-filter_complex` |
| 命令总装 | `capture.py:47-124` `start_hls()` | 唯一决定参数顺序的地方；`-vf` 必须排在所有 `-i` 之后 |
| 切片与分发 | `httpd.py:230-307` | 三条路由 + DLNA 专用响应头 |

### 2.2 采集源选择

`source` 的形态（`manager.py:88`、`ffmpeg_manager.py:901-902`）：

```json
{"type": "screen", "id": "desktop"}
{"type": "screen", "id": "screen:0,0,1920,1080"}
{"type": "window", "id": "win:1234", "title": "Chrome · Google Chrome", "screen_no": 1, "crop": [x,y,w,h], "crop_norm": [fx,fy,fw,fh]}
```

- 缺省即「整个屏幕」：`manager.py:104-106`，`source` 为空时补 `{"type":"screen","id":"desktop"}`。
- 「整个屏幕」在多屏机器上抓的是**所有显示器的并集**，前端为此专门给出提示文案（`src/locales/zh-CN.json:210`），并且实测过并集尺寸 4000×2571 这种奇数高度会被 x264 拒绝初始化（`ffmpeg_manager.py:510` 的 `_list_monitors` docstring、`ffmpeg_manager.py:886-889`）。
- 指定某块显示器：`_list_monitors()`（`ffmpeg_manager.py:510-578`）产出 `screen:x,y,w,h`，Windows 上翻译成 gdigrab 的 `-offset_x/-offset_y/-video_size`（`ffmpeg_manager.py:925-929`）。**非 Windows / 非 macOS 直接返回空表**（`ffmpeg_manager.py:529-530`）。
- 指定窗口：见 §3。macOS 上窗口＝「抓它所在的屏再按几何裁」，且裁剪坐标必须是**此刻**的，所以 `start()` 会先 `refresh_window()` 重算一次（`manager.py:109-113`）。

### 2.3 编码与切片参数（契约）

`capture.py:89-124` 是唯一决定编码参数的地方，每一项都有明确理由：

| 参数 | 值 | 为什么 | 证据 |
|---|---|---|---|
| `-profile:v -level` | `main` / `42` | 电视解码器普遍只认 Main；High 的 8×8 变换在老渲染器上直接拒播，表现为「换个分辨率就黑屏」 | `capture.py:91-93` |
| `-g` | `fps × segment_seconds` | HLS 只能在关键帧处切片。分片降到 1 秒而 GOP 还是 2 秒，切片点照样两秒一个，降延迟完全落空 | `capture.py:95-98`；测试 `tests/test_screencast.py:438` `test_gop_follows_segment_length` |
| `-r` | `fps` | 输入设备帧率失控时按目标帧率 CFR 封顶（macOS avfoundation 实测能让 raw 管道冲到 5000fps） | `capture.py:99-100`、`ffmpeg_manager.py:943-947` |
| `-x264-params` | `scenecut=0:open_gop=0:repeat_headers=1` | 屏幕内容几乎每帧都像「场景切换」，默认策略会在每次切窗口时插 IDR，HLS 于是切出几百毫秒的碎分片，电视解析器直接放弃。固定 + 闭合 GOP + 重复 SPS/PPS 让每个分片能独立起解 | `capture.py:101-105` |
| `-max_muxing_queue_size` | `screencast.muxing_queue_size`（默认 1024） | 屏幕帧到达是突发的（切窗口/滚动），默认 10 帧复用队列溢出后 FFmpeg 报 `Error queuing more packets` 并退出，表现为投屏中途断流 | `capture.py:113-115` |
| `-hls_flags` | `delete_segments+independent_segments+temp_file` | `temp_file` 先写 `.tmp` 再改名，否则客户端可能在半截播放列表上拿到没有 `#EXTM3U` 结尾的内容并判定流损坏 | `capture.py:119-121` |
| `-pix_fmt` | `yuv420p` | 兼容性 | `capture.py:94` |
| `-tune` | `zerolatency` | 直播低延迟 | `capture.py:90` |
| 音频 | `-c:a aac -b:a 128k -ar 48000 -ac 2`，无声时 `-an` | 有音频输入才写 aac | `capture.py:107-110`；测试 `tests/test_screencast.py:461` |

缩放滤镜：`build_scale_filter()`（`ffmpeg_manager.py:883-895`）

```
scale=<w>:<h>:force_original_aspect_ratio=decrease:force_divisible_by=2
```

`decrease` 保证比上限小的源不被放大重编码；`force_divisible_by=2` 是唯一兜底——x264 拒绝奇数尺寸（`width not divisible by 2` 后整个编码进程退出），而桌面尺寸经常就是奇数（Windows 显示缩放会给出 1917×1081 这类值）。宽高为 0 时回落到后台参数 `screencast.max_width` / `screencast.max_height`（默认 1920×1080，`params.py:64-72`）。

### 2.4 一条真实拼装出来的命令行

下面是按 `capture.py:78-124` 的拼接顺序、代入默认参数（`params.py` 中 `browser_segment_seconds=1`、`playlist_size=6`、`muxing_queue_size=1024`、`x264_preset=veryfast`）与前端默认画质（`ScreenCastPanel.vue:25-28`：1280×720 / 15fps / 2M）后**实际会组装出的参数序列**，场景为 Windows + 浏览器通道 + 整屏 + 麦克风 + WASAPI 环回：

```bash
ffmpeg -hide_banner -loglevel error -nostdin \
  -f gdigrab -framerate 15 -i desktop \
  -f dshow -i "audio=麦克风阵列 (Realtek(R) Audio)" \
  -f s16le -ar 48000 -ac 2 -i pipe:0 \
  -filter_complex "[1:a]aformat=sample_fmts=s16:sample_rates=48000:channel_layouts=stereo[m0];[2:a]aformat=sample_fmts=s16:sample_rates=48000:channel_layouts=stereo[m1];[m0][m1]amix=inputs=2:duration=longest:dropout_transition=0:normalize=0" \
  -vf "scale=1280:720:force_original_aspect_ratio=decrease:force_divisible_by=2" \
  -c:v libx264 -preset veryfast -tune zerolatency -profile:v main -level 42 \
  -b:v 2M -pix_fmt yuv420p -g 15 -r 15 \
  -x264-params scenecut=0:open_gop=0:repeat_headers=1 \
  -c:a aac -b:a 128k -ar 48000 -ac 2 \
  -max_muxing_queue_size 1024 -f hls -hls_time 1 -hls_list_size 6 \
  -hls_flags delete_segments+independent_segments+temp_file \
  -hls_segment_filename "%TEMP%\hancast_screencast_hls\a1b2c3\seg%03d.ts" \
  "%TEMP%\hancast_screencast_hls\a1b2c3\live.m3u8"
```

macOS + DLNA 通道 + 指定窗口 + 仅系统声音（Audio Tap），差异部分：

```bash
ffmpeg -hide_banner -loglevel error -nostdin \
  -use_wallclock_as_timestamps 1 -f avfoundation -framerate 15 -i 1:none \
  -f avfoundation -i :2 \
  -vf "crop=trunc(iw*0.520833/2)*2:trunc(ih*0.416667/2)*2:trunc(iw*0.239583):trunc(ih*0.291667),scale=1920:1080:force_original_aspect_ratio=decrease:force_divisible_by=2" \
  -c:v libx264 -preset veryfast -tune zerolatency -profile:v main -level 42 \
  -b:v 2M -pix_fmt yuv420p -g 30 -r 15 \
  -x264-params scenecut=0:open_gop=0:repeat_headers=1 \
  -c:a aac -b:a 128k -ar 48000 -ac 2 \
  -max_muxing_queue_size 1024 -f hls -hls_time 2 -hls_list_size 6 \
  -hls_flags delete_segments+independent_segments+temp_file \
  -hls_segment_filename "/tmp/hancast_screencast_hls/a1b2c3/seg%03d.ts" \
  "/tmp/hancast_screencast_hls/a1b2c3/live.m3u8"
```

阅读这两条样例时需要注意：

- **日志里的真实形式是单行**：`logger.info(f"[ScreenCast] HLS cmd: {' '.join(cmd)}")`（`capture.py:135`），不带 shell 引号；上面为了可读性做了换行并补了引号。要看真命令，去日志里搜 `HLS cmd:`。
- 会话号 `a1b2c3`、临时目录、设备名都是示例值；**参数序列与顺序**才是代码保证的部分。
- `crop=` 里的六个比例数字是示例（真实值由 `_window_entry` 按当时窗口几何算出，`ffmpeg_manager.py:356-384`）；表达式**格式**由 `build_crop_filter`（`ffmpeg_manager.py:387-402`）决定，`trunc(iw*fw/2)*2` 的写法是为了保证裁出来是偶数。
- `-g` 与 `-hls_time` 必须同源：`-g = fps × segment_seconds`（`capture.py:98`）。上面 Windows 例是 15×1=15，macOS 例是 15×2=30。
- macOS 例里只有一路音频（仅系统声音）时**不会**出现 `-filter_complex`，两路才有（`ffmpeg_manager.py:1033-1037`）。
- `-vf` 出现在**所有** `-i` 之后，这不是风格问题，见 §7.2。

### 2.5 HTTP 分发

服务：`screencast/httpd.py`，`aiohttp` 跑在独立线程（`httpd.py:84-128`）。

| 路由 | 处理函数 | 说明 |
|---|---|---|
| `GET /r/{session_id}` | `httpd.py:237-253` | 观看页。会话不在册 → 404 文本「投屏已结束或地址无效」；在册则读 `www/index.html`，替换 `__SESSION_ID__` 与 `__PLAYER_CONFIG__` 后返回 |
| `GET /static/{filename}` | `httpd.py:255-262` | 观看页静态资源（`hls.min.js` 等）。`basename` + 扩展名白名单双重限制 |
| `GET /hls/{session_id}/{filename}` | `httpd.py:277-307` | 播放列表与分片。目录穿越由 `_safe_hls_path`（`httpd.py:266-275`）拦 |

端口：默认 **8765**（`httpd.py:32`），启动时先试 8765、被占用则退回随机端口（`httpd.py:84-128` 的 `for try_port in (port, 0)`），实际端口从 `site._server.sockets[0].getsockname()[1]` 读回。因此**URL 里的端口不一定是 8765**，前端一律用后端返回的 `watch_url` / `url`。

MIME 与响应头（`httpd.py:291-306`）：

```
.m3u8 → application/vnd.apple.mpegurl
.ts   → video/mp2t
其它  → application/octet-stream
Cache-Control: no-cache, no-store
transferMode.dlna.org: Streaming
contentFeatures.dlna.org: DLNA.ORG_OP=01;DLNA.ORG_CI=0;DLNA.ORG_FLAGS=01700000000000000000000000000000
```

两个 DLNA 头是必需的：渲染器靠它们区分「边下边播」和「先下完再播」，缺 `transferMode` 的直播播放列表会被部分电视当普通文件缓冲，表现为控制器收到 `Play` 却迟迟等不到拉流请求（`httpd.py:300-303`）。`Cache-Control` 必需：直播列表每秒重生成，缓存会让观众看到过期分片（`httpd.py:297`）。

**关于 CORS：这个 HTTP 服务不发任何 CORS 头。** 全仓 `Access-Control-Allow-Origin` 只出现在 `media/server.py:491`（那是解析代理，不是投屏服务）。浏览器通道之所以不需要 CORS，是因为观看页与流同源、页面里用的是相对路径（`www/index.html:61-65`），不会触发跨源预检。**跨源嵌入观看页（例如把 `/r/<sid>` iframe 进别的站点）会因为拿不到 CORS 头而失败。**

拉流证据：`_note_pull` / `_note_miss`（`httpd.py:194-226`）统计 `pulls`（`.m3u8` 命中次数）、`misses`（要的文件不在，含未注册会话与已删除分片）、`clients`（独立客户端，上限 64）。`viewers()`（`httpd.py:186-192`）只统计 `screencast.viewer_window_seconds`（默认 15 秒）窗口内拉过播放列表的独立客户端。

DLNA 起流校验消费这份证据：`manager.py:348-380` 的 `_verify_dlna_pull` 在 `screencast.dlna_verify_seconds`（默认 12 秒）内轮询，

- `pulls > 0 且 misses >= 6` → 报「{设备} 跟不上当前码率（多个分片已被删除），请降低分辨率或码率后重试」（`manager.py:358-364`）；
- `pulls > 0` → 记一条 info 后收工（`manager.py:365-369`）；
- 窗口内一次都没拉到 → 报「{设备} 在 N 秒内没有拉取播放列表：请确认电视与本机在同一网段、允许 HanCast 接收局域网连接，或换较低分辨率重试」（`manager.py:370-380`）。

设计动机写在 `manager.py:349-351`：电视不会把「播不出来」回报给控制器，黑屏时「根本没拉到」和「拉到了但解码不了」的处置方式完全不同，只能靠本机侧的拉流证据区分。契约测试：`tests/test_screencast.py:795-843`（`TestDlnaVerify`）。

### 2.6 播放侧

浏览器观看页的播放器配置由后端注入（`httpd.py:47-56` `player_config()`）：

```python
max_latency = max(param("player.live_max_latency_duration_count"),
                  param("player.live_sync_duration_count") + 1)
```

**`liveMaxLatencyDurationCount` 必须严格大于 `liveSyncDurationCount`**，否则 hls.js 构造函数直接抛错、播放页白屏；`max()` 这层夹逼就是防用户把两个后台参数配成非法组合（`httpd.py:47-56`）。

`www/index.html:102-132` 的 hls.js 分支在注入配置之上再叠一层固定默认：`enableWorker:true`、`manifestLoadingMaxRetry:4`、`manifestLoadingRetryDelay:1000`、`levelLoadingMaxRetry:4`、`fragLoadingMaxRetry:4`；遇到 404 直接显示「投屏已结束」而不是无限重试。

电视侧没有播放代码——它只是一个 HLS 客户端。HanCast 能观测到的只有 §2.5 的拉流证据。

Linux 现状一句话：**只有「整屏 + 麦克风」这一条最小可用路径**，显示器/窗口枚举与系统声音都没有实现。

### 3.2 macOS

**窗口枚举**：`ffmpeg_manager.py:266-318` `darwin_windows()`，用 ctypes 直接调 CoreGraphics（`CGWindowListCopyWindowInfo`），不引 pyobjc。

- 系统窗口按 owner 过滤：`_CG_SYSTEM_OWNERS = {"WindowManager"}`（`ffmpeg_manager.py:152`、用于 `:301`）。
- **没有「屏幕录制与系统音频」权限时，系统会静默去掉 `kCGWindowName`**，窗口标题退化成 App 名（`darwin_windows` docstring，`ffmpeg_manager.py:266` 起）。前端把这个情况写进了提示文案：「macOS 未授予『屏幕录制』权限时窗口标题会显示为『（无标题）』，此时只能按所有者识别」（`src/locales/zh-CN.json:214`）；标签拼装逻辑在 `ffmpeg_manager.py:371-372`。
- 读 `CGWindowBounds` 里的数值必须走 `_cf_num`（`ffmpeg_manager.py:210-223`）：`kCFNumberDoubleType` 是 6 而不是 12，按 SInt128 读会越界写，结果是所有 bounds 变成 `5e-315`、枚举出 0 个窗口。
- 显示器枚举 `darwin_displays()`（`ffmpeg_manager.py:225-263`）要把 CoreGraphics 的 y-up 坐标翻成窗口坐标系（`top: -b.y`），并带上 Retina 缩放比。

**窗口→采集参数**：`_window_entry()`（`ffmpeg_manager.py:356-384`）同时产出像素版 `crop` 与**比例版** `crop_norm`，真正下发给 ffmpeg 的是比例版（`build_video_input` 优先取 `crop_norm`，`ffmpeg_manager.py:933-934`）。原因写在 `ffmpeg_manager.py:378-382`：avfoundation 送进 `crop` 滤镜的坐标系是它**实际采集的那块缓冲区**，而缓冲区尺寸在不同机器上不保证等于算出来的像素尺寸（HiDPI / 缩放分辨率下差 2 倍），像素版会裁到错位的一块。比例版与缓冲区尺寸无关，只要长宽比一致即可，偶数尺寸交给后面的 `scale`。

**屏幕设备索引不固定**：`avfoundation_screen_indexes()`（`ffmpeg_manager.py:81-128`）动态枚举。曾经固定用 `1`，在装有 OBS Virtual Camera 的机器上抓到的是摄像头（docstring，`ffmpeg_manager.py:81` 起）。探测失败时回落索引 1 并打 warning（`ffmpeg_manager.py:939-942`）。

**系统声音（Audio Tap）**：`screencast/macos_tap.py`。avfoundation 只认「输入设备」，而系统声音是**输出**，所以必须自己造一个输入设备：

```
AudioHardwareCreateProcessTap  ──► 一个进程级 tap（抓取全局立体声，排除自己）
        +
AudioHardwareCreateAggregateDevice ──► 名为「HanCast 系统声音」的聚合输入设备
        (uid: com.hancast.system-audio)
        ▼
avfoundation 里多出一个可选设备  ──► ffmpeg -f avfoundation -i :<idx>
```

- 设备名与 UID：`macos_tap.py:28-29`。
- 可用性判定：`supported()` = `hasattr(_CA, "AudioHardwareCreateProcessTap")`，即 **macOS 14.2+**（`macos_tap.py:182-186`）。
- `setPrivate: 0` 是整件事的关键（`macos_tap.py:340-344`，`argtypes=[ctypes.c_int8]` 因为 arm64 的 BOOL 是 int8）：默认建出来的是**私有环回**，而 ffmpeg 是另一个进程，于是 avfoundation 里永远看不到它。
- 排除自己的进程：`_self_pids` / `_self_process_objects`（`macos_tap.py:211-236`）。排除列表要的是 `AudioObjectID` 而不是 unix pid，传 pid 会得到 `'!obj'`；不排除的话自己投出去的音频会形成回音。
- 残留聚合设备清理：`_stale_aggregate()`（`macos_tap.py:301-311`）。聚合设备是系统级的，进程退出后设备仍留在系统里，表现为一个永远静音的假设备，且同 UID 二次创建报 `'nope'`。`ensure_device()`（`macos_tap.py:385-415`）会先清残留；`destroy_device()`（`macos_tap.py:418-432`）在停止/清理时销毁，进程被强杀时的残留由下一次 `ensure_device` 兜底（`macos_tap.py:426`）。
- 索引会变：Audio Tap 设备是枚举时现建的，avfoundation 索引跟着其他设备增减走。界面存的是用户当时看到的索引，`start()` 会按名称换成本次枚举到的真实索引（`manager.py:147-154`），测试见 `tests/test_screencast.py:880` `test_macos_tap_index_is_refreshed_at_start`。
- 14.1 及以下：只列物理设备，装了 BlackHole 的用户照旧可选（`ffmpeg_manager.py:772-775`、`ffmpeg_manager.py:1019-1025`）。BlackHole 需要用户自己在「音频 MIDI 设置」里把系统输出路由进去。
- 麦克风权限：见 §7.4。

### 3.3 Windows

**显示器 / 窗口枚举**：`_list_monitors()`（`ffmpeg_manager.py:510-578`）、`_list_windows()` + `_castable()`（`ffmpeg_manager.py:580-684`）。窗口用 `EnumWindows`，可投性判据全部来自实测（`_castable` docstring，`ffmpeg_manager.py:619` 起）：

- 必须有 `WS_CAPTION` 或 `WS_THICKFRAME`；
- 排除 `WS_EX_NOACTIVATE` / `WS_EX_TOOLWINDOW`（否则列表里会混进 `com.han.hancast-siw` 这类 16×16 的壳窗口、`CHeadBarWindow` 之类的输入法条）；
- 排除 `DWMWA_CLOAKED`：**另一个虚拟桌面上的窗口对 gdigrab 不可见（BitBlt 全黑）**；
- 排除位于 `-32000,-32000` 的窗口（最小化 / `WinDisplay` 之类）。

窗口标题走 gdigrab 的 `-i title=<标题>`（`ffmpeg_manager.py:918-922`）。注意 gdigrab 抓的是**屏幕上的那块矩形**：`GetWindowRect` 含 8px 不可见缩放边框（实测 2576×1408 → gdigrab 有效区 2560×1392；客户区 900×620 → 884×581，少掉的 16×39 是边框+标题栏），并且**别的窗口压在它上面时，投出去的就是压着它的那个**（不置顶时同一份代码两轮亮度 235 vs 45）。全部实测记录在 `tools/probe-win-window-picker.py:9-18`（另见 `:286-288`）。前端提示文案把这条讲清楚了（`src/locales/zh-CN.json:214`）。

**dshow 设备枚举与「分段头解析」**：`_list_audio_devices()`（`ffmpeg_manager.py:701-819`）。`ffmpeg -list_devices true -f dshow -i dummy` 的输出解析有两条坑：

1. **新版 ffmpeg 不再打印 "DirectShow audio devices" 这条分段头**——那条字符串压根不在 exe 里（用 `findstr` 验过，见 `ffmpeg_manager.py:711-716` 的注释）。所以主判据是设备行尾部的 `(audio|video|none)` 后缀：`r'"(.+)"\s*\((audio|video|none)\)\s*$'`（`ffmpeg_manager.py:726`）；只有解析不到后缀时才回落到分段头模式（测试 `tests/test_screencast.py:118` `test_windows_falls_back_to_dshow_section_header`）。
2. **"Alternative name" 行也带引号**，在分段头格式下会伪装成设备混进来，必须显式排除（`ffmpeg_manager.py:736-737`）。

**编码**：Windows 上 `ffmpeg -list_devices` 的输出可能是 cp936 而不是 UTF-8，直接 `decode()` 会得到空枚举结果，所以所有子进程输出走 `_run_utf8()`（`ffmpeg_manager.py:38-49`）。

**系统声音**：WASAPI 环回，见 §4.2。

**多屏并集**：`_list_monitors` docstring 记录了实测 4000×2571（奇数高度，x264 拒绝初始化），这是 `force_divisible_by=2` 存在的直接原因。

### 3.4 Linux

`x11grab` + `$DISPLAY`（缺省 `:0`），见 `ffmpeg_manager.py:952-954`。音频只有 `-f pulse -i default` 一条麦克风路径（`ffmpeg_manager.py:1045-1047`）。显示器与窗口枚举都没有实现，`_list_monitors` 在非 nt / 非 darwin 平台直接返回 `[]`。

## 4. 音频链路

### 4.1 混音：aformat 规整 + amix

多路音频必须先规整再混：`_mix_filter()`（`ffmpeg_manager.py:959-975`）

```
[1:a]aformat=sample_fmts=s16:sample_rates=48000:channel_layouts=stereo[m0];
[2:a]aformat=sample_fmts=s16:sample_rates=48000:channel_layouts=stereo[m1];
[m0][m1]amix=inputs=2:duration=longest:dropout_transition=0:normalize=0
```

- **为什么先 `aformat`**：`amix` 要求各输入的采样率、声道、采样格式一致，而 dshow 麦克风给的是设备原生格式（44.1k 单声道很常见），WASAPI 环回又跟着渲染设备走（48k 立体声），直接串起来混音图建不起来，FFmpeg 报 `Input formats not supported`（`ffmpeg_manager.py:962-965`）。
- **为什么 `normalize=0`**：默认归一会把两路各砍一半音量，实测人声明显发虚（`ffmpeg_manager.py:972-974`）。
- **为什么 `duration=longest:dropout_transition=0`**：任一路掉线不能让整条混音停摆或突变音量。
- **标签必须用真实输入序号**：视频占输入 0，音频从 1 起（`capture.py:81-82` 传 `input_offset=1`）。`take()` 每追加一个输入就把当前序号记成 `[N:a]` 并自增（`ffmpeg_manager.py:997-1002`）。标签指向无音频流的视频输入会让 FFmpeg 启动失败（`ffmpeg_manager.py:983-985`）。

各平台的音频输入拼装见 `build_audio_input()`（`ffmpeg_manager.py:978-1048`）：

| 场景 | 参数 |
|---|---|
| Windows 麦克风 | `-f dshow -i audio=<名>`（`:1046-1047`） |
| Windows 系统声音（环回） | `-f s16le -ar <rate> -ac <ch> -i pipe:0`（`:1048-1054`） |
| Windows 系统声音（dshow 立体声混音，罕见） | `-f dshow -i audio=<名>`（`:1055-1057`） |
| macOS 麦克风 | `-f avfoundation -i :<idx>`（`:1079-1080`） |
| macOS 系统声音 | `-f avfoundation -i :<idx>`（`:1081-1083`） |
| macOS 双路 | 两个 `-f avfoundation -i :<idx>` + `amix`（`:1074-1078`，avfoundation 单输入只支持一个音频设备） |
| Linux 麦克风 | `-f pulse -i default`（`:1087-1088`） |
| 都不勾 | 返回 `[]` → 编码侧写 `-an`（`capture.py:109-110`） |

### 4.2 Windows 系统声音：WASAPI 环回与「零字节饿死」

`screencast/loopback.py`。上游 FFmpeg 到 9.0 都没有 WASAPI 输入设备（ticket #9408 仍开着），所以环回必须由 sidecar 自己采成 s16le PCM，从 stdin 灌给 ffmpeg（`loopback.py:1-18` 模块 docstring、`ffmpeg_manager.py:1010-1013`）。

```
┌── sidecar 进程 ─────────────────────────────────────────┐
│  LoopbackStream                                         │
│   pyaudiowpatch (PortAudio/WASAPI)                      │
│     frames_per_buffer=1024 (≈21ms)                      │
│        │                                                │
│        ▼  loopback-pump 线程 (_pump_loop, :169-184)      │
│   Queue(maxsize=64) ── _offer 满了丢最旧 (:186-196)       │
│        │                                                │
│        ▼  read() (:198-209)                             │
│     有数据 → 原样返回                                     │
│     无数据 → _pad() 按单调时钟补静音 (:211-222)            │
│        │                                                │
│        ▼  _feed_loopback 线程 (capture.py:219-256)       │
│     proc.stdin.write(...)                               │
└───────────────────────┬─────────────────────────────────┘
                        ▼  -f s16le -i pipe:0
                    FFmpeg 子进程
```

**「零字节饿死」问题**：环回端点在**没人出声**时不提供数据。实测记录在 `loopback.py:1-18`：Windows .68 上 FxSound 端点 2.00 秒读到 380928 字节（≈ 实时 384000），而「扬声器 (Realtek(R) Audio)」环回在没人出声时 `read()` **直接卡住**。卡住的后果是 stdin 一个字节都不写，FFmpeg 的 `pipe:0` 输入饿死——画面正常、音频轨道停滞，HLS 的交织器反过来把视频也憋住。

**修法（按单调时钟补静音）**：`_pad()`（`loopback.py:211-222`）

```python
expected = int((time.monotonic() - self._started) * self._bytes_per_sec)
owed = expected - self._delivered
if owed < self._align:
    return b""
n = min(owed, self._chunk_bytes * MAX_PAD_CHUNKS) // self._align * self._align
```

- 用**单调时钟**算「到目前为止本该交付多少字节」，欠多少补多少，不依赖设备回调的节奏；
- `MAX_PAD_CHUNKS = 4`（≈85ms，`loopback.py:40`）是单次补静音的上限：**补太长会让音频冲到视频前面，HLS 的交织器反过来把视频憋住**（`loopback.py:36-40` 的注释）；
- `read()` 先 `self._q.get(timeout=POLL_SECONDS)`（0.05 秒，`loopback.py:36`），拿不到才走 `_pad()`（`loopback.py:198-209`），所以真数据和补白之间不会打架。

契约测试：`tests/test_screencast.py:493-620`（`TestLoopbackOwnership`），其中 `:561` `test_starved_device_still_feeds_realtime_silence` 直接锁住「设备不出数据时仍按实时速率交付静音」这条行为；该测试类的 docstring 里保留了 .68 上 v2.2.22 / v2.2.23 的现场证据（0.42 秒停滞、`0xc0000005` / `ntdll.dll`）。

**跨线程关流会崩**：PortAudio 的 C 调用不可并发、`close()` 不可重入，别的线程去 close 就是踩已释放的 stream（实测 `0xc0000005`，`loopback.py:133-137`、`capture.py:349-351`）。因此**关流权归采集线程**：`_release()`（`loopback.py:224-230`）只由 pump 线程调用，`stop()` 只是把请求交给它并 `feeder.join(timeout=2)`（`capture.py:327-359`）。测试：`tests/test_screencast.py:581` `test_close_is_executed_by_the_pump_thread_only`、`:599` `test_stop_leaves_the_wedged_stream_to_the_pump`。

**环回必须在 FFmpeg 之前打开**：`capture.py:137-146`。设备被别的程序独占、或者用户在选完之后把输出切走了，都要在这一步就说清楚（错误文案「系统声音采不起来：输出设备可能已被切换或独占…」），而不是留下一个没声音的会话。

**喂料线程早退要留证据**：`_feed_loopback`（`capture.py:219-256`）在写 stdin 出异常时记异常类型、`rc = proc.poll()` 与 stderr 提示（`capture.py:239-246`）。背景是 .68 上偶发「起流 0.3 秒后」就断，没有这条日志根本查不下去。

### 4.3 「当前出声」这条标记怎么来的

Windows 上每块**渲染设备**各有一条自己的环回镜像，只有对应当前默认输出的那条才真能抓到声音；选到闲置的那块，画面正常但投出去没声音（前端提示文案 `src/locales/zh-CN.json:224`）。

判定方式是**「是不是系统默认输出端点」这个布尔标记，不是靠名字猜**：

- `loopback_devices()`（`loopback.py:55-94`）枚举时把默认端点排在第一位并打上 `default=True`。排序是必要的：机器上挂着 HDMI / 虚拟声卡时，PortAudio 列表的第一位往往是一块没在出声的喇叭。
- `resolve(name)`（`loopback.py:97-111`）按名字找回设备，找不到回落 `devices[0]`。
- 标记随设备条目一路上抛：`ffmpeg_manager.py:765-768` 把 `default` 透传进 `audio_inputs`。
- 前端渲染成后缀：`ScreenCastPanel.vue:81-89`，`hasLoopbackMirror` 为真时给 `d.default` 的条目拼上 `t('screencast.defaultOutputSuffix')`，即「（当前出声）」（`src/locales/zh-CN.json:223`）。
- 同一处也负责显示 `screencast.loopbackTip`（`ScreenCastPanel.vue:321`），提醒用户换了输出设备（拔插耳机、切蓝牙）后要关掉面板重开以刷新列表。

契约测试：`tests/test_screencast.py:657` `test_live_loopback_flagged_and_sorted_first`、`:665` `test_default_lookup_failure_keeps_the_list`。验收脚本 `tools/verify-win-screencast-tone-content.sh` 也明确要求「系统设备按 `default` 标记选，不按名字选」。

### 4.4 开录前的静音闸门

勾了麦克风却拿不到声音是最难自查的一类故障：没有录音权限时系统不报错也不弹窗（macOS 尤其如此），设备照样枚举得到，只是采回来的每个样本都是 0，画面流畅、毫无异常。所以 `start()` 在开录前**试采一秒**：

- `audio_input_silent(device, seconds=1.0)`（`ffmpeg_manager.py:821-860`）跑一次 `-t 1 -ar 48000 -ac 1 -c:a pcm_s16le -f wav -`，解析 WAV 里的 PCM 样本。返回值是三态：`True`（全静音）/ `False`（有信号）/ `None`（**测不出来**，例如读到的数据 `len(data) < 8000`）。
- 只有 `is True` 才拦（`manager.py:129-138`）；`None` 不拦——测不出来不等于没声音。
- 拦截文案直接给出两个平台的授权路径（`manager.py:134-138`）。
- 另一道前置闸门是 `_missing_audio_devices()`（`manager.py:171-202`）：勾了声学设备、系统里却找不到它，直接说清楚，而不是静默降级成 `-an`（`manager.py:123-128` 的注释记录了以前静默降级的后果：用户以为在收声，实际每一帧都是哑的）。枚举本身不可用时返回 `None` 放行——「别拦住投屏」（`manager.py:191`）。

契约测试：`tests/test_screencast.py:170` `test_audio_input_silent_reads_wav_pcm`、`:904` `test_mic_without_signal_blocks_start`、`:869` `test_system_audio_without_device_rejected`。

### 5.2 启动

`start()`（`manager.py:82-169`）按顺序过闸门，任何一步失败都直接返回可读的 `error`：

```
running?                → 「已有投屏正在进行，请先停止」            (manager.py:92-93)
target ∈ {dlna,browser} → 「未知目标类型: X」                       (manager.py:95-97)
ffmpeg.check()          → FFmpeg 不可用                             (manager.py:100-102)
source 合法性            → 「窗口源缺少窗口信息」                     (manager.py:104-108)
macOS window            → refresh_window() 重算此刻几何              (manager.py:109-113)
system 但没选设备        → 带平台指引的错误                          (manager.py:117-120)
mic 但没选设备           → 「未选择麦克风设备」                       (manager.py:121-122)
设备存在性               → _missing_audio_devices()                  (manager.py:125-128)
麦克风全静音             → audio_input_silent() 闸门 + 授权指引       (manager.py:129-138)
标记 _loopback          → 匹配到环回设备才写                         (manager.py:139-146)
macOS tap 索引重解析     → 按名称换成本次枚举的真实索引                (manager.py:147-154)
新会话号                 → secrets.token_hex(3)                      (manager.py:157)
_start()                → 异常则 logger.exception + _teardown
                          + 「启动失败: {e}」                        (manager.py:158-163)
成功 → _emit()；失败 → _teardown()                                  (manager.py:165-169)
```

`_start()`（`manager.py:262-339`）的实际动作顺序：

1. `target=dlna` 时先校验 `device_id` 与设备在线（`manager.py:265-271`）；
2. `httpd.start()` + `register_session()`（`manager.py:273-277`）——失败即返回，不会留下半个会话；
3. 建会话独占目录并起 FFmpeg（`manager.py:279-287`）；
4. 拼 `m3u8_url`（`manager.py:290-291`）；
5. DLNA：构造 DIDL（`build_didl_item(m3u8_url, HLS_MIME, f"{device.display_name} 屏幕投屏")`，`manager.py:296-297`）→ `session.play(...)`（`manager.py:299`）。
   - `ControlUrlUnavailable` / `RendererUnresponsive` → 先 `_stop_cast` 释放电视，再原样回传异常文本（`manager.py:300-306`）；
   - 其它异常 → 同样先释放，再回「电视拒绝播放（…），可换较低分辨率/码率后重试」（`manager.py:307-315`）；
   - 成功后起 `screencast-dlna-verify` 守护线程做拉流校验（`manager.py:322-325`）。
6. 浏览器：拼 `watch_url`（`manager.py:328`）并返回宽高帧率。

FFmpeg 就绪判定：起流后最多等 8 秒，且要求 `getmtime(m3u8) >= started_at`（`capture.py:167-189`）。两种失败各有文案——「FFmpeg 提前退出（退出码 N）」+ stderr 提示，或「HLS 输出超时未生成（屏幕捕获失败，可能是窗口不存在/权限未授予）」+ 提示。

`stderr` 提示由 `_stderr_hint()`（`capture.py:274-288`）按标记串匹配给出：`not divisible`、`Failed to`、`Invalid argument`、`Permission denied`、`No such file`、`Cannot open`、`Device or resource busy`；保留尾部 40 行（`capture.py:24` `_STDERR_TAIL`）。`_drain_stderr`（`capture.py:263-272`）必须一直读——**不读满 64KB 管道会把 FFmpeg 卡死**。

### 5.3 停止

`stop()`（`manager.py:204-229`）**幂等**：没在跑也走一遍 `_teardown()` 并返回 `{"ok": True, "already_stopped": True}`（`manager.py:206-208`）。测试 `tests/test_screencast.py:938` `test_stop_is_idempotent`。

DLNA 通道下停止分两步：先 `handler._stop_cast(...)` 摘电视（`manager.py:214-223`），再 `_teardown()` 拆本机。`_stop_cast`（`commands.py:475-502`）的 docstring 明确了顺序理由：**先摘会话再发 SOAP Stop**，且 `control_failed` 必须一路传到前端。`_stop_cast` 抛异常时，把当前设备记成失败并带上异常文本（`manager.py:220-223`）——不能因为电视失联就让用户停不掉本机。

返回值 `{ok, control_failed, reasons}`（`manager.py:229`）；`manager.py:227-228` 的注释写清了语义：分片目录已删、HTTP 服务已停，电视顶多把缓冲播完；但 Stop 没送达时必须让前端知道，否则用户以为「停止」＝电视已经回到待机。

契约测试：`hancast-backend/tests/test_stop_cast_delivery.py`（159 行）锁住停止链路的三条契约；端到端脚本 `tools/verify-dlna-stop-chain.py` 要求**渲染器自报** `PLAYING → STOPPED`（只看本机状态会骗人）。

### 5.4 异常提前退出

FFmpeg 进程死掉或卡流由 `_watch` 线程发现（`capture.py:290-315`）：

- 进程退出 → 「屏幕捕获进程已退出（退出码 N）」；
- `m3u8` 的 mtime 超过 15 秒没动 → 「屏幕捕获已停止输出（画面卡住）」。

回调进 `manager._on_capture_error()`（`manager.py:388-406`），顺序很关键：

```python
self._teardown()          # 先拆
self._state["error"] = msg  # 再写错误
```

因为 `_teardown` 里的 `_reset` 会清空 `error`，**先写后拆的话前端拿不到失败原因，只剩一个「不知道为什么不投了」的黑屏**（`manager.py:395-396`）。之后如果通道是 dlna，还要主动 `_stop_cast` 释放电视，否则电视继续拉一条死流、前端也起不了下一次（`manager.py:399-405`）。测试：`tests/test_screencast.py:970` `test_capture_error_frees_dlna_channel`。

### 5.5 端口释放与会话注销

`_teardown()`（`manager.py:408-435`）的契约写在 docstring 里：**幂等，且任何一步失败都不能挡住其余步骤**——这一步冒异常的话，用户点「停止投屏」就永远没有回应（注释直接记了曾真的发生过：会话注销抛 `TypeError` 冒到命令循环）。步骤：

```
capture.stop()          → 异常只记 warning                     (manager.py:415-420)
httpd.unregister_session(sid) → 异常只记 warning               (manager.py:423-427)
rmtree(hls/<sid>)       → ignore_errors=True                   (manager.py:428)
httpd.stop()            → 没有会话就把服务停下来，下次 start
                          才能拿回固定端口 8765                  (manager.py:429-433)
_release_tap()          → 仅 macOS，销毁自建 Audio Tap 设备      (manager.py:434, 437-450)
_reset()                → 清空状态                              (manager.py:435, 452-464)
```

两个曾经真实踩过的坑：

1. `unregister_session` 里 `sessions` 是 **set**，`pop(id, None)` 会抛 `TypeError` → 表现是「点了停止没反应」；改用 `discard`（`httpd.py:158-175`，注释在 `:170-172`）。
2. `httpd.stop()` 必须停掉 `run_forever`，否则线程存活、下次 `start()` 被 `is_alive()` 短路，端口拿不回来（`httpd.py:130-154`，注释在 `:143-144`）。

进程退出兜底：`commands.py:255-259` 的 `cleanup()` **先**调 `screencast.cleanup()`；`manager.cleanup()`（`manager.py:249-260`）依次 `stop()` → `httpd.stop()` → `_release_tap()`，其中最后一步是兜底：没有会话时 `stop()` 会提前返回、走不到 `_teardown`，环回/聚合设备就漏释放了（`manager.py:259`）。

### 5.6 状态事件如何到前端

统一出口是 `_emit()`（`manager.py:466-471`）：`protocol_io.emit_event("screen_cast_state_changed", self.status())`，走 Sidecar ↔ 壳层的 JSON 行协议（stdout）。`_emit` 自己吞异常，只记 warning——状态推送失败不该把业务线程带崩。

触发点：启动成功（`manager.py:166`）、停止（`manager.py:226`）、拉流校验出结论（`manager.py:363`、`:380`）、观众数变化（`manager.py:382-386`，由 httpd 事件循环线程回调）、采集异常（`manager.py:406`）。

`status()`（`manager.py:231-241`）在快照之上补三样：

- `viewers`：**只有 `target == "browser"` 才实时刷新**（`manager.py:234-235`）；
- `pull`：拉流证据 `{pulls, misses, clients, last}`（`manager.py:236-239`）；
- `ffmpeg`：`ffmpeg.check()` 结果（`manager.py:240`）。

前端监听在 `src/stores/screencast.ts:152-166`；`ScreenCastPanel.vue:367-386` 渲染「投屏中」徽标、观众数与邀请链接，`:389-391` 在停止态仍展示 `lastError`，`:394` 挂 `StopWarningBanner`。

### 5.7 `close()` 只等 0.5 秒这条修复的来龙去脉

提交 `73a8345`，改动只有一行：`loopback.py:241` 的 `self._pump.join(timeout=1.0)` → `join(timeout=0.5)`。

推理链条（提交信息与 `loopback.py:224-243` 的注释一致）：

1. 环回正常交付时，采集线程在**一个 chunk（≈21ms）内**就从 `read()` 返回；
2. 于是 `join(1.0)` 唯一会真等满的场景，恰恰是「端点没数据、`read()` 一直阻塞」——也就是 §4.2 里刚修好的那条饿死路径；
3. 结果：设备越安静，每次点「停止投屏」都要白等满一秒；
4. 把超时压到 0.5 秒，正常路径照样瞬间返回，病态路径的等待减半。注释同步到新架构：**关闭权在采集线程，不在喂料线程**（跨线程 close 会踩已释放的 stream，实测 `0xc0000005`，见 §4.2）。

这条修复与前一条（`c97ff52` 按单调时钟补静音）是同一个现场的连续两步：先让安静端点不再饿死管线，再让「等一个安静端点」不再拖慢停止。

### 5.8 FFmpeg 依赖：检测已有，缺失时按需下载（v2.3.11）

**历史一句**：FFmpeg 曾经随包——`bundle.resources` 里挂 `ffmpeg/*`，CI 从 `eugeneware/ffmpeg-static` 的 `b6.1.1` 下静态单文件、Windows 改名 `ffmpeg.exe`。v2.3.11 起全部删除：它是一个用户机器上普遍已装、且体积按平台各异（几十 MB 起）的外部依赖，随包只让安装包变大，换来的还是用户没法自己升级的那一份。现在改为**检测本机已装的 FFmpeg，确实没有时让用户自选**（自己装 / 让程序下载）。

检测顺序（`ffmpeg_deps.status()`，`utils/ffmpeg_deps.py:189-252`；`ffmpeg_manager.check()` 只是把 `_configured()` 的返回值递进去，`ffmpeg_manager.py:416-441`）：

| 层 | 来源 | 判据 |
|---|---|---|
| ① 手动指定 | 设置/弹窗里填的路径（`screencast.ffmpeg_path`） | 路径本身 `-version` 跑不通就**降级继续找**并打 warning（`ffmpeg_manager.py:425-427`），不让一个失效配置把功能锁死 |
| ② 系统已装 | `search_dirs()` = `PATH` + 平台常见目录（`ffmpeg_deps.py:104-117`）；Windows 还要往 winget 包目录里下钻一层 `bin/`（`_walk_dirs()`，`:120-139`） | 逐个候选跑 `-version`（`read_version()`，`:142-162`，30 秒结果缓存 `:36`） |
| ③ 本程序下载的那份 | `<SETTING_DIR>/bin/`（`managed_dir()`，`:51-53`） | 同上；命中则 `source="downloaded"` |

「文件在」不等于「能用」——每一层都必须真跑出 `-version` 才算命中，这是 ②③ 顺序里最容易被忽略的一条：装坏了的 exe、平台不匹配的构建，都会被跳过并继续往下找。

手动指定那条还有个配套行为：指了 ffmpeg 而系统里找不到 ffprobe 时，会去**同目录**取那份 ffprobe 当搭档（`ffmpeg_deps.py:219-225`），因为 gyan/BtbN 这类包都是两个二进制同目录分发。已知边界：`set_ffmpeg_path` 只能设不能清（§5.1），但失效路径会在 `_configured()` 里被降级掉（`ffmpeg_manager.py:425-427`），所以不会被一个旧配置永久锁住。

必需/可选是两条清单（`:43-44`）：`REQUIRED=("ffmpeg",)`、`OPTIONAL=("ffprobe",)`。ffprobe 之所以只是可选——macOS 那条 ffmpeg-static 产物**只有一个 ffmpeg 二进制**，缺 ffprobe 不该拦住屏幕投屏，它只影响 `media/parser.py` 的时长探测（那里用 `probe_path() or "ffprobe"`）。

`status()` 的返回同时是弹窗的数据源：`ok / path / version / source / items[] / missing[] / optional_missing[] / managed_dir / platform / arch / install_commands[] / download / error`。`install_commands()`（`:178-188`）按平台给可复制的命令：Windows `winget install --id Gyan.FFmpeg -e` / `choco install ffmpeg -y`，macOS `brew install ffmpeg` / `port install ffmpeg`，Linux `apt install ffmpeg` / `dnf install ffmpeg`。

下载走后台任务表 + 轮询，理由和 §2 的解析异步化同一个：归档几百 MB，而 Rust 侧 `COMMAND_TIMEOUT = 60s`（`src-tauri/src/sidecar.rs:18`）等不起。

- `start_download()`（`:448-469`）拿锁起线程**立刻返回**任务句柄；
- `download_status()`（`:470-474`）给前端轮询，阶段 ∈ `connecting / downloading / extracting / verifying / done / failed`；`_download_archive()`（`:355-397`）每 0.4 秒汇报 `received/total/percent/speed/elapsed`；
- 源按 `(sys_platform, machine)` 选（`_SOURCES`，`:264-296`）：win32/amd64 → gyan.dev `ffmpeg-release-essentials.zip`，win32/arm64 → BtbN，darwin arm64 与 x86_64 → ffmpeg-static `b6.1.1` 的 `.gz`，linux x86_64/aarch64 → johnvansickle `tar.xz`；
- 体积闸门 `MAX_ARCHIVE_BYTES = 512MB`（`:32`）拦 Content-Length 撒谎的响应；解压只按 **basename** 匹配想要的名（`_wanted_names()`/`_extract()`，`:398-447`），不照归档里的路径落盘，且落盘 `chmod 0o755`；
- 收尾必须 `verifying` 再跑一次 `-version`，跑不起来报的是「下载并解包成功，但这个 ffmpeg 跑不起来……多半是当前平台用不了这份构建」（`_run_download()`，`:480-520`），归档无论如何用完即删。

失败时给用户看的是**底层异常原文**：`format_error()`（`:308-324`）沿 `__cause__`/`__context__` 逐层收集、去重、用 ` ← ` 连接（最多 3 段），所以弹窗里出现的是 `连接下载源失败（https://…）— ConnectionError: …` 这种能据以判断的句子，而不是一句「下载失败」。

前端两个入口（第 20 个组件 `src/components/FfmpegDepsModal.vue`）：

1. 面板底部「打开依赖」按钮——`ScreenCastPanel.vue:198-201`，只在 `!sc.ffmpegOk` 的错误条里出现；旧的「手填 ffmpeg 路径」输入框已由弹窗接管（手填仍在，位置在弹窗里，`FfmpegDepsModal.vue:74-` 的 `onSetManual` 走 `set_ffmpeg_path`）。
2. 打开面板时自动提示一次——`ScreenCastPanel.vue:43-50`：`list_screen_sources` 回来带 `ffmpeg.ok=false` 就自动弹，`depsPrompted` 保证每次开面板只弹一次，关掉不再追着弹。

弹窗四个动作分别落在：`打开安装目录` → Rust `open_ffmpeg_dir`（前端**不传路径**，由 Rust 读 Sidecar 报告里的 `managed_dir` 并 `create_dir_all`，避免前端拿到一个不存在或不属于本程序的目录）；`重新检测` → `ffmpeg_status(refresh=true)`；复制安装命令 → `install_commands`；`下载并继续` → `ffmpeg_download_start` 后 store 每 1s 轮询 `ffmpeg_download_status`（`src/stores/screencast.ts:114-128`、`:143-153`），`done` 时立刻带 refresh 重报一次，`onUnmounted` 停表（`:284`）。

## 7. 平台限制与已知坑

这一节列的是**做不到**或**容易做错**的事，每条都附证据。

### 7.1 FFmpeg 没有 WASAPI 输入，PortAudio 环回是硬依赖

- 事实：上游 FFmpeg **到 9.0 都没有 WASAPI 输入设备**，ticket #9408 仍开着。证据：`screencast/loopback.py:1-18` 模块 docstring；`hancast-backend/pyproject.toml:23-26`（注释「FFmpeg 没有 WASAPI 输入（ticket #9408 未合并）」+ 依赖 `pyaudiowpatch>=0.2.12.9; sys_platform == 'win32'`）。
- 后果：Windows 系统声音**必须**由 sidecar 自己用 PortAudio 采成 s16le PCM，再从 `-f s16le -i pipe:0` 灌进 ffmpeg（`ffmpeg_manager.py:1010-1013`）。这条路径带来 §4.2 的全部复杂度（补静音、跨线程关流、喂料线程诊断），也带来一个额外依赖 `pyaudiowpatch`（仅 win32）。
- 不要用 dshow 的「立体声混音」替代：绝大多数机器的驱动根本没注册这个设备（`ffmpeg_manager.py:759-761`）。代码里保留了 dshow 分支（`ffmpeg_manager.py:1014-1016`）只是给极少数有这个设备的机器兜底。

### 7.2 有些 FFmpeg 能力任何版本都没有，只能自己做原生辅助

两类，都不是「升级 ffmpeg 就能解决」：

1. **macOS 没有窗口输入**。`ffmpeg_manager.py:144-146` 的注释明确：FFmpeg avfoundation **从 6.1 到 master 都没有窗口输入**。所以 macOS 的「指定窗口」只能实现为「抓它所在那块屏 + `crop`」（`ffmpeg_manager.py:948-951`）。这带来两个用户可见的语义差别：
   - 别的窗口压在目标窗口上面时，投出去的是**压着它的那个**（前端提示 `zh-CN.json:214` 已明说）；
   - 窗口移动/关闭/最小化后必须重新选择，`start()` 前会强制重算几何（`manager.py:109-113`、`ffmpeg_manager.py:686-699`）。
2. **macOS 系统声音不是输入设备**。avfoundation 只认输入设备，系统声音是输出（`macos_tap.py:1-13`）。HanCast 的做法是用 ctypes 直接调 CoreAudio 造一个聚合输入设备（`macos_tap.py:328-370`），**不引新依赖**（不用 pyobjc、不用装 BlackHole）。这就是「原生辅助」的形态：能力在系统 API 里，ffmpeg 拿不到，只能自己在进程外造一个 ffmpeg 能看见的设备。

顺带一条同类限制：**Windows 环回设备是每块渲染设备一条镜像**，只有默认输出那条真能抓到声音（§4.3），ffmpeg 侧没有任何机制帮你选对。

### 7.3 adhoc 签名与 macOS TCC

- 事实：macOS 15+ 把「本地网络」做成 TCC 权限，**按代码身份判定**。CI 不签名时主程序只有 Rust 链接器写的 adhoc 签名（`Identifier=HanCast-<16位hex>`、`flags=0x20002(adhoc,linker-signed)`），**同一个 bundle id 每次构建换一个身份**，NetworkAgent 认不出它就静默拒绝组播（`sendto 239.255.255.250` → `Errno 65`），连弹窗都没有、TCC.db 里也不留记录。证据：`src-tauri/Info.plist:5-20` 的注释块、`.github/workflows/build.yml:359-366` 的注释块。
- A/B 实测（同一台机器、同一份字节，2026-10-13）：产物原样 → 心跳日志 `通道 broadcast`；`codesign --force --deep -s -` 重签 → `通道 multicast`（24 条）+ 入站 200。证据：`.github/workflows/build.yml:364-366`。
- 因此 CI 在**打 dmg 之前**必须重签，并断言签名 Identifier == `com.han.hancast`、且不带 `linker-signed` 标志：`.github/workflows/build.yml:367-388`（签名 `:377`、校验 `:378`、Identifier 断言 `:379-383`、linker-signed 断言 `:384-387`）。签完再动 bundle 会让签名失效，所以顺序不能换（`.github/workflows/build.yml:366`）。dmg 也不复用 `tauri build --bundles dmg`，因为它会重跑 cargo 重建 `.app`，把上一步的修复覆盖掉（`.github/workflows/build.yml:390-395`）。
- 声明本身也是双份的，缺一不可：只写 `NSLocalNetworkUsageDescription` → 单播/入站通、组播仍 `Errno 65`；再补 `NSBonjourServices=["_upnp._tcp"]` 才有 `通道 multicast`（`src-tauri/Info.plist:9-13`）。实际出货的三个 key：`NSLocalNetworkUsageDescription`（`:21-22`）、`NSBonjourServices`（`:23-26`）、`NSMicrophoneUsageDescription`（`:35-36`）。
- 引入这条的提交是 `bd847da`（v2.2.13 停止链路如实回报 + NSBonjourServices）；`src-tauri/Info.plist:14` 的注释记了「2.2.13 就是这么翻车的」——光有 plist 不够。

⚠️ 未验证：**「每次发版都要重新授予『屏幕录制』和『麦克风』」这一说法在本仓找不到直接证据。** 仓内的 adhoc/代码身份证据（`src-tauri/Info.plist:14-19`、`.github/workflows/build.yml:359-366`）覆盖的是**本地网络**权限与签名 Identifier 不稳定，A/B 实测记录的也是组播通道，不是屏幕录制/麦克风的 TCC 重新弹窗。按同一套「TCC 按代码身份判定」的机制推断，屏幕录制/麦克风授权理论上会受同样影响，但仓库里没有对应的实测记录或断言，所以不下结论。

### 7.4 麦克风权限：声明齐全也可能恒静音

`src-tauri/Info.plist:27-34` 把这条坑写得很完整：

- 缺 `NSMicrophoneUsageDescription` 的后果**不是「弹窗询问被拒」，而是根本不弹**：TCC 直接判「拒绝且不再提示」；
- ffmpeg 作为子进程从 App 继承这条授权，抓到的音频**恒为静音**，而设备照样枚举得到（枚举不过是以 "Microphone" 开头的字符串），于是用户看到的是「选了麦克风但投出去没声音」；
- 声明只是前提：**TCC 在第一次真正访问音频时才写库，而 ffmpeg 自己不会触发弹窗**。

所以前端在勾选麦克风时先用 webview 走一次 `getUserMedia({audio:true})` 把授权拿到，再让 ffmpeg 接手：`ScreenCastPanel.vue:106-129`（`ensureMicAccess`）、`:110` 的注释、`:129` 的 watch、`:132` 的 onStart 前置；被拒时 `:307` 给「重试授权」按钮，文案 `screencast.micDenied`（`zh-CN.json:220`）。后端还有 §4.4 的静音闸门作为最后一道防线。

⚠️ 未验证：**出货的 `Info.plist` 里没有 `NSAudioCaptureUsageDescription`**（全文只有 §7.3 列的三个 key，`src-tauri/Info.plist:21-36`），而 `tools/run-macos-tap-probe.sh:5-8` 明确要求探针跑在一个带 `NSAudioCaptureUsageDescription` 的 `.app` bundle 里，并记录「裸 python 跑的话 `CreateProcessTap` 返回 noErr 但零条流」。两者是否意味着**出货 App 的 Audio Tap 也需要这条声明**、还是「麦克风声明已足够覆盖 Audio Tap」，仓库里没有结论性证据（`src-tauri/Info.plist:27` 只写了一句「ScreenCaptureKit 采系统声音同样要求这条声明」，指的仍是 `NSMicrophoneUsageDescription`，而 HanCast 用的是 Audio Tap 不是 ScreenCaptureKit）。

### 7.5 `-vf` 必须排在所有 `-i` 之后

- 症状：选了麦克风或系统声音就投不起来，ffmpeg 报 `Option vf cannot be applied to input url audio=…` 并 EINVAL 退出。
- 原因：ffmpeg 把 `-i` **之前**的选项判给「下一个输入」，夹在中间的 `-vf` 会落到麦克风输入上。
- 证据：`ffmpeg_manager.py:907-911`（docstring，含「2026-10-14 .68 实据」）、`capture.py:85-88`（拼接处的注释与实现）。
- 修复提交：`68bbb29`（v2.2.23）。
- 回归防线：`tests/test_screencast.py:378` `test_video_filter_sits_after_all_inputs`；`tools/verify-screencast-audio-order.cmd` / `.ps1`（旧实现必须 FAIL）；`tools/verify-win-screencast-audio-live.cmd`（在已发布产物上断言看不到这条错误串）。

同类的「选项归属」坑还有 gdigrab 的 `-framerate`：它是**输入选项**，必须排在 `-i` 前面，不给的话 gdigrab 默认 1fps，窗口投屏变成幻灯片（`ffmpeg_manager.py:920-922`）。

### 7.6 分片目录必须会话独占

复用同一目录会让上一轮的 `live.m3u8` 残留，电视拉到的是已被删除分片的死流（`capture.py:53-54`）。两处防护：`start_hls` 开头整体 `rmtree` 再 `makedirs`（`capture.py:73-75`，测试 `tests/test_screencast.py:466` `test_old_session_dir_is_wiped`）；`_handle_hls` 先查会话是否在册，不在册直接 404 而不是「目录存在就给」（`httpd.py:280-284`）。

### 7.7 观看页响应不能把 charset 写进 content_type

aiohttp 禁止 `content_type` 里带参数，charset 要用 `charset=` 单独传；写在一起会让这两个错误分支在**真正被触发时**抛 `ValueError` 变成 500（`httpd.py:239-247`）。测试类 `tests/test_screencast.py:734-778`（`TestWatchPageResponses`）的 docstring 直接写了「这两条错误分支曾经因为 content_type 带 charset 直接 500」，覆盖 `:744` 停止后观看页 404 而非 500、`:750` 未注册会话的 HLS 404、`:763` 已注册会话正常服务。

### 7.8 观众数文案与实现不一致

前端邀请提示写「最多支持 20 人同时观看」（`src/locales/zh-CN.json:235`），而后端 `viewers` 的实现上限是 **64** 个独立客户端（`httpd.py:198`、`:205`），且 `viewers()` 统计的是 `viewer_window_seconds`（默认 15 秒）窗口内拉过播放列表的客户端数（`httpd.py:186-192`），并非并发连接数。**没有代码强制 20 这个上限。** 这句话应理解为产品口径而非技术限制。

### 7.9 `viewers` 对 DLNA 通道不刷新

`status()` 只在 `target == "browser"` 时才实时取 `viewers`（`manager.py:234-235`）。DLNA 通道下 `viewers` 恒为 0（`manager.py:319` 初始化），即便电视确实一直在拉流——拉流证据在 `status()["pull"]` 里，不在 `viewers` 里。排查电视黑屏时看 `pull`，不要看 `viewers`。

### 7.10 采集与分发的固有延迟

延迟下限就是分片粒度（`httpd.py:1-12`）：浏览器 1 秒分片端到端约 1–3 秒，电视 2 秒分片约 3–6 秒。想再低只能减小分片，代价是请求变密、慢客户端 `misses` 上涨（`manager.py:358-364`）。`tools/verify-watch-page-live.mjs` 用真实 Chromium + CDP 量的是**实际画面运动与延迟**，不是接口返回值——`status` 说 running 只代表进程还在（`tools/verify-win-screencast-dwell.sh` 的立项理由同样是这条）。

### 7.11 其它已知边界

- **FFmpeg 依赖发现顺序**：手动指定 → 系统已装（`PATH` + 平台常见目录）→ 本程序下载到 `<SETTING_DIR>/bin/`（`utils/ffmpeg_deps.py:189-252`，`check()` 在 `ffmpeg_manager.py:429-441`，`set_path()` 在 `:448`）。自 v2.3.11 起**不再随包**，曾经夹在中间的「随包 `ffmpeg/` 目录」那一层连同 `_get_base_path()` / `_find_in_program_dir()` 一起删了。找不到时前端弹「需要下载运行依赖」（`FfmpegDepsModal.vue`，见 §5.8），手填路径的入口也在那里面。
- **`_run_utf8`**：Windows 上 ffmpeg 子进程输出可能是 cp936，直接 decode 会得到空枚举（`ffmpeg_manager.py:38-49`）。所有枚举都必须走它。
- **sidecar 的 stdin 是协议管道**：`_spawn` 默认把子进程 stdin 设为 `DEVNULL`，只有喂环回时才开管道（`capture.py:205-217`，注释在 `:210-212`：sidecar 的 stdin 正是与 Tauri 之间的 JSON 行协议管道）。误把 ffmpeg 接到 sidecar 自己的 stdin 上会直接破坏协议。
- **`discovery.guard_mx` 是死参数**：登记在 `params.py:113-117`（默认 1，范围 1–8 秒），但全仓只有这一处出现，没有任何读取点。Device Guard 自己用的是模块常量 `SSDP_MX = 1`（`security/guard.py:37`）。改这个参数不会有任何效果。
