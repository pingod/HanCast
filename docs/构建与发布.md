## 1. 版本号 SSOT

### 1.1 真源

真源是 **`package.json` 的 `version` 字段**（`package.json:4`，当前 `2.3.9`）。
`scripts/sync-version.cjs:4` 的文档串明写「以 package.json 为单一真相源（SSOT）」，`:17-19` 读它，`:22` 把命令行参数当目标版本、缺省时回落成 `package.json` 的当前值。

> ⚠️ `scripts/check-version.cjs:3,12-13` 自称「以 `src-tauri/tauri.conf.json` 为 source of truth」，与 `sync-version.cjs` 的口径**相反**。该脚本在 `build.yml`、`package.json` 的 scripts、`windows-build.ps1`、`test-all.sh/.bat` 里都没有被引用（全仓 grep 仅命中它自身），属于**未接线的孤儿脚本**。判定 CI 行为时以 `sync-version.cjs` 为准。

### 1.2 `npm run version:set <ver>` 刷进哪些文件

`package.json:14` → `node scripts/sync-version.cjs`（带参数）。带参数时先把新版本写回 `package.json`（`sync-version.cjs:29-33`），再逐个刷下面 7 处契约点（`sync-version.cjs:40-121` 的 `targets` 表）：

| # | 文件 | 匹配形状 | 证据 |
|---|------|----------|------|
| 0 | `package.json` | `"version"` | `sync-version.cjs:29-33` |
| 1 | `src-tauri/tauri.conf.json` | `"version": "x.y.z"` | `sync-version.cjs:41-48`；实值 `tauri.conf.json:4` |
| 2 | `src-tauri/Cargo.toml` | 行首 `version = "x.y.z"` | `sync-version.cjs:49-56`；实值 `Cargo.toml:4` |
| 3 | `src-tauri/Cargo.lock` | `name = "HanCast"` 紧跟的 `version = "x.y.z"` | `sync-version.cjs:57-68`；实值 `Cargo.lock:7` |
| 4 | `hancast-backend/pyproject.toml` | 行首 `version = "x.y.z"` | `sync-version.cjs:69-76`；实值 `pyproject.toml:8` |
| 5 | `hancast-backend/hancast_sidecar/utils/config.py` | `self.version = "x.y.z"` | `sync-version.cjs:77-84`；实值 `config.py:39` |
| 6 | `src/api/commands.ts` | `MOCK_SETTINGS.version` + mock `check_update` 的 `current` / `latest` | `sync-version.cjs:85-112` |
| 7 | `src/stores/settings.ts` | `version: 'x.y.z'` | `sync-version.cjs:113-120` |

第 6 项有个刻意收窄的正则（`sync-version.cjs:88-107`）：**只**改 `MOCK_SETTINGS` 里的 `version`，不再用全局 `/version:\s*'x\.y\.z'/g`。原因是全局正则会把同文件里 dev 假索引的**规则包版本**一起刷成应用版本，两条假索引项变成同版本，设置页「一条可更新」当场失效（`sync-version.cjs:90-92` 注释；提交 `9227adf`）。

`src-tauri/Cargo.lock` 自 v2.3.8 起也是契约点（第 3 项）。此前这里的说法是「cargo 在构建时自己跟着 `Cargo.toml` 更新」——
它只在**构建**这一侧成立：CI 跑 `tauri build` 没带 `--locked`，lock 与 manifest 不一致时 cargo 只是**悄悄重写自己内存里的 lock**，
仓库那份照旧滞后，所以历史上每一版都要人肉补 `Cargo.lock` 那一行（v2.3.5/6/7 三次的发布提交都各补了一次，
`git show <tag>:src-tauri/Cargo.lock` 可验），而 v2.3.8 首发提交就漏了。收进契约点后，漏补会被
`version:set` / 无参数同步当场改写，滞后于 `package.json` 也会被闸门 A 拦下。
同一处的第二课是**行尾**：那条正则必须写成 `\r?\n`。Windows runner 上 `actions/checkout` 把文本刷成 CRLF，
写死 `\n` 时 `read`/`replace` 双双落空，`expect` 闸门当场判「脚本正则已失效」——v2.3.8 的 `windows-x64`
就是在 `prebuild` 炸掉、连带 `Upload to draft Release` 被 skip（macOS/Linux 检出是 LF，所以只有那边红）。
闸门这次的表现是**正好的**：宁可 CI 毫秒级失败，也不要安静发一版没人知道装的是哪版。

### 1.3 `prebuild` 钩子何时触发

`package.json:15` 定义 `"prebuild": "node scripts/sync-version.cjs"`（**无参数**）。npm 的 `pre<script>` 约定使它在 `npm run build`（`package.json:8` = `vue-tsc && vite build`）之前自动执行。

触发点一共两处，都是无参数模式：

1. `npm run build` → npm 先跑 `prebuild`。CI 的 `Build frontend` 步骤（`build.yml:243-244`）走这条。
2. `tauri build` / `tauri dev` → `src-tauri/tauri.conf.json:9` 的 `beforeBuildCommand` 就是 `node scripts/sync-version.cjs`。

### 1.4 CI 里的版本闸门

**闸门 A：版本 SSOT 滞后闸门**（`sync-version.cjs:123-153`，出自提交 `47acc76`）

仅在**无参数**模式下生效（`sync-version.cjs:130`）。逻辑：

1. `cmpVer`（`:131-138`）逐段数字比较，缺段按 0。
2. 遍历 `targets`，用每个条目自己的 `read()` 读回该处**当前写着**的版本（`:140-145`）。
3. 任何一处 `cmpVer(cur, newVersion) > 0`（即比 `package.json` **新**）就收进 `ahead`。
4. `ahead` 非空 → 打印「package.json 是 X，但这些契约点已经写着更高的版本」+ 提示跑 `npm run version:set <x.y.z>` → `process.exit(1)`（`:146-152`）。

设计意图（`:124-129` 注释）：无参数模式下任何一处比 SSOT 新，唯一解释就是发布时漏 bump 了 `package.json`。v2.3.3 就是这么毁的——tag 里 `package.json` 停在 2.3.2、其余 6 处已写对 2.3.3，钩子忠实地把旧版本刷回全部契约点，产物 `Info.plist` 的 `CFBundleShortVersionString` 变成 2.3.2，Windows 连文件名都露出来（`HanCast_2.3.2_x64-setup.exe`），只有 workflow 按 tag ref 拼的 artifact 名是对的。让它毫秒级炸掉，好过安静地发一版自报错误版本的包。

**闸门 B：契约点漏匹配闸门**（`sync-version.cjs:67, 109-111, 176-181`）

`targets` 条目可声明 `expect(content)`。替换写回后重新读文件，若 `expect` 不成立说明这一处根本没被正则覆盖到（字段改名/挪位置），`missed++`；`missed > 0` 则 `exit(1)`（`:184-187`）。声明了 `expect` 的有两处：`src/api/commands.ts`（`:109-111`，契约是「`MOCK_SETTINGS` 里有 `version: '…'` 且存在 `current: '…',`」）与 `src-tauri/Cargo.lock`（`:67`，契约是「lock 里存在 `name = "HanCast"` 紧跟 `version = '…'` 那一条」——cargo 若哪天不再把本地包写进 lock，这一处会先炸，而不是静默漏改）。注释原话：「漏了就是漏了，别用『已是最新』蒙过去」。

**闸门 C：CI 侧的版本解析兜底**（`build.yml:214-236` 步骤 `Resolve version`；`build.yml:609-633` job `read_version` 是同一份逻辑的副本）

```bash
if [ "${GITHUB_REF_TYPE}" = "tag" ]; then
  ver="${GITHUB_REF_NAME#v}"          # 只有 tag 才把 ref 当版本号
else
  ver=$(node -e "console.log(require('./package.json').version)" 2>/dev/null || echo 0.0.0)
fi
case "$ver" in
  ''|main|master|HEAD|dev|undefined|null) echo "::error::…"; exit 1 ;;
esac
```

分支推送绝不能用分支名当版本，否则会产出 `vmain` 这种荒谬版本号（`build.yml:247-248` 注释）。解析结果写进 `$GITHUB_ENV` 的 `VERSION`，供 artifact 名与 dmg 文件名使用。

**`check-version.cjs` 的判定逻辑**（未在 CI 中运行，仅供本地手动排查）：以 `src-tauri/tauri.conf.json` 的 `version` 为期望值（`:12-13`），只比 3 个文件——`package.json`、`src-tauri/Cargo.toml`、`hancast-backend/pyproject.toml`（`:15-19`）；任一不等打印 `MISMATCH`（`:26`），最后 `exit(1)`（`:33-36`）。它**不检查** `config.py`、`commands.ts`、`settings.ts`，覆盖面比 `sync-version.cjs` 的 7 处窄。

### 1.5 Sidecar 自报版本在哪

`hancast-backend/hancast_sidecar/utils/config.py:39` 的 `self.version = "2.3.9"`，由 `sync-version.cjs:77-84` 维护。它经 `config.py:99` 进 `get_settings()` 的返回体、经 `config.py:137-139` 的 `get_version()` 对外暴露，最终出现在 UPnP 的 `SERVER` / `modelNumber` 与 config dump 里。

产物级判据：`tools/accept-macos-artifact.sh:200-201` 从**装好的 .app** 里 grep 这一行并 `chk "sidecar 自报版本"`。注释（`:198-199`）记着 v2.2.19 曾漏改这一处，导致真机上的「版本号」不再能证明装的是哪版。

### 2.2 `npm run tauri dev` 与 `npm run tauri build` 的差别

| | `npm run tauri dev` | `npm run tauri build` |
|---|---|---|
| 前端 | `beforeDevCommand: npm run dev`（Vite dev server），`devUrl: http://localhost:1420`（`tauri.conf.json:7-8`） | `beforeBuildCommand: node scripts/sync-version.cjs`（`tauri.conf.json:9`），前端**静态**来自 `frontendDist: ../dist`（`tauri.conf.json:10`） |
| Sidecar | `#[cfg(debug_assertions)]` 分支：`uv run python -m hancast_sidecar.main`，cwd = `hancast-backend/`（`src-tauri/src/sidecar.rs:160-172`） | `#[cfg(not(debug_assertions))]` 分支：在 `resource_dir` 与 `current_exe().parent()` 里模糊查找 `hancast-sidecar*` 并 spawn，cwd = `resource_dir`（`sidecar.rs:174-212`） |
| 需要 Nuitka 产物 | 不需要 | **需要** |
| 需要 mpv 在 `src-tauri/` 下 | 不需要 | **需要**（否则 glob 落空，`build.rs` 直接失败）；FFmpeg 自 v2.3.11 起**不随包**，见 §3.3 |

关键坑：`beforeBuildCommand` **只做版本同步**，既不构建前端也不构建 sidecar。CI 因此把它拆成独立步骤（`build.yml:238-284`），本地也必须照抄这个顺序：

```bash
npm ci                                # 或 npm install
npm run build                         # 触发 prebuild → sync-version；产出 dist/
node scripts/sync-sidecar.cjs         # hancast-backend/hancast_sidecar → src-tauri/hancast_sidecar
npm run build:sidecar                 # Nuitka；win/mac 产出 src-tauri/hancast-sidecar/，Linux 产出
#                                       src-tauri/target/sidecar-dist/；两种情况都把依赖 flatten 到 src-tauri/ 根
#                                       （Linux 连 sidecar exe 一起，见 §2.3）
(cd linux-capture && cargo build --release --locked) &&   # 仅 Linux（v2.3.19）：Wayland 抓屏 helper
cp linux-capture/target/release/hancast-wlgrab src-tauri/hancast-wlgrab
node scripts/check-resources.cjs      # Preflight：逐个 glob 校验（Linux 还查 helper 的存在与执行位）
npx tauri build --bundles <targets>   # 见 §4.2 的三平台 targets
```

> ⚠️ Linux 少构建 helper 不会让 `tauri build` 报含糊的 glob 错——Preflight 的
> `checkLinuxWlgrab`（§3.3）会点名「先构建它：cd linux-capture && cargo build --release --locked」。
> 装到真机上的表现是**投屏按钮报「Wayland 屏幕抓取不可用」并给出原因**（`capture.py:81-107` 明确
> 拒绝退回 x11grab——那条无声黑屏正是 v2.3.18 的用户报告，见 §6.8）。
>
> ⚠️ 这条 `cargo build` **只能在 Linux 上跑**：`main.rs:328` 用 `libc::MFD_CLOEXEC` 建共享内存，
> macOS 侧编译直接 `E0425`（`linux-capture/target/` 已被 `.gitignore:78` 忽略，本机没有产物是正常的）。
> 本机要验编译，用交叉目录或 CI；不要在 mac 上为它加 `#[cfg]` 兜底。

> ⚠️ `windows-build.ps1:320-327` 的 Step 5 只**回显**「前端 npm run build」，实际执行的只有 `cargo tauri build` 一行。由于 `beforeBuildCommand` 不含前端构建，这条脚本会拿**上一次遗留的 `dist/`** 打包。用它之前请先手动 `npm run build`。

### 2.3 Python Sidecar 的 Nuitka 打包

命令：`npm run build:sidecar`（`package.json:11`）= `cd hancast-backend && uv sync --all-extras && uv run python scripts/build_sidecar.py`。`uv sync --all-extras` 会带上 `[project.optional-dependencies].dev` 里的 `nuitka>=2.0`、`ordered-set`、`zstandard`（`pyproject.toml:41`）。

Nuitka 参数（`build_sidecar.py:345-368`）：

```
--standalone
--output-filename=hancast-sidecar-<target-triple>
--output-dir=hancast-backend/build
--include-data-dir=<...>/hancast_sidecar/xml=hancast_sidecar/xml
--include-package=hancast_sidecar
--include-package=lxml
--include-package=netifaces

--include-package=curl_cffi      # JA3 指纹伪造（utils/httpclient.py）
--include-module=_cffi_backend   # curl_cffi import 时点名要，缺了就静默退回 requests
--nofollow-import-to=tkinter,unittest,test,distutils,setuptools,pip,_pytest,pytest
```

Windows 追加（`build_sidecar.py:374-383`）：`--include-package=pyaudiowpatch`、`--include-module=_portaudiowpatch`、`--windows-icon-from-ico=<src-tauri/icons/icon.ico>`。`_portaudiowpatch` 只在 `try/except` 里被 import，不点名的话打出来的包就没有 WASAPI 环回能力，表现为界面上「系统声音」永远选不到设备（`:370-373` 注释）。

target triple 由 `get_target_triple()` 按 `platform.system()/machine()` 推（`build_sidecar.py:10-28`），与 Tauri `externalBin` 的命名约定一致。

**产物位置与后处理**：

| 阶段 | 路径 | 证据 |
|------|------|------|
| Nuitka 原始输出 | `hancast-backend/build/main.dist/` | `build_sidecar.py:334-335` |
| move 之后 | Windows/macOS：`src-tauri/hancast-sidecar/`；**Linux：`src-tauri/target/sidecar-dist/`**（都是 `hancast-sidecar-<triple>[.exe]` + 依赖） | `:300-304, 398-403` |
| 临时目录清理 | 删 `hancast-backend/build/` | `:406` |
| 冲突清理 | 删产物里的 `types/`（与 Python 内置 `types` 模块冲突） | `:409-412` |
| 依赖提升 | `flatten_dependencies()`：产物目录里除可执行文件外的所有条目 → `src-tauri/` 根；**Linux 连 exe 一起提升**（落地名去掉 triple，成 `src-tauri/hancast-sidecar`） | `:53-136`（exe 段 `:122-135`）、调用点 `:324-325, 434-435` |
| macOS dylib 修路 | `fix_macos_dylib_paths()`：`libpython*.dylib` 的 install name 改 `@rpath/…`，可执行文件补 `@loader_path` 与 `@loader_path/../Resources` 两条 rpath | `:138-256` |
| 图标 | `copy_icon()`：仓库根 `png/HanCast-air.png` → `src-tauri/icons/icon.png` 与 `128x128@2x.png` | `:31-49, 431` |

已存在产物时**默认跳过重建**（只重跑 `flatten_dependencies`），必须 `--force` 才真编译（`build_sidecar.py:315-326, 438-440`）。

**Linux 为什么要改产出目录、还要把 exe 也提升**：Nuitka `--standalone` 只从**可执行文件所在目录**解析运行时——
`libpython3.12.so.1.0` 走 `DT_NEEDED` + RPATH `$ORIGIN`，`lxml/etree.so` 这类扩展模块走 Python 层按 exe 同级
拼出来的绝对路径（不是 soname 查表，`LD_LIBRARY_PATH`／RPATH 都救不回来）。而 Tauri 的 Linux bundler 把
`externalBin` 装 `/usr/bin`、`resources` 装 `/usr/lib/HanCast`，两者被拆层 → sidecar `exit 127`。
v2.3.16 的 deb/rpm/Arch 包就是这么打出来的：CI 四条装端检查全绿，装到 CachyOS 上双击即崩。
修法是把 exe 和依赖放在同一层：`tauri.linux.conf.json` 用 `resources: ["hancast-sidecar", ...]` 承载 exe、
`externalBin` 置空，`src-tauri/hancast-sidecar` 这个名字因此让给文件（`target/sidecar-dist/` 是给 dist 目录用的，
文件系统里同名文件与目录不能共存）。Rust 侧不用改：`find_sidecar_binary` 前缀匹配 + 执行位校验 + resource_dir 优先
（`sidecar.rs:44-129`）本来就吃得下这个布局。代价是 Linux 不再有 `/usr/bin/hancast-sidecar` 这个命令名，
Preflight、CI 冒烟与 Arch 容器验收都按新路径断言，并且**硬失败**如果 `/usr/bin/hancast-sidecar` 重新出现。

macOS 那段 dylib 改写不是可选装饰：Nuitka 产出用 `@executable_path/libpython3.12.dylib` 引用运行时，而 Tauri 把 `externalBin` 放 `Contents/MacOS/`、把 `resources` 放 `Contents/Resources/`，`@executable_path` 于是指向错目录，dyld 报 `Library not loaded` → sidecar 进程直接退出 → 用户看到的是「发现不了设备」（`build_sidecar.py:141-161` 注释）。`@loader_path` 单用不行，只有 `@rpath` + rpath 才有多目录回退能力（`:160-161`）。Linux 上同一个坑没有 rpath 可修（soname 查表救不了 Python 层拼出来的绝对路径），所以只能让 exe 与依赖同级，见上一节。

### 2.4 为什么直接跑 `hancast.exe` 会闪退

`README.md:143` 记了这条现象，根因在壳层的启动链路：

1. release 构建走 `#[cfg(not(debug_assertions))]` 分支（`src-tauri/src/sidecar.rs:25` 起的 `find_sidecar_binary`，spawn 在 `:174-212`）。
2. 它只在 `resource_dir` 和 `current_exe().parent()` 两个目录里找 `hancast-sidecar*`（`sidecar.rs:186-196`）。
3. 找不到就返回 `Err`，错误文本里带各目录实际内容（`sidecar.rs:127`）。
4. `lib.rs` 的 `setup` 用 `?` 直接把这个 Err 抛出去（`src-tauri/src/lib.rs:1147-1151`），Tauri 随即退出。

`lib.rs:1160-1161` 的注释原话：「这里失败会让 setup 返回 Err，Tauri 随即退出，表现为『窗口一闪就退』。所以失败时必须把原因打出来，否则用户只看到闪退、无从排查。」失败时会 `eprintln!("[FATAL] Failed to start sidecar, aborting startup: {e}")`。

`src-tauri/target/release/HanCast.exe` 旁边没有 sidecar、没有 `*.dll`/`*.pyd`、没有 `mpv/`、没有 `hancast_sidecar/`，所以必崩。同一份代码在 dev 下不崩，是因为 `#[cfg(debug_assertions)]` 分支改走 `uv run python -m hancast_sidecar.main`（`sidecar.rs:160-172`）。

macOS 上还有第二层：即使 sidecar 找到了，`Contents/MacOS/` 与 `Contents/Resources/` 的分裂会让 Nuitka 的 loader 报 `ImportError: dlopen(.../Contents/MacOS/lxml/etree.so)`——Nuitka `--standalone` 只从「可执行文件所在目录」解析模块，`sys.path` / `PYTHONPATH` 都不生效。CI 的修法是给 `Resources/` 的每一项在 `MacOS/` 建同名符号链接（`build.yml:354-419`）。

### 2.5 仓库根 `portable_config` 的拷入要求（提交 `9450a36`）

两套 `mpv/` 目录，别搞混：

| 位置 | 是否入库 | 作用 |
|------|----------|------|
| 仓库根 `mpv/` | 只有 `mpv/portable_config/` 入库 | `.gitignore:86-87` = `mpv/*` + `!mpv/portable_config/`；二进制/动态库约 120MB 不提交 |
| `src-tauri/mpv/` | 不入库 | `bundle.resources` 的 glob 相对 `src-tauri/` 解析（`tauri.conf.json:47-52`），所以打包用的必须是这一份 |

结论：**每次构建前都要把仓库根的 `mpv/portable_config/` 拷进 `src-tauri/mpv/portable_config/`**，否则 `mpv/portable_config/**/*` 一个文件都匹配不到，`build.rs` 直接失败。

- CI（macOS / Windows）：`build.yml:158-161`
- CI（Linux）：`build.yml:202-205`
- 本地 Windows：`windows-build.ps1:296-302`（`Copy-Item "mpv" -Destination "src-tauri\mpv" -Recurse -Force`，整目录拷，顺带带上 `portable_config`）

提交 `9450a36`（`docs: 记录 tauri glob 语义、release 闸门、仓库根 portable_config 拷入要求`）就是把这条写进文档的那次。

### 2.6 Tauri `resources` 的 glob 语义坑

`scripts/check-resources.cjs:11-22` 复刻了 `tauri-utils-2.10.1/src/resources.rs` 的三条语义：

1. **glob 不递归**：`glob::glob("mpv/*")` 只列 `mpv/` 的直接子项，即使 `require_literal_separator=false`，`*` 也不跨目录层级。要递归必须显式写 `**`。
2. **命中目录会被静默丢弃**（上游 crate tauri-utils 的 `resources.rs` L195 `if entry.is_dir() { skip }`，不在本仓），不报错、不递归。
3. 因此 `GlobPathNotFound` 的触发条件是「一个**文件**都没匹配到」，而不是「一个路径都没匹配到」——只匹配到目录同样构建失败。

第 2 条咬过人：macOS 的 `mpv/*` 看得见 `mpv.app/`，但它是目录，被丢弃，app 打出来没有 mpv，反倒把一起拷进去的 `mpv.tar.gz` 打进了 bundle。修法是 `tauri.macos.conf.json:7` 显式写 `mpv/mpv.app/**/*`，且 CI 解完嵌套 tarball 后立刻删掉它（`build.yml:143-149`）。

另外两条约束：

- **动态库 glob 必须是顶层**（`*.so` 而非 `**/*.so`），否则会把 `src-tauri/target/` 下整个 Rust 构建产物打进安装包。见 `tauri.macos.conf.json:10-11`、`tauri.windows.conf.json:7-8`、`tauri.linux.conf.json:7-8`。
- **平台配置合并是整体替换**：Tauri 用 `json_patch::merge`（RFC 7386 JSON Merge Patch），数组不做逐元素合并（`check-resources.cjs:44` 注释）。所以每个 `tauri.<platform>.conf.json` 必须写出**完整**的 `bundle.resources` 数组，不能只写增量。

### 3.3 `check-resources.cjs` 检查了什么

`node scripts/check-resources.cjs`，可用 `TAURI_PLATFORM=win32|linux|darwin` 覆盖当前平台（`check-resources.cjs:25,31`）。CI 里它是 `Preflight: verify bundle.resources globs` 步骤（`build.yml:281-282`），**必须跑在 sidecar 构建之后、`tauri build` 之前**——`hancast_sidecar/**/*` 与 `*.so`/`*.dll`/`*.pyd` 都是 Nuitka 的产物，在此之前根本不存在。

流程（`check-resources.cjs:253-318`）：

1. 按平台解析 resources：overlay 文件里有 `bundle.resources` 就**整体替换** base 的数组，不做合并（`:33-55`）。打印 `platform` / `resources source` / `resources count`（`:255-257`）。
2. 逐个 glob 用复刻语义遍历（`segToRegExp` 把 `*` 编成 `[^/]*`，`:57-61`；`walk` 处理 `**` 可匹配 0 层，`:79-101`），把命中项分成 `files` 与 `dirs`（`:103-111`）。
3. `files.length === 0` → `MISSING`，附原因（`only N dir(s), no file` 或 `0 matches`），`failed++`（`:267-272`）。
4. 命中了目录、但该目录下一个文件都不会进 bundle → `warn`，并直接给出修法建议：把 `X/*` 换成 `X/**/*`（`:288-297`）。
5. 打印 `total files that will be bundled`（`:300`）。
6. **二进制包目录对账**（`checkBinaryPackages`，`:143-166`，v2.3.8 起）：`includePackages()`（`:134-141`）从 `hancast-backend/scripts/build_sidecar.py` 里读出每条 `--include-package=X`，逐个查 `X/**/*` 在 `src-tauri/` 的实际命中数——产出里有该目录、白名单却没列它，就 `MISSING` 并计入失败（`:157-161`）。这一条专为 v2.3.7 的坑而装：`curl_cffi/` 没进白名单时，顶层 `*.so` 抓不到目录里的 `_wrapper.abi3.so`，产物 import 失败后按设计静默降级回 `requests`，**构建照样成功、日志一句错都不报**，只有对账能发现。目录形态不存在（纯 Python 被编进可执行文件）则判 `ok`，不算失败。
7. **Linux 布局判据**（v2.3.17 起）：`checkLinuxSidecarLayout`（`:179-215`）断言 `src-tauri/hancast-sidecar` 是**带执行位的文件**、`resources` 里列了它、且 `tauri.linux.conf.json` 的 `bundle.externalBin` 是**空数组**——非空就会在 `/usr/bin` 再放一份与依赖拆开的 sidecar，装端启动即 `exit 127`。
8. **Linux Wayland helper 判据**（v2.3.19 起）：`checkLinuxWlgrab`（`:223-251`，注释 `:217-222`）对 `src-tauri/hancast-wlgrab` 做同样三件事（存在 / 是文件不是目录 / 带执行位），并断言 `resources` 列出 `hancast-wlgrab`。它的理由与 #7 同源，但抓的是另一处：glob 数量看不出「helper 没在同一层」，而 `screencast/wlgrab.py` 的 `_candidate_paths` 只探「sidecar exe 同级 / resource_dir / 包的上一级」，探不到就让 `capture.py:81-107` 直接失败并把原因回给前端（**不退回 x11grab**——退回等于把 v2.3.18 的无声黑屏再发一遍，见 §6.8）。失败文案直接点名「先构建它：`cd linux-capture && cargo build --release --locked`」。
9. `failed > 0 || pkgFailed > 0 || layoutFailed > 0 || wlgrabFailed > 0` → dump `src-tauri/` 顶层清单与 Nuitka dist 清单（各最多 50 条），`exit(1)`（`:309-317`）。

存在的意义（`:5-9` 注释）：`tauri-build` 对任何含 `*` 的 glob，匹配为空就直接失败并报 `glob pattern <pattern> path not found or didn't match any files.`，而且**在第一个失败的 glob 处中断**，后续 glob 从不被校验，排查成本极高。Preflight 把它变成一次性、精确、带实际清单的诊断。

### 3.4 bundle 阶段还有一道「npm ↔ Rust 版本配对」闸门（v2.3.21 实测）

`tauri build` 在真正打包之前会比对 **npm 侧 `@tauri-apps/*` 与 Rust 侧 `tauri*` 的主次版本**，不一致就三平台一起失败，
报的是 `Error Found version mismatched Tauri packages. Make sure the NPM package and Rust crate versions are on the same major/minor releases:`，
下面逐行列出成对的包与版本（v2.3.21 第一次的 tag run 就是这两行：`tauri (v2.11.5) : @tauri-apps/api (v2.12.4)`、`tauri-plugin-notification (v2.4.0) : @tauri-apps/plugin-notification (v2.7.0)`）。

**本机三条命令全都不会报这件事**——`cargo check`、`vue-tsc`、`vite build` 各自只看自己那一侧，只有 `tauri build` 的这一步会拦，
所以它天然是「推上去才知道」的失败。真正说了算的是两把锁：`package-lock.json`（CI 用 `npm ci`，`build.yml:124`）与 `src-tauri/Cargo.lock`。

**它容易被一次“只是加个插件”的改动撞开**：npm 侧的 `@tauri-apps/plugin-*` 把 `@tauri-apps/api` 写成运行时依赖，
`plugin-notification@2.7.0` 要求 `api ^2.12.0`，于是宽范围 `"@tauri-apps/api": "^2.0.0"` 会在水合时飘到 2.12.4，而 Cargo.lock 里的 `tauri` 还是 2.11.5。
v2.3.21 的处置是把 npm 侧收成 `~2.11.1`（api）与 `~2.4.0`（通知插件），Rust 侧写 `tauri-plugin-notification = "2.4"`，**两边成对改**；
要升就一起升（`tauri` crate 到 2.12.x + api 到 2.12.x + 插件到 2.7.x），单改一边照样失败。

### 4.4 签名情况

| 平台 | 签名 | 细节 |
|------|------|------|
| macOS | **adhoc 深签**（`codesign --force --deep --sign -`） | `build.yml:429-450`，出自提交 `c983c4e`（v2.2.14）。必须在**打 dmg 之前**签：签完再动 bundle 会让签名失效（`:428`）。dmg 挂载后再断一次 Identifier（`:485-489`） |
| Windows | 无 | 用户可能遇到 SmartScreen 提示 |
| Linux | 无 | — |

macOS 为什么非签不可（`build.yml:421-428` 与 `src-tauri/Info.plist:5-20` 注释）：macOS 15+ 的「本地网络」权限按**代码身份**判定。Tauri 不签名时主程序留下的是 Rust 链接器写的 adhoc 签名，Identifier 形如 `HanCast-<16位hex>`、flags `0x20002(adhoc,linker-signed)`——同一个 bundle id 每次构建换一个身份，NetworkAgent 认不出它就**静默拒绝组播**（`sendto 239.255.255.250` → `Errno 65`），连弹窗都没有、`TCC.db` 里也不留记录。2026-10-13 同一台机器、同一份字节 A/B：产物原样 → 心跳「通道 broadcast」；重签 → 「通道 multicast」(24 条) + 入站 200。

所以 `Info.plist` 的两条声明（`NSLocalNetworkUsageDescription`、`NSBonjourServices=["_upnp._tcp"]`）+ **稳定签名身份**三者缺一不可（`Info.plist:9-19`）。`Info.plist` 经 `tauri.macos.conf.json:3-5` 的 `bundle.macOS.infoPlist` 接入，且必须纳入版本控制——CI 从仓库构建，本地未跟踪的副本不会进产物（`Info.plist:20`）。

> ⚠️ `build.yml:7` 的头注释仍写着「不执行代码签名」，与 `:429-450` 的实际步骤矛盾，属**过时注释**。

### 4.5 Release 怎么创建

`release` job（`build.yml:635-692`）：

```yaml
needs: [build, read_version]
if: >
  needs.build.result == 'success' &&
  github.ref_type == 'tag' &&
  ( github.event_name == 'push' || inputs.make_release == true )
```

三个条件缺一不可（`:638-641`）。`make_release` 默认 false，所以在 `main` 上手动 dispatch 只构建、不发布——曾经用 `refs/heads/main` 当 tag 发 Release，被 GitHub API 400 拒掉（`AGENTS.md:405-407` 记录了这段历史）。

步骤：

| 步骤 | 行号 | 作用 |
|------|------|------|
| `Checkout this tag` | `:648-649` | 检出**被测 tag** 的工作区，规则包 zip 直接从这里取 |
| `Check rule-pack assets match the index` | `:651-653` | `python3 tools/build-rule-packs.py --check`；产物或索引与源不一致就非 0 退出 |
| `Stage rule-pack zips for the release` | `:655-660` | `cp rule-packs/dist/*.zip artifacts/rule-packs/` |
| `Download all build artifacts` | `:662-670` | `pattern: bundle-*`、`path: artifacts`、`merge-multiple: true` |
| `List downloaded artifacts` | `:672-675` | `find artifacts -type f` |
| `Publish draft release` | `:677-692` | `softprops/action-gh-release@v2`，`draft: true`、`generate_release_notes: true` |

上传的文件 glob（`:682-692`）：`artifacts/**/*.dmg`、`*.app`、`*.app.tar.gz`、`*.exe`、`*.msi`、`*.deb`、`*.rpm`、`*.AppImage`、**`*.pkg.tar.zst`**，以及 **`artifacts/rule-packs/*.zip`**。

**规则包 zip 随 Release 发布**出自提交 `356f6eb`。理由（`:644-647` 注释）：索引里的 sha256 必须和 Release 上的字节逐位一致，否则用户装包会被摘要校验拦下；zip 用固定时间戳（1980-01-01）与固定条目顺序生成（`tools/build-rule-packs.py:13-14, 40, 95-106`），所以从 tag 工作区直接上传的字节和重跑脚本的字节相同，不需要另建一条产线。

**Release 是 draft**：这是刻意的闸门。CI 出包 → 人工装 draft 里的产物跑验收（§6）→ 通过后才在 GitHub 上把它 publish 成正式 Release。

## 5. 发布流程 runbook

从改代码到用户能下载的完整顺序：

```bash
# ── 0. 源码级 / 真机级验收（必须在打 tag 之前做完）──
cd hancast-backend && uv run pytest                       # 后端单测
npx vue-tsc --noEmit                                      # 前端类型
hancast-backend/.venv/bin/python tools/verify-rule-packs-live.py "<链接>"
python3 tools/ssdp_probe.py                               # 真机链路，按需
# …按本轮改动挑 tools/ 里对应的脚本，见 tools/README.md

# ── 1. bump 版本（唯一入口，别手改各文件）──
npm run version:set 2.3.6
npm run version:sync        # 复核：打印当前版本并再同步一次
node scripts/check-version.cjs   # 可选：三处粗校验（未接入 CI）

# ── 2. 复核规则包产物与索引一致（改了 rule-packs/ 才需要重建）──
python3 tools/build-rule-packs.py --check
python3 tools/build-rule-packs.py            # 仅当 --check 失败时

# ── 3. 提交 ──
git add -A && git commit -m "chore(release): v2.3.6（…）"

# ── 4. 打 tag（tag 一推 CI 就开始产包，所以第 0 步必须已完成）──
git tag v2.3.6

# ── 5. push（分支 + tag）──
git push origin HEAD:main
git push origin v2.3.6

# ── 6. 看 CI ──
gh run watch                       # 或 gh run list --workflow=build.yml
gh run view <run-id> --log-failed  # 失败时

# ── 7. 产物验收（draft Release / artifact 到手后）──
gh release download v2.3.6 --pattern '*.dmg' --dir /tmp
tools/install-macos-artifact.sh 2.3.6 /tmp/HanCast_2.3.6_aarch64.dmg
tools/accept-macos-artifact.sh 2.3.6

# ── 8. 全部 PASS 才 publish ──
gh release edit v2.3.6 --draft=false
```

**项目纪律：验收必须在打 tag 之前做完。**
tag 一推，CI 立刻产包并建 draft Release；此时才发现代码有问题，就得再 bump 一版重打 tag，版本号白白烧掉一个。因此第 0 步（源码级 + 真机级）是 tag 前的闸门，第 7 步（产物级）是 publish 前的闸门——两道都不能省。

**第二道纪律：禁止手工补丁冒充验收。** 出自提交 `76bba31`（`chore(tools): 打包产物验收脚本，禁止手工补丁冒充验收`）。`tools/accept-macos-artifact.sh:3-4` 的原话：「验收 **CI 产物本身**：全程 CLI，不碰 UI 坐标，禁止任何手工补丁（重装/重签都不许）。每轮装完包都跑一遍；任一项 FAIL 就说明这版产物不能用，别拿本地补丁版冒充。」`tools/install-macos-artifact.sh:5-6` 同样写着「装的是 CI 产物本身，不做任何补丁（重签/替换文件都不许）」。

这条纪律有血的教训：v2.2.13 就是靠这套检查（14 项）才发现「plist 齐全但组播仍被拒」，而当时的**本地重签把现场掩盖了**（`76bba31` 提交说明）。同理，`tools/pull-rule-packs-installed.py:5-8` 也写着「手改 `share_rules/plugins/` 里的文件则是拿补丁冒充验收，产物里根本没跑过 `plugin_pull`」。

## 7. 回滚与常见构建故障

### 7.1 CI 卡住/失败时看哪

按「最早失败的那个步骤」定位，`fail-fast: false`（`build.yml:42`）意味着三平台互不牵连，可以只看挂掉的那条：

```bash
gh run list --workflow=build.yml --limit 5
gh run view <run-id>                       # 看哪条矩阵、哪个步骤红了
gh run view <run-id> --log-failed          # 只看失败日志
gh run view <run-id> --job <job-id> --log  # 单矩阵项全日志
```

高频落点：

| 症状 | 先看 | 常见根因 |
|------|------|----------|
| 毫秒级失败，日志是 `❌ package.json 是 X，但这些契约点已经写着更高的版本` | `Build frontend`（`:243-244`） | 版本 SSOT 滞后闸门（§1.4 闸门 A）。跑 `npm run version:set <x.y.z>` 重新提交、重打 tag |
| `MISSING <glob> -> 0 matches` / `only N dir(s), no file` | `Preflight`（`:281-282`） | 见 §3.3；最常见是 `portable_config` 没拷、mpv 没下下来、sidecar 没构建 |
| `no usable mpv binary found under src-tauri/mpv` | `Download & unpack MPV`（`:128`） | MPV release 资产名/tag 变了，或 `api.github.com` 之外的下载被限流 |
| `helper 在无 Wayland 会话下退出码 N（应为 3）` | `Build Wayland capture helper (Linux)`（`:259-280`） | cargo 那步没产出二进制；或 helper 在 `--version` 之前就被链接失败（Linux runner 缺 `libwayland-client`，见 #6） |
| `hancast-wlgrab 没进包或没有可执行位` | deb 冒烟（`:314-315`）+ Preflight `checkLinuxWlgrab` | `tauri.linux.conf.json` 的 `bundle.resources` 少了 `hancast-wlgrab`，或本地没先构建（`linux-capture/` 产物是 gitignore 的） |
| `list_screen_sources 的返回里没有 capture 字段（wlgrab 模块没进包？）` | deb 冒烟（`:339-340`） | Nuitka 没收起 `screencast/wlgrab.py` / `screencast/pulse.py`（延迟 import，只有这条命令会暴露） |
| `sidecar did not reach 'DLNA server started'` | `Fix macOS sidecar resource layout`（`:354-428`） | dylib rpath 没改对（`build_sidecar.py:138-256`），或 Nuitka 少收了某个 `--include-package` |
| `签名 Identifier 是 'HanCast-<hex>'，主程序仍是 linker-signed` | `Adhoc sign macOS app`（`:429-450`） | 签名步骤被跳过或签名后又动了 bundle |
| `dmg 内的 .app 签名 Identifier 是 …` | `Bundle macOS dmg`（`:457-507`） | `cp`/`hdiutil` 环节把签名弄丢 |
| release job 里 `需要重建: dist/…` / `需要重建: index.json` | `Check rule-pack assets match the index`（`:651-653`） | 改了 `rule-packs/<pack>/` 却没重跑 `tools/build-rule-packs.py` |
| release job 没跑 | `release` 的 `if`（`:638-641`） | ref 不是 tag；或手动 dispatch 时没勾 `make_release` |
| Release 上传报重复文件 | `Publish draft release`（`:677-692`） | `download-artifact` 的 `pattern` 不是 `bundle-*`，把按格式拆分的 artifact 也拉了下来 |

回滚：Release 是 draft，publish 前发现问题直接删 draft + 删 tag，不影响用户。已 publish 的版本要撤回，就在 GitHub 上把 Release 改回 draft 或删掉资产，再 `git tag -d <tag> && git push origin :refs/tags/<tag>`——但更推荐直接往前发一版修复，因为规则包索引的 `url` 指向 `main` 分支的 raw 路径（`build-rule-packs.py:36-38`），历史 tag 的产物地址并不随 tag 走。

### 7.2 本地 `cargo check` 需要什么桩

### 7.3 push 被拒怎么处理

当前分支拓扑（2026-10-15）：本地工作分支是 `feat/js-rule-plugins`，远端只有 `origin` → `https://github.com/pingod/HanCast`，跟踪分支是 `origin/main`；另有本地 `main` 与 `backup/v2.2.11-amend`。

本地 `main` 落后于 `origin/main` 时，`git push origin main` 会被拒（non-fast-forward）。项目做法是**不先合并本地 main**，而是直接把当前工作分支的头推到远端 main：

```bash
git fetch origin
git push origin HEAD:main
```

这样远端 main 拿到的是工作分支上那条已经验收过的历史，本地那条陈旧的 `main` 不参与、也不需要 rebase。**不要**用 `--force`：它会覆盖别人（或另一台机器）推上去的提交。

> ⚠️ 未验证：仓库里没有任何文件写下这条 push 纪律（全仓 grep `HEAD:main` / `HEAD:master` 零命中）。上面的做法是从当前分支拓扑与「本地 main 长期落后于 origin/main」这一事实推出的操作惯例，不是成文规范。

### 7.4 Gitee 镜像同步

`push-gitee.ps1`（PowerShell，仅 Windows）：

```powershell
.\push-gitee.ps1                     # 只推
.\push-gitee.ps1 -Message "…"        # 先 git add . && git commit -m "…" 再推
```

- 镜像地址硬编码在 `push-gitee.ps1:8`：`https://gitee.com/buxiangqumingzi/han-cast.git`
- remote 名 `gitee`，不存在时自动 `git remote add`（`:11-15`）
- 带 `-Message` 时会 `git add .`（`:20`）——注意这是全量添加，别在脏工作树上用

> ⚠️ 该脚本当前**跑不通**：`:26` 执行的是 `git push gitee master`，而本地没有 `master` 分支（只有 `main`、`feat/js-rule-plugins`、`backup/v2.2.11-amend`），且当前仓库没有配置 `gitee` remote（`git remote -v` 只有 `origin`）。要用得先把 `master` 改成 `main`（或 `HEAD:master`）。

### 7.5 其它构建故障速查

| 症状 | 根因 / 处置 |
|------|-------------|
| `glob pattern … path not found or didn't match any files.` | `build.rs` 阶段的 Tauri 原生报错，第一个失败的 glob 就中断。用 `node scripts/check-resources.cjs` 拿到精确诊断（§3.3） |
| 本地构建成功但产物里没有 mpv（macOS） | `mpv/*` 命中了 `mpv.app/` 目录但目录被 Tauri 丢弃。macOS overlay 必须写 `mpv/mpv.app/**/*`（`tauri.macos.conf.json:7`） |
| bundle 体积莫名多出 ~44MB | macOS 的 mpv 资产 zip 里套着 `mpv.tar.gz`，没删就被 `cp -a` 混进了 bundle。CI 在 `build.yml:148-149` 显式删它 |
| 安装包里有整个 Rust `target/` | 动态库 glob 写成了 `**/*.so`。必须是顶层 `*.so`（§2.6） |
| 平台 overlay 加了新 glob，另一个平台构建挂了 | Tauri 的平台合并是数组整体替换，每个 overlay 必须写**完整**数组（§2.6） |
| sidecar 明明构建过了却仍在重建 / 或明明改了代码却没重建 | `build_sidecar.py:315-326`：产物已存在则跳过，只有 `--force` 才真编译。本地改完后直接 `uv run python scripts/build_sidecar.py --force`（要手工清就删产物目录：Windows/macOS 是 `src-tauri/hancast-sidecar/`，Linux 是 `src-tauri/target/sidecar-dist/` **加** 提升到根的那批 `src-tauri/*` 与 `src-tauri/hancast-sidecar` 文件） |
| Windows 装完「系统声音」选不到设备 | Nuitka 漏了 `--include-package=pyaudiowpatch` / `--include-module=_portaudiowpatch`（`build_sidecar.py:374-378`） |
| macOS 装完「发现不了设备」，日志是 `Library not loaded: @executable_path/libpython3.12.dylib` | `fix_macos_dylib_paths()` 没跑成（缺 `install_name_tool`，`build_sidecar.py:172-174` 会打 Warning 后跳过） |
| 设置页整块读不到后台参数，命令回 `'ascii' codec can't encode characters` | 父进程没给 `LANG`/`LC_*`，Python stdout 退回 ASCII。壳层 spawn 时必须带 `PYTHONIOENCODING=utf-8`（`src-tauri/src/sidecar.rs:168, 209`）。判据脚本 `tools/verify-sidecar-utf8-protocol.py` |
| 本地 `npm run tauri build` 打出来的界面是旧的 | `beforeBuildCommand` 不含前端构建（§2.2）。先手动 `npm run build` |
