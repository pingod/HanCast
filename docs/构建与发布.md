## 1. 版本号 SSOT

### 1.1 真源

真源是 **`package.json` 的 `version` 字段**（`package.json:4`，当前 `2.3.9`）。
`scripts/sync-version.cjs:4` 的文档串明写「以 package.json 为单一真相源（SSOT）」，`:17-19` 读它，`:22` 把命令行参数当目标版本、缺省时回落成 `package.json` 的当前值。

> ⚠️ `scripts/check-version.cjs:3,12-13` 自称「以 `src-tauri/tauri.conf.json` 为 source of truth」，与 `sync-version.cjs` 的口径**相反**。该脚本在 `build.yml`、`package.json` 的 scripts、`windows-build.ps1`、`test-all.sh/.bat` 里都没有被引用（全仓 grep 仅命中它自身），属于**未接线的孤儿脚本**。判定 CI 行为时以 `sync-version.cjs` 为准。

### 1.2 `npm run version:set <ver>` 刷进哪些文件

`package.json:14` → `node scripts/sync-version.cjs`（带参数）。带参数时先把新版本写回 `package.json`（`sync-version.cjs:29-33`），再逐个刷下面 7 处契约点（`sync-version.cjs:40-121` 的 `targets` 表）：

| # | 文件 | 匹配形状 | 证据 |
|---|------|----------|------|
| 0 | `package.json` | `"version"` | `sync-version.cjs:29-33` |
| 1 | `src-tauri/tauri.conf.json` | `"version": "x.y.z"` | `sync-version.cjs:41-48`；实值 `tauri.conf.json:4` |
| 2 | `src-tauri/Cargo.toml` | 行首 `version = "x.y.z"` | `sync-version.cjs:49-56`；实值 `Cargo.toml:4` |
| 3 | `src-tauri/Cargo.lock` | `name = "HanCast"` 紧跟的 `version = "x.y.z"` | `sync-version.cjs:57-68`；实值 `Cargo.lock:7` |
| 4 | `hancast-backend/pyproject.toml` | 行首 `version = "x.y.z"` | `sync-version.cjs:69-76`；实值 `pyproject.toml:8` |
| 5 | `hancast-backend/hancast_sidecar/utils/config.py` | `self.version = "x.y.z"` | `sync-version.cjs:77-84`；实值 `config.py:39` |
| 6 | `src/api/commands.ts` | `MOCK_SETTINGS.version` + mock `check_update` 的 `current` / `latest` | `sync-version.cjs:85-112` |
| 7 | `src/stores/settings.ts` | `version: 'x.y.z'` | `sync-version.cjs:113-120` |

第 6 项有个刻意收窄的正则（`sync-version.cjs:88-107`）：**只**改 `MOCK_SETTINGS` 里的 `version`，不再用全局 `/version:\s*'x\.y\.z'/g`。原因是全局正则会把同文件里 dev 假索引的**规则包版本**一起刷成应用版本，两条假索引项变成同版本，设置页「一条可更新」当场失效（`sync-version.cjs:90-92` 注释；提交 `9227adf`）。

`src-tauri/Cargo.lock` 自 v2.3.8 起也是契约点（第 3 项）。此前这里的说法是「cargo 在构建时自己跟着 `Cargo.toml` 更新」——
它只在**构建**这一侧成立：CI 跑 `tauri build` 没带 `--locked`，lock 与 manifest 不一致时 cargo 只是**悄悄重写自己内存里的 lock**，
仓库那份照旧滞后，所以历史上每一版都要人肉补 `Cargo.lock` 那一行（v2.3.5/6/7 三次的发布提交都各补了一次，
`git show <tag>:src-tauri/Cargo.lock` 可验），而 v2.3.8 首发提交就漏了。收进契约点后，漏补会被
`version:set` / 无参数同步当场改写，滞后于 `package.json` 也会被闸门 A 拦下。
同一处的第二课是**行尾**：那条正则必须写成 `\r?\n`。Windows runner 上 `actions/checkout` 把文本刷成 CRLF，
写死 `\n` 时 `read`/`replace` 双双落空，`expect` 闸门当场判「脚本正则已失效」——v2.3.8 的 `windows-x64`
就是在 `prebuild` 炸掉、连带 `Upload to draft Release` 被 skip（macOS/Linux 检出是 LF，所以只有那边红）。
闸门这次的表现是**正好的**：宁可 CI 毫秒级失败，也不要安静发一版没人知道装的是哪版。

### 1.3 `prebuild` 钩子何时触发

`package.json:15` 定义 `"prebuild": "node scripts/sync-version.cjs"`（**无参数**）。npm 的 `pre<script>` 约定使它在 `npm run build`（`package.json:8` = `vue-tsc && vite build`）之前自动执行。

触发点一共两处，都是无参数模式：

1. `npm run build` → npm 先跑 `prebuild`。CI 的 `Build frontend` 步骤（`build.yml:271-272`）走这条。
2. `tauri build` / `tauri dev` → `src-tauri/tauri.conf.json:9` 的 `beforeBuildCommand` 就是 `node scripts/sync-version.cjs`。

### 1.4 CI 里的版本闸门

**闸门 A：版本 SSOT 滞后闸门**（`sync-version.cjs:123-153`，出自提交 `47acc76`）

仅在**无参数**模式下生效（`sync-version.cjs:130`）。逻辑：

1. `cmpVer`（`:131-138`）逐段数字比较，缺段按 0。
2. 遍历 `targets`，用每个条目自己的 `read()` 读回该处**当前写着**的版本（`:140-145`）。
3. 任何一处 `cmpVer(cur, newVersion) > 0`（即比 `package.json` **新**）就收进 `ahead`。
4. `ahead` 非空 → 打印「package.json 是 X，但这些契约点已经写着更高的版本」+ 提示跑 `npm run version:set <x.y.z>` → `process.exit(1)`（`:146-152`）。

设计意图（`:124-129` 注释）：无参数模式下任何一处比 SSOT 新，唯一解释就是发布时漏 bump 了 `package.json`。v2.3.3 就是这么毁的——tag 里 `package.json` 停在 2.3.2、其余 6 处已写对 2.3.3，钩子忠实地把旧版本刷回全部契约点，产物 `Info.plist` 的 `CFBundleShortVersionString` 变成 2.3.2，Windows 连文件名都露出来（`HanCast_2.3.2_x64-setup.exe`），只有 workflow 按 tag ref 拼的 artifact 名是对的。让它毫秒级炸掉，好过安静地发一版自报错误版本的包。

**闸门 B：契约点漏匹配闸门**（`sync-version.cjs:67, 109-111, 176-181`）

`targets` 条目可声明 `expect(content)`。替换写回后重新读文件，若 `expect` 不成立说明这一处根本没被正则覆盖到（字段改名/挪位置），`missed++`；`missed > 0` 则 `exit(1)`（`:184-187`）。声明了 `expect` 的有两处：`src/api/commands.ts`（`:109-111`，契约是「`MOCK_SETTINGS` 里有 `version: '…'` 且存在 `current: '…',`」）与 `src-tauri/Cargo.lock`（`:67`，契约是「lock 里存在 `name = "HanCast"` 紧跟 `version = '…'` 那一条」——cargo 若哪天不再把本地包写进 lock，这一处会先炸，而不是静默漏改）。注释原话：「漏了就是漏了，别用『已是最新』蒙过去」。

**闸门 C：CI 侧的版本解析兜底**（`build.yml:242-264` 步骤 `Resolve version`；`build.yml:527-551` job `read_version` 是同一份逻辑的副本）

```bash
if [ "${GITHUB_REF_TYPE}" = "tag" ]; then
  ver="${GITHUB_REF_NAME#v}"          # 只有 tag 才把 ref 当版本号
else
  ver=$(node -e "console.log(require('./package.json').version)" 2>/dev/null || echo 0.0.0)
fi
case "$ver" in
  ''|main|master|HEAD|dev|undefined|null) echo "::error::…"; exit 1 ;;
esac
```

分支推送绝不能用分支名当版本，否则会产出 `vmain` 这种荒谬版本号（`build.yml:247-248` 注释）。解析结果写进 `$GITHUB_ENV` 的 `VERSION`，供 artifact 名与 dmg 文件名使用。

**`check-version.cjs` 的判定逻辑**（未在 CI 中运行，仅供本地手动排查）：以 `src-tauri/tauri.conf.json` 的 `version` 为期望值（`:12-13`），只比 3 个文件——`package.json`、`src-tauri/Cargo.toml`、`hancast-backend/pyproject.toml`（`:15-19`）；任一不等打印 `MISMATCH`（`:26`），最后 `exit(1)`（`:33-36`）。它**不检查** `config.py`、`commands.ts`、`settings.ts`，覆盖面比 `sync-version.cjs` 的 7 处窄。

### 1.5 Sidecar 自报版本在哪

`hancast-backend/hancast_sidecar/utils/config.py:39` 的 `self.version = "2.3.9"`，由 `sync-version.cjs:77-84` 维护。它经 `config.py:99` 进 `get_settings()` 的返回体、经 `config.py:137-139` 的 `get_version()` 对外暴露，最终出现在 UPnP 的 `SERVER` / `modelNumber` 与 config dump 里。

### 2.2 `npm run tauri dev` 与 `npm run tauri build` 的差别

### 2.4 为什么直接跑 `hancast.exe` 会闪退

`README.md:143` 记了这条现象，根因在壳层的启动链路：

1. release 构建走 `#[cfg(not(debug_assertions))]` 分支（`src-tauri/src/sidecar.rs:25` 起的 `find_sidecar_binary`，spawn 在 `:174-212`）。
2. 它只在 `resource_dir` 和 `current_exe().parent()` 两个目录里找 `hancast-sidecar*`（`sidecar.rs:186-196`）。
3. 找不到就返回 `Err`，错误文本里带各目录实际内容（`sidecar.rs:127`）。
4. `lib.rs` 的 `setup` 用 `?` 直接把这个 Err 抛出去（`src-tauri/src/lib.rs:1147-1151`），Tauri 随即退出。

`lib.rs:1145-1146` 的注释原话：「这里失败会让 setup 返回 Err，Tauri 随即退出，表现为『窗口一闪就退』。所以失败时必须把原因打出来，否则用户只看到闪退、无从排查。」失败时会 `eprintln!("[FATAL] Failed to start sidecar, aborting startup: {e}")`。

`src-tauri/target/release/HanCast.exe` 旁边没有 sidecar、没有 `*.dll`/`*.pyd`、没有 `mpv/`、没有 `hancast_sidecar/`，所以必崩。同一份代码在 dev 下不崩，是因为 `#[cfg(debug_assertions)]` 分支改走 `uv run python -m hancast_sidecar.main`（`sidecar.rs:160-172`）。

macOS 上还有第二层：即使 sidecar 找到了，`Contents/MacOS/` 与 `Contents/Resources/` 的分裂会让 Nuitka 的 loader 报 `ImportError: dlopen(.../Contents/MacOS/lxml/etree.so)`——Nuitka `--standalone` 只从「可执行文件所在目录」解析模块，`sys.path` / `PYTHONPATH` 都不生效。CI 的修法是给 `Resources/` 的每一项在 `MacOS/` 建同名符号链接（`build.yml:283-318`）。

### 2.5 仓库根 `portable_config` 的拷入要求（提交 `9450a36`）

两套 `mpv/` 目录，别搞混：

| 位置 | 是否入库 | 作用 |
|------|----------|------|
| 仓库根 `mpv/` | 只有 `mpv/portable_config/` 入库 | `.gitignore:86-87` = `mpv/*` + `!mpv/portable_config/`；二进制/动态库约 120MB 不提交 |
| `src-tauri/mpv/` | 不入库 | `bundle.resources` 的 glob 相对 `src-tauri/` 解析（`tauri.conf.json:47-52`），所以打包用的必须是这一份 |

结论：**每次构建前都要把仓库根的 `mpv/portable_config/` 拷进 `src-tauri/mpv/portable_config/`**，否则 `mpv/portable_config/**/*` 一个文件都匹配不到，`build.rs` 直接失败。

- CI（macOS / Windows）：`build.yml:158-161`
- CI（Linux）：`build.yml:202-205`
- 本地 Windows：`windows-build.ps1:296-302`（`Copy-Item "mpv" -Destination "src-tauri\mpv" -Recurse -Force`，整目录拷，顺带带上 `portable_config`）

提交 `9450a36`（`docs: 记录 tauri glob 语义、release 闸门、仓库根 portable_config 拷入要求`）就是把这条写进文档的那次。

### 2.6 Tauri `resources` 的 glob 语义坑

`scripts/check-resources.cjs:11-22` 复刻了 `tauri-utils-2.10.1/src/resources.rs` 的三条语义：

1. **glob 不递归**：`glob::glob("mpv/*")` 只列 `mpv/` 的直接子项，即使 `require_literal_separator=false`，`*` 也不跨目录层级。要递归必须显式写 `**`。
2. **命中目录会被静默丢弃**（上游 crate tauri-utils 的 `resources.rs` L195 `if entry.is_dir() { skip }`，不在本仓），不报错、不递归。
3. 因此 `GlobPathNotFound` 的触发条件是「一个**文件**都没匹配到」，而不是「一个路径都没匹配到」——只匹配到目录同样构建失败。

第 2 条咬过人：macOS 的 `mpv/*` 看得见 `mpv.app/`，但它是目录，被丢弃，app 打出来没有 mpv，反倒把一起拷进去的 `mpv.tar.gz` 打进了 bundle。修法是 `tauri.macos.conf.json:7` 显式写 `mpv/mpv.app/**/*`，且 CI 解完嵌套 tarball 后立刻删掉它（`build.yml:143-149`）。

另外两条约束：

- **动态库 glob 必须是顶层**（`*.so` 而非 `**/*.so`），否则会把 `src-tauri/target/` 下整个 Rust 构建产物打进安装包。见 `tauri.macos.conf.json:10-11`、`tauri.windows.conf.json:7-8`、`tauri.linux.conf.json:7-8`。
- **平台配置合并是整体替换**：Tauri 用 `json_patch::merge`（RFC 7386 JSON Merge Patch），数组不做逐元素合并（`check-resources.cjs:44` 注释）。所以每个 `tauri.<platform>.conf.json` 必须写出**完整**的 `bundle.resources` 数组，不能只写增量。

### 3.3 `check-resources.cjs` 检查了什么

`node scripts/check-resources.cjs`，可用 `TAURI_PLATFORM=win32|linux|darwin` 覆盖当前平台（`check-resources.cjs:25,31`）。CI 里它是 `Preflight: verify bundle.resources globs` 步骤（`build.yml:250-251`），**必须跑在 sidecar 构建之后、`tauri build` 之前**——`hancast_sidecar/**/*` 与 `*.so`/`*.dll`/`*.pyd` 都是 Nuitka 的产物，在此之前根本不存在。

流程（`check-resources.cjs:168-233`）：

1. 按平台解析 resources：overlay 文件里有 `bundle.resources` 就**整体替换** base 的数组，不做合并（`:33-55`）。打印 `platform` / `resources source` / `resources count`（`:169-172`）。
2. 逐个 glob 用复刻语义遍历（`segToRegExp` 把 `*` 编成 `[^/]*`，`:57-61`；`walk` 处理 `**` 可匹配 0 层，`:79-101`），把命中项分成 `files` 与 `dirs`（`:103-111`）。
3. `files.length === 0` → `MISSING`，附原因（`only N dir(s), no file` 或 `0 matches`），`failed++`（`:181-188`）。
4. 命中了目录、但该目录下一个文件都不会进 bundle → `warn`，并直接给出修法建议：把 `X/*` 换成 `X/**/*`（`:193-212`）。
5. 打印 `total files that will be bundled`（`:215`）。
6. **二进制包目录对账**（`checkBinaryPackages`，`:143-166`，v2.3.8 起）：`includePackages()`（`:123-141`）从 `hancast-backend/scripts/build_sidecar.py` 里读出每条 `--include-package=X`，逐个查 `X/**/*` 在 `src-tauri/` 的实际命中数——产出里有该目录、白名单却没列它，就 `MISSING` 并计入失败（`:218`）。这一条专为 v2.3.7 的坑而装：`curl_cffi/` 没进白名单时，顶层 `*.so` 抓不到目录里的 `_wrapper.abi3.so`，产物 import 失败后按设计静默降级回 `requests`，**构建照样成功、日志一句错都不报**，只有对账能发现。目录形态不存在（纯 Python 被编进可执行文件）则判 `ok`，不算失败。
7. `failed > 0 || pkgFailed > 0` → dump `src-tauri/` 顶层清单与 Nuitka dist 清单（各最多 50 条），`exit(1)`（`:220-227`）。

存在的意义（`:5-9` 注释）：`tauri-build` 对任何含 `*` 的 glob，匹配为空就直接失败并报 `glob pattern <pattern> path not found or didn't match any files.`，而且**在第一个失败的 glob 处中断**，后续 glob 从不被校验，排查成本极高。Preflight 把它变成一次性、精确、带实际清单的诊断。

macOS 为什么非签不可（`build.yml:359-366` 与 `src-tauri/Info.plist:5-20` 注释）：macOS 15+ 的「本地网络」权限按**代码身份**判定。Tauri 不签名时主程序留下的是 Rust 链接器写的 adhoc 签名，Identifier 形如 `HanCast-<16位hex>`、flags `0x20002(adhoc,linker-signed)`——同一个 bundle id 每次构建换一个身份，NetworkAgent 认不出它就**静默拒绝组播**（`sendto 239.255.255.250` → `Errno 65`），连弹窗都没有、`TCC.db` 里也不留记录。2026-10-13 同一台机器、同一份字节 A/B：产物原样 → 心跳「通道 broadcast」；重签 → 「通道 multicast」(24 条) + 入站 200。

所以 `Info.plist` 的两条声明（`NSLocalNetworkUsageDescription`、`NSBonjourServices=["_upnp._tcp"]`）+ **稳定签名身份**三者缺一不可（`Info.plist:9-19`）。`Info.plist` 经 `tauri.macos.conf.json:3-5` 的 `bundle.macOS.infoPlist` 接入，且必须纳入版本控制——CI 从仓库构建，本地未跟踪的副本不会进产物（`Info.plist:20`）。

> ⚠️ `build.yml:7` 的头注释仍写着「不执行代码签名」，与 `:367-388` 的实际步骤矛盾，属**过时注释**。

### 4.5 Release 怎么创建

`release` job（`build.yml:553-609`）：

```yaml
needs: [build, read_version]
if: >
  needs.build.result == 'success' &&
  github.ref_type == 'tag' &&
  ( github.event_name == 'push' || inputs.make_release == true )
```

三个条件缺一不可（`:556-559`）。`make_release` 默认 false，所以在 `main` 上手动 dispatch 只构建、不发布——曾经用 `refs/heads/main` 当 tag 发 Release，被 GitHub API 400 拒掉（`AGENTS.md:405-407` 记录了这段历史）。

步骤：

| 步骤 | 行号 | 作用 |
|------|------|------|
| `Checkout this tag` | `:566-567` | 检出**被测 tag** 的工作区，规则包 zip 直接从这里取 |
| `Check rule-pack assets match the index` | `:569-571` | `python3 tools/build-rule-packs.py --check`；产物或索引与源不一致就非 0 退出 |
| `Stage rule-pack zips for the release` | `:573-578` | `cp rule-packs/dist/*.zip artifacts/rule-packs/` |
| `Download all build artifacts` | `:580-588` | `pattern: bundle-*`、`path: artifacts`、`merge-multiple: true` |
| `List downloaded artifacts` | `:590-593` | `find artifacts -type f` |
| `Publish draft release` | `:595-609` | `softprops/action-gh-release@v2`，`draft: true`、`generate_release_notes: true` |

上传的文件 glob（`:600-609`）：`artifacts/**/*.dmg`、`*.app`、`*.app.tar.gz`、`*.exe`、`*.msi`、`*.deb`、`*.rpm`、`*.AppImage`，以及 **`artifacts/rule-packs/*.zip`**。

**规则包 zip 随 Release 发布**出自提交 `356f6eb`。理由（`:562-565` 注释）：索引里的 sha256 必须和 Release 上的字节逐位一致，否则用户装包会被摘要校验拦下；zip 用固定时间戳（1980-01-01）与固定条目顺序生成（`tools/build-rule-packs.py:13-14, 40, 95-106`），所以从 tag 工作区直接上传的字节和重跑脚本的字节相同，不需要另建一条产线。

**Release 是 draft**：这是刻意的闸门。CI 出包 → 人工装 draft 里的产物跑验收（§6）→ 通过后才在 GitHub 上把它 publish 成正式 Release。

## 5. 发布流程 runbook

从改代码到用户能下载的完整顺序：

```bash
# ── 0. 源码级 / 真机级验收（必须在打 tag 之前做完）──
cd hancast-backend && uv run pytest                       # 后端单测
npx vue-tsc --noEmit                                      # 前端类型
hancast-backend/.venv/bin/python tools/verify-rule-packs-live.py "<链接>"
python3 tools/ssdp_probe.py                               # 真机链路，按需
# …按本轮改动挑 tools/ 里对应的脚本，见 tools/README.md

# ── 1. bump 版本（唯一入口，别手改各文件）──
npm run version:set 2.3.6
npm run version:sync        # 复核：打印当前版本并再同步一次
node scripts/check-version.cjs   # 可选：三处粗校验（未接入 CI）

# ── 2. 复核规则包产物与索引一致（改了 rule-packs/ 才需要重建）──
python3 tools/build-rule-packs.py --check
python3 tools/build-rule-packs.py            # 仅当 --check 失败时

# ── 3. 提交 ──
git add -A && git commit -m "chore(release): v2.3.6（…）"

# ── 4. 打 tag（tag 一推 CI 就开始产包，所以第 0 步必须已完成）──
git tag v2.3.6

# ── 5. push（分支 + tag）──
git push origin HEAD:main
git push origin v2.3.6

# ── 6. 看 CI ──
gh run watch                       # 或 gh run list --workflow=build.yml
gh run view <run-id> --log-failed  # 失败时

# ── 7. 产物验收（draft Release / artifact 到手后）──
gh release download v2.3.6 --pattern '*.dmg' --dir /tmp
tools/install-macos-artifact.sh 2.3.6 /tmp/HanCast_2.3.6_aarch64.dmg
tools/accept-macos-artifact.sh 2.3.6

# ── 8. 全部 PASS 才 publish ──
gh release edit v2.3.6 --draft=false
```

**项目纪律：验收必须在打 tag 之前做完。**
tag 一推，CI 立刻产包并建 draft Release；此时才发现代码有问题，就得再 bump 一版重打 tag，版本号白白烧掉一个。因此第 0 步（源码级 + 真机级）是 tag 前的闸门，第 7 步（产物级）是 publish 前的闸门——两道都不能省。

**第二道纪律：禁止手工补丁冒充验收。** 出自提交 `76bba31`（`chore(tools): 打包产物验收脚本，禁止手工补丁冒充验收`）。`tools/accept-macos-artifact.sh:3-4` 的原话：「验收 **CI 产物本身**：全程 CLI，不碰 UI 坐标，禁止任何手工补丁（重装/重签都不许）。每轮装完包都跑一遍；任一项 FAIL 就说明这版产物不能用，别拿本地补丁版冒充。」`tools/install-macos-artifact.sh:5-6` 同样写着「装的是 CI 产物本身，不做任何补丁（重签/替换文件都不许）」。

这条纪律有血的教训：v2.2.13 就是靠这套检查（14 项）才发现「plist 齐全但组播仍被拒」，而当时的**本地重签把现场掩盖了**（`76bba31` 提交说明）。同理，`tools/pull-rule-packs-installed.py:5-8` 也写着「手改 `share_rules/plugins/` 里的文件则是拿补丁冒充验收，产物里根本没跑过 `plugin_pull`」。

## 7. 回滚与常见构建故障

### 7.1 CI 卡住/失败时看哪

按「最早失败的那个步骤」定位，`fail-fast: false`（`build.yml:42`）意味着三平台互不牵连，可以只看挂掉的那条：

```bash
gh run list --workflow=build.yml --limit 5
gh run view <run-id>                       # 看哪条矩阵、哪个步骤红了
gh run view <run-id> --log-failed          # 只看失败日志
gh run view <run-id> --job <job-id> --log  # 单矩阵项全日志
```

高频落点：

| 症状 | 先看 | 常见根因 |
|------|------|----------|
| 毫秒级失败，日志是 `❌ package.json 是 X，但这些契约点已经写着更高的版本` | `Build frontend`（`:271`） | 版本 SSOT 滞后闸门（§1.4 闸门 A）。跑 `npm run version:set <x.y.z>` 重新提交、重打 tag |
| `MISSING <glob> -> 0 matches` / `only N dir(s), no file` | `Preflight`（`:250`） | 见 §3.3；最常见是 `portable_config` 没拷、mpv 没下下来、sidecar 没构建 |
| `no usable mpv binary found under src-tauri/mpv` | `Download & unpack MPV`（`:128`） | MPV release 资产名/tag 变了，或 `api.github.com` 之外的下载被限流 |
| `sidecar did not reach 'DLNA server started'` | `Fix macOS sidecar resource layout`（`:292`） | dylib rpath 没改对（`build_sidecar.py:111-232`），或 Nuitka 少收了某个 `--include-package` |
| `签名 Identifier 是 'HanCast-<hex>'，主程序仍是 linker-signed` | `Adhoc sign macOS app`（`:367`） | 签名步骤被跳过或签名后又动了 bundle |
| `dmg 内的 .app 签名 Identifier 是 …` | `Bundle macOS dmg`（`:395`） | `cp`/`hdiutil` 环节把签名弄丢 |
| release job 里 `需要重建: dist/…` / `需要重建: index.json` | `Check rule-pack assets match the index`（`:569`） | 改了 `rule-packs/<pack>/` 却没重跑 `tools/build-rule-packs.py` |
| release job 没跑 | `release` 的 `if`（`:556-559`） | ref 不是 tag；或手动 dispatch 时没勾 `make_release` |
| Release 上传报重复文件 | `Publish draft release`（`:595`） | `download-artifact` 的 `pattern` 不是 `bundle-*`，把按格式拆分的 artifact 也拉了下来 |

回滚：Release 是 draft，publish 前发现问题直接删 draft + 删 tag，不影响用户。已 publish 的版本要撤回，就在 GitHub 上把 Release 改回 draft 或删掉资产，再 `git tag -d <tag> && git push origin :refs/tags/<tag>`——但更推荐直接往前发一版修复，因为规则包索引的 `url` 指向 `main` 分支的 raw 路径（`build-rule-packs.py:36-38`），历史 tag 的产物地址并不随 tag 走。

### 7.2 本地 `cargo check` 需要什么桩

打包资源只在 CI/完整构建里生成，本机直接 `cargo check` 会因 `bundle.resources` 的 glob 落空而在 `build.rs` 阶段失败。用 `tools/rust-check.sh`：

```bash
tools/rust-check.sh                      # 等价于 cargo check
tools/rust-check.sh --release            # 透传参数给 cargo check
```

它按 Tauri 配置建**一次性空桩**，check 完只删自己建的文件（`rust-check.sh:1-5, 11-21` 的 `trap cleanup EXIT` + 逆序删除，绝不动仓库里已存在的路径，`:24-28` 的 `stub()` 遇已存在就跳过）。建的桩（`:37-49`）：


### 7.3 push 被拒怎么处理

当前分支拓扑（2026-10-15）：本地工作分支是 `feat/js-rule-plugins`，远端只有 `origin` → `https://github.com/pingod/HanCast`，跟踪分支是 `origin/main`；另有本地 `main` 与 `backup/v2.2.11-amend`。

本地 `main` 落后于 `origin/main` 时，`git push origin main` 会被拒（non-fast-forward）。项目做法是**不先合并本地 main**，而是直接把当前工作分支的头推到远端 main：

```bash
git fetch origin
git push origin HEAD:main
```

这样远端 main 拿到的是工作分支上那条已经验收过的历史，本地那条陈旧的 `main` 不参与、也不需要 rebase。**不要**用 `--force`：它会覆盖别人（或另一台机器）推上去的提交。

> ⚠️ 未验证：仓库里没有任何文件写下这条 push 纪律（全仓 grep `HEAD:main` / `HEAD:master` 零命中）。上面的做法是从当前分支拓扑与「本地 main 长期落后于 origin/main」这一事实推出的操作惯例，不是成文规范。

### 7.4 Gitee 镜像同步

`push-gitee.ps1`（PowerShell，仅 Windows）：

```powershell
.\push-gitee.ps1                     # 只推
.\push-gitee.ps1 -Message "…"        # 先 git add . && git commit -m "…" 再推
```

- 镜像地址硬编码在 `push-gitee.ps1:8`：`https://gitee.com/buxiangqumingzi/han-cast.git`
- remote 名 `gitee`，不存在时自动 `git remote add`（`:11-15`）
- 带 `-Message` 时会 `git add .`（`:20`）——注意这是全量添加，别在脏工作树上用

> ⚠️ 该脚本当前**跑不通**：`:26` 执行的是 `git push gitee master`，而本地没有 `master` 分支（只有 `main`、`feat/js-rule-plugins`、`backup/v2.2.11-amend`），且当前仓库没有配置 `gitee` remote（`git remote -v` 只有 `origin`）。要用得先把 `master` 改成 `main`（或 `HEAD:master`）。

### 7.5 其它构建故障速查

| 症状 | 根因 / 处置 |
|------|-------------|
| `glob pattern … path not found or didn't match any files.` | `build.rs` 阶段的 Tauri 原生报错，第一个失败的 glob 就中断。用 `node scripts/check-resources.cjs` 拿到精确诊断（§3.3） |
| 本地构建成功但产物里没有 mpv（macOS） | `mpv/*` 命中了 `mpv.app/` 目录但目录被 Tauri 丢弃。macOS overlay 必须写 `mpv/mpv.app/**/*`（`tauri.macos.conf.json:7`） |
| bundle 体积莫名多出 ~44MB | macOS 的 mpv 资产 zip 里套着 `mpv.tar.gz`，没删就被 `cp -a` 混进了 bundle。CI 在 `build.yml:148-149` 显式删它 |
| 安装包里有整个 Rust `target/` | 动态库 glob 写成了 `**/*.so`。必须是顶层 `*.so`（§2.6） |
| 平台 overlay 加了新 glob，另一个平台构建挂了 | Tauri 的平台合并是数组整体替换，每个 overlay 必须写**完整**数组（§2.6） |
| sidecar 明明构建过了却仍在重建 / 或明明改了代码却没重建 | `build_sidecar.py:270-280`：产物已存在则跳过，只有 `--force` 才真编译。本地改完后用 `npm run build:sidecar` 前先删 `src-tauri/hancast-sidecar/`，或直接 `uv run python scripts/build_sidecar.py --force` |
| Windows 装完「系统声音」选不到设备 | Nuitka 漏了 `--include-package=pyaudiowpatch` / `--include-module=_portaudiowpatch`（`build_sidecar.py:318-326`） |
| macOS 装完「发现不了设备」，日志是 `Library not loaded: @executable_path/libpython3.12.dylib` | `fix_macos_dylib_paths()` 没跑成（缺 `install_name_tool`，`build_sidecar.py:145-147` 会打 Warning 后跳过） |
| 设置页整块读不到后台参数，命令回 `'ascii' codec can't encode characters` | 父进程没给 `LANG`/`LC_*`，Python stdout 退回 ASCII。壳层 spawn 时必须带 `PYTHONIOENCODING=utf-8`（`src-tauri/src/sidecar.rs:168, 209`）。判据脚本 `tools/verify-sidecar-utf8-protocol.py` |
| 本地 `npm run tauri build` 打出来的界面是旧的 | `beforeBuildCommand` 不含前端构建（§2.2）。先手动 `npm run build` |
