## 1. 三个进程 + 两个外援

```
┌──────────────────────────┐  invoke(name, payload)   ┌─────────────────────────────┐
│  Vue 3 WebView           │ ───────────────────────→ │  Rust 壳层 (Tauri 2)        │
│  src/                    │ ←─────────────────────── │  src-tauri/src/lib.rs       │
│  stores + components     │   Promise / Tauri 事件    │  71 条 #[tauri::command]    │
└──────────────────────────┘                          └──────────┬──────────────────┘
                                                                 │ 每行一个 JSON 对象
                                                     stdin ↓     ↑ stdout（单写者锁）
                                              ┌──────────────────┴──────────┐
                                              │  Python Sidecar（Nuitka 编译）│
                                              │  hancast_sidecar/           │
                                              │  64 条命令 + 6 个事件         │
                                              └───────┬──────────────┬───────┘
                                                  Popen │              │ Popen
                                              ┌─────────┴──┐   ┌──────┴────────┐
                                              │ mpv        │   │ ffmpeg        │
                                              │ 接收投屏播放│   │ 屏幕投屏采集转码│
                                              │ IPC socket │   │ 子进程管道     │
                                              └────────────┘   └───────────────┘
```

| 层 | 位置 | 职责 | 不知道 |
| --- | --- | --- | --- |
| 前端 | `src/` | 渲染、交互、i18n、状态聚合、进度模拟 | DLNA/SOAP/XML；只认命令名与事件名 |
| 壳层 | `src-tauri/src/` | Sidecar 生命周期、请求-响应配对、系统能力（剪贴板、窗口、托盘、自启、日志导出）、事件转发 | 业务语义（除更新检查外全部透传） |
| Sidecar | `hancast-backend/hancast_sidecar/` | SSDP/DLNA/UPnP、媒体服务、解析规则、屏幕投屏、投屏确认、配置与参数 | 界面 |
| mpv | 外部进程 | 播放推到本机的媒体 | HanCast 存在 |
| ffmpeg | 外部进程 | 屏幕/窗口/音频采集与 HLS 切片 | HanCast 存在 |

ffmpeg 自 v2.3.11 起**不随包分发**：由 Sidecar 在运行时按「手动指定 → 系统已装 → 本程序下载到配置目录 `bin/`」检测出来，三路都落空时前端弹「需要下载运行依赖」（`utils/ffmpeg_deps.py`，细节见 [屏幕投屏](屏幕投屏.md) §5.8）。mpv 仍然随包。

**命令归属**：71 条壳层命令里 **10 条就地执行**（`minimize_window`、`close_window`、`read_clipboard`、`write_clipboard`、`export_logs`、`is_store_version`、`get_autostart`、`set_autostart`、`open_ffmpeg_dir`、`notify_os`），其余 **61 条转发 Sidecar**。`open_ffmpeg_dir` 是「就地但要先问 Sidecar」——它下发 `ffmpeg_status` 拿 `managed_dir`，再调系统文件管理器，路径不接受前端传入（`lib.rs:869-896`）。逐条清单见 [前端 API 参考](HanCast-Frontend-API.md) §2。

**数量为什么对不上**（新人必问）：壳层 **67** 条（`lib.rs:1509-1581`）≠ Sidecar 注册表 **62** 条（`commands.py:131-224`），差额是**双向**的，别按一个方向减。

- 从壳层往下减：10 条就地执行、根本不下发（上一条点过名）；`parse_media_file` 与 `parse_media_url` 在壳层是两条命令，到 Sidecar 归并成一条 `parse_media`（`lib.rs:269-310`）。所以 57 条转发只剩 **56 个字面 `cmd` 名**。
- 从注册表往回看：有 **6 条壳层不会字面下发**——`unhide_device`、`get_hidden_devices` 没有前端入口（`commands.py:142-143`）；`browser_result` 只由壳层的浏览器通道反向 RPC 下发（`commands.py:193`，见 [反爬实现取证与浏览器通道](反爬实现取证与浏览器通道.md)）；`plugin_check_updates` / `plugin_import` / `plugin_pull` 自 v2.3.20 起改走 `plugin_task_start` 的 operation（`lib.rs:385-432`、`commands.py:171`），这三条注册项保留下来只为了「直发仍然可用」，慢操作不再同步占住命令通道。
- 合账：`56 + 6 = 62`、`10 + 57 = 67`。`exit` 两边都不算——它不进注册表，由主循环直接拦下（`main.py:126-128`）。

## 2. 网络面（端口与协议）

| 用途 | 传输 | 端口 | 绑定位置 | 失败行为 |
| --- | --- | --- | --- | --- |
| SSDP 收包（M-SEARCH/NOTIFY） | UDP | **1900**（固定，`ssdp.py:32`） | `0.0.0.0:1900` + 每张网卡 join `239.255.255.250`（`ssdp.py:437`、`ssdp.py:424`） | 组播收不到 → 靠广播回退与手动加设备 |
| SSDP 通告/搜索 | UDP | 目的 `239.255.255.250:1900`（`ssdp.py:831`） | 组播 TTL 由后台参数 `discovery.multicast_ttl` 决定（默认 2） | 组播 `sendto` 失败 → 子网**广播**重发（`ssdp.py:844-851`、`_notify_broadcast` `ssdp.py:860-885`） |
| UPnP 描述与 SOAP 控制端点 | TCP | 首选 **8080**（`protocol/server.py:349`） | `ThreadingHTTPServer('0.0.0.0', 8080)` | `errno` 记进日志后换随机端口（`protocol/server.py:360-369`），随后把真实端口回灌给 SSDP（`commands.py:_start_services`，见 §3） |
| 本地文件/代理媒体服务（投本地文件、投需要本机代签名的直链） | TCP | 随机空闲端口（`media/server.py:646`） | `MediaServer`，`base_url` 用选定网卡 IP（`media/server.py:648`） | 多网卡机器若不选网卡，电视会拿到默认路由 IP 而拉不到流（`commands.py:69-72`） |
| 屏幕投屏 HLS 分发 | TCP | 随机端口，起服后回读（`screencast/httpd.py:108`） | aiohttp，同时供 DLNA 通道与浏览器观看页 | 端口占用即换；停止时显式释放（见 [屏幕投屏](屏幕投屏.md) §5.5） |
| mpv IPC | Unix socket / 命名管道 | — | `--input-ipc-server=`（`renderer/mpv.py:471`） | 连接失败按状态回报 |

链路内 HTTP（抓描述、抓来源页面、拉流代理）**显式绕过系统代理**——这台机器上 `127.0.0.1:9565` 之类的 GFW 代理会吞掉局域网请求。相关取证见 [反爬实现取证与浏览器通道.md](反爬实现取证与浏览器通道.md) 与 [故障排查](故障排查.md) 的代理条目。

**发现是被动收通告，不是端口扫描**：设备只来自 SSDP 的 NOTIFY / M-SEARCH 响应，然后逐条 GET 通告里的 `LOCATION` 取描述。描述解析的**准入条件是「提供 AVTransport 服务」**（`ssdp.py:1095`、门槛在 `ssdp.py:1190-1196`），`deviceType` 只作展示标签——路由器/NAS 的 IGW、MediaServer 描述能被 UPnP 栈正常解析，但投不了屏，v2.3.13 起一律不登记（判据脚本 `tools/verify-ssdp-cast-gate.py`，细节见 [故障排查](故障排查.md) §3.5）。手动添加走同一条门槛（`ssdp.py:1252-1256`）；`_MANUAL_PORTS`（`ssdp.py:1233`）只是给手输的裸 IP 猜端口，不构成扫描。

## 3. Sidecar 内部：一次启动装起了什么

`CommandHandler.__init__`（`commands.py:54-209`）按固定顺序装配，顺序本身是约束：

```
0. main.py:25-27   stdin/stdout/stderr 一律强制 UTF-8（必须在 setup_logger 之前，
                   否则中文响应变成 success:false）
1. main.py:43      setup_logger("hancast")      → 控制台 + RotatingFileHandler
2. commands.py:55-57  Config() 读 hancast_setting.json → params 载入覆盖项
3. commands.py:63  MpvManager.check()           → 定位 mpv（bundled 路径优先）
4. commands.py:67  MPVRenderer(path)
5. commands.py:72  MediaServer(lan_ip=选定网卡)  → 本地文件 HTTP
6. commands.py:75  ShareResolver(media_server, config) → 规则包管线 + 插件目录
7. commands.py:87-94 DLNAServer(friendly_name, usn, ip, port=8080)
8. commands.py:97-103 SSDPService(..., preferred_ip=选定网卡)
9. commands.py:106-107 DeviceGuard(config) + 确认请求回调
10. commands.py:131-224 注册 64 条命令
11. commands.py:201-205 ssdp.set_callbacks(found / lost / should_ignore)
12. commands.py:208、209-221 _start_services()：
       protocol.set_on_state_change(...) → dlna_server.start()
       → ssdp._port = dlna_server.get_port()   ← 端口可能被换掉，必须先起 DLNA
       → ssdp.start()（内部注册自己的 ALIVE 通告）
13. main.py:110    emit {"event":"ready"}
14. main.py:113    for line in sys.stdin：逐行执行
```

两个易踩的顺序依赖：

- **SSDP 必须等 DLNA 端口定下来**（第 12 步中 `ssdp._port` 回灌，`commands.py:212-214`），否则 8080 被占时描述 URL 指向死端口，设备列表永远空。
- **UTF-8 包裹必须早于 logger 初始化**（`main.py:21-28` 的注释记录了 v2.2.18 的打包版事故）。

## 4. 线程与并发模型

Sidecar 是**多线程 + 多 HTTP 服务器**，不是 asyncio 单循环（aiohttp 只用在屏幕投屏分发上）。

| 执行体 | 起于 | 干什么 | 与主线程的共享点 |
| --- | --- | --- | --- |
| 主线程 stdin 循环 | `main.py:113` | 解析一行 → 执行 → 写响应 | 只经 `protocol_io` 写 stdout |
| SSDP 收包线程 | `ssdp.py:330-332` | 收 M-SEARCH/NOTIFY，回调 `_on_device_found` | 事件经 stdout 锁 |
| SSDP NOTIFY/心跳线程 | `ssdp.py:338-340` | ALIVE 通告、byebye、组播→广播回退 | — |
| 探活线程 | `ssdp.py:774` | 判定 `discovery.device_stale_s` 过期 → `device_lost` | 设备表 |
| DLNA HTTP 线程池 | `protocol/server.py:350`（ThreadingHTTPServer） | 供描述 XML、收 SOAP 控制 | `protocol` 状态、Guard 判定 |
| 媒体 HTTP 线程 | `media/server.py:656` | 本地文件 Range、代理转发 | 会话 URL |
| 解析任务线程 | `commands.py:691`（`RESOLVE_<task_id>`，最多 3 并发，`commands.py:674`） | 粘贴解析（网络抓取 + 规则执行） | `_resolve_tasks` + `_resolve_lock` |
| Guard 确认等待 | `security/guard.py:69`（`threading.Event`）+ 探测用 `ThreadPoolExecutor`（`guard.py:456`、`guard.py:611`） | 阻塞等待用户决定 / 并发探测设备信息 | 确认队列 + `_lock` |
| mpv 管理线程 | `renderer/mpv.py:545-555`（`start_mpv` + `ipc` 两个线程） | 持有 `Popen`、读写 IPC | `proc_lock`、`_stopping` |
| ffmpeg 读/写线程 | `screencast/manager.py:322`、`ffmpeg_manager.py` | 采集喂帧、读 stderr、环回补静音 | `_avf_screen_lock`（`ffmpeg_manager.py:31`） |
| 手动设备恢复 | `commands.py:219` | 启动后重建手动设备 | 配置 |

**stdout 是唯一的跨线程出口**，因此所有写入必须走 `protocol_io._write_lock`（`protocol_io.py:25`）。`print()` 不是原子的：两个线程同时写会产生行内交错，那一行对壳层既不是合法响应也不是合法事件，会被静默丢弃，对应请求就永远等不到回包（`protocol_io.py:8-17` 记录了这一点）。新增任何主动推送时，只能用 `protocol_io.emit_event` / `emit_response`。

**壳层侧的请求配对**：`send_command` 用自增 id 注册 `oneshot` channel（`sidecar.rs:371-380`），`handle_stdout_line` 按 `id` 派发响应、按 `event` 名字 `app.emit` 转发（`sidecar.rs:345-368`）。Sidecar 退出时把所有挂起请求一次性回 `success:false`，避免前端永久挂起（`sidecar.rs:334-341`）。

## 5. 四条主数据流

### 5.1 发送投屏（本地文件 / 直链）

```
拖文件 → parse_media_file → MediaServer 起 HTTP（随机口，选定网卡 IP）
      → start_cast(deviceId, uri, mime) → DLNA SetAVTransportURI + Play
      → cast_state_changed 事件回灌 → CastController 轮询 GetPositionInfo
```

关键约束：推给电视的 URI 必须是**电视能直连**的地址。所以本机代理只在源站要求 Cookie/Referer/签名时效时才介入（`media/server.py`），而介入时也必须绕开系统代理。切画质不是读缓存——源站签名带时效，攒下来的 URL 必然过期，所以切档 = 带 `ctx.quality` 重新解析一次再 `Stop → SetURI → Play`（`CastController.vue`，v2.3.6）。

### 5.2 粘贴投屏（分享口令 / 短链 / 任意网页）

```
resolve_share(text, quality) → 立即返回 {task_id, status:"pending"}（commands.py:691）
                            → 后台线程解析：正则取候选 → 规则管线
   规则来源只有两种（v2.3.3 起程序不再内置任何规则）：
     · 声明式 JSON 站点规则（<share_rules>/*.json，declarative.py）
     · JS 规则包（<share_rules>/plugins/<id>/，QuickJS 沙箱 jsruntime.py）
前端轮询 get_resolve_result(task_id) → 候选排序 → 用户选设备 → start_cast
失败：写进按域名归类的失败台账（media/failures.py，v2.3.6），设置页可查可删
```

为什么异步化：一次解析可能要跟随短链、抓页面、跑 JS 沙箱，串行会卡住输入框；命令面与超时见 [前端 API 参考](HanCast-Frontend-API.md) §2.3，规则写法见 [分享解析规则](分享解析规则.md) 与 [解析插件开发指南](解析插件开发指南.md)。

### 5.3 接收投屏（本机作为 DLNA 渲染端）

```
外部控制点 → SOAP SetAVTransportURI（protocol/dlna.py）
          → DeviceGuard 判定（security/guard.py:188-272）
               受信 → 直接放行
               陌生 → emit cast_confirm_request（commands.py:1002）
                      → GuardConfirmModal 弹窗，默认 15s 超时（config.py:202-209）
                      → respond_cast_confirm(requestId, approved, policy)
          → MPVRenderer 播放（renderer/mpv.py:471 起 IPC）
          → TransportState 变化 → cast_state_changed
停止：Stop 动作发出后如实回报「电视未确认停止」→ StopWarningBanner（commands.py:547-555）
```

完整取证见 [投屏确认](投屏确认.md)。入站信封本身不合法（前导空白/BOM、压根不是 XML）走的是另一条出口：`protocol/dlna.py:628-641` 先剔前导垃圾，剔完仍解析不了就回 SOAP Fault 402，不再冒成裸 HTTP 500（排错见 [故障排查](故障排查.md) §5.4）。

### 5.4 屏幕投屏（本机画面推出去）

```
list_screen_sources → 选源（全屏/窗口/显示器 + 麦克风 + 系统声音）
start_screen_cast(params) → ffmpeg_manager 拼命令 → Popen ffmpeg
   采集 → x264 编码（preset/尺寸走后台参数）→ HLS 切片（浏览器通道 1s、电视通道 2s）
   → aiohttp httpd 供 m3u8/ts（同一份片源供两个出口）
   出口 A：DLNA 设备，SetURI 指向 m3u8，dlna_verify_seconds 内确认拉流
   出口 B：浏览器观看页（screencast/www/ + hls.js 低延迟参数）
状态：screen_cast_state_changed（manager.py:469，载荷 == screen_cast_status）
```

完整设计与平台限制见 [屏幕投屏](屏幕投屏.md)。

## 6. 磁盘上的状态（配置目录全清单）

目录 `SETTING_DIR`（`config.py:22-27`）：

| 平台 | 路径 |
| --- | --- |
| Windows | `%APPDATA%\HanCast` |
| macOS | `~/Library/Application Support/HanCast` |
| Linux | `~/.config/hancast` |

| 文件 / 键 | 内容 | 定义处 |
| --- | --- | --- |
| `hancast_setting.json` | 全部用户设置，**原子写**（临时文件 + `os.replace` + 锁） | `config.py:34`、`config.py:70-80` |
| ├ `usn` | 本机 UPnP UDN 的一部分，首次生成后固定 | `config.py:61-64`、`config.py:141-146` |
| ├ `friendly_name` | 电视上看到的接收端名字，默认 `HanCast(<platform.node()>)` | `config.py:36-38` |
| ├ `media_port` | 媒体服务端口，`0` = 自动 | `config.py:111-114` |
| ├ `network_interface` | 选定网卡的 IPv4，空 = 自动（全部接口） | `config.py:106-109` |
| ├ `hidden_devices` / `manual_devices` | 隐藏设备 UDN 列表 / 手动加的设备地址（IP、IP:端口、描述 XML URL） | `config.py:150-198` |
| ├ `device_guard` | `{enabled, confirm_timeout, trusted_devices, blacklisted_devices}` | `config.py:202-214` |
| ├ `mpv` | mpv 路径与偏好 | `config.py:218-225` |
| ├ `ignored_update_version` | 用户点过「此版本不再提示」 | `config.py:231-245` |

**身份只有一个来源**：桌面/移动 UA 登记在 `params.py:29-34`，`identity.py` 反向读它；历史上规则层写 Chrome/124、代理层写 Chrome/120，同一次投屏向源站报两个浏览器——站点风控盯的正是这种不一致（`identity.py:1-10`）。

## 9. 架构级不变量（改代码前必读）

1. **stdout 只能经 `protocol_io` 写**（§4）。任何新增线程要推事件，都必须走 `emit_event`，不能用 `print`。
2. **请求必须有响应**。Sidecar 命令抛异常时主循环仍会回 `success:false`（`main.py:138-140`）；壳层在 Sidecar 退出时把挂起请求全部判失败（`sidecar.rs:334-341`）。新增命令若走异步任务模式，必须同时提供轮询出口（参考 `resolve_share` / `get_resolve_result`）。
3. **所有 stdio 一律 UTF-8**，且包裹点在 logger 初始化之前（`main.py:21-28`）。
4. **链路内 HTTP 绕开系统代理**，且 UA/设备号只从 `identity.py` / 后台参数取（§6）。
5. **端口不写死假设**：DLNA 8080 可能退化成随机口，任何拼 URL 的地方都要用 `dlna_server.get_port()` / `MediaServer.base_url`，不要重新拼。
6. **多网卡必须用选定 IP**（`config.network_interface`），否则电视拿到默认路由 IP（`commands.py:69-72`）。
7. **程序不携带任何内置解析规则**（v2.3.3）。新增站点走规则包或 `share_rules/*.json`，不要往 Python 里加硬编码规则。
8. **后台参数是唯一可调面**。新能力若需要用户可调，登记进 `PARAM_SPECS`（`params.py:41`），别开新的配置文件键。
9. **投屏目标 URI 必须电视可直连**；带时效签名的流不做缓存复用（切档重新解析，§5.1）。
10. **版本只有一个真源**：`package.json:4`。改版本用 `npm run version:set`，CI 有滞后闸门（[构建与发布](构建与发布.md) §1）。历史上此处曾误写为被同步的 `tauri.conf.json`，现更正。
11. **常驻前端 Store 首次创建必须归属 App**（`src/App.vue:20-25`）。Pinia setup 只运行一次，其组件卸载钩子也只绑定首次调用者；若由 Home 首建，跳到设置时会解除监听，返回首页不会自动重建。当前 device/cast/screencast 都由根组件持有。

**验证边界**：以上均由离线并发用例复现并证明（`tests/test_session_poll_generation.py`、
`tests/test_stop_cast_delivery.py`、`tests/test_plugin_tasks.py`、`tests/test_screencast.py`），
假会话/假网络/临时插件目录，不触网、不写真机；`cargo check` 通过。
**没有**在真机上跑过这些失败场景，也不等于电视端行为已验证；协作式取消在 DNS 等待与
QuickJS 执行中只能等它自己结束，`requests` 的 socket timeout 不是总计时器。

最值得加强的用户场景，按收益排序：

1. **第一次投屏就能知道卡在哪**：在界面按发现设备 → 解析 → 电视接受 → 实际拉流呈现诊断；复用现有日志和拉流统计，区分 VPN/网卡、防火墙、格式不支持，而不是统一报“失败”。
2. **播放途中换内容、换来源、换清晰度**：先完成会话所有权及取消/截止时间，再实现可靠的媒体↔屏幕移交、可取消解析和失败重试；不要用重试掩盖旧任务仍在执行。
3. **连续观看与长时间后台使用**：可选最近播放/待播队列、地址过期后重新解析、休眠恢复后重发现；这些是规划，当前没有完整实现。多设备独立播放不等于时钟同步的“多房同步”。

跨层可维护性建议：把命令名/入参/响应错误码集中成可生成 TS 类型的契约；`commands.ts` 的浏览器演示与生产适配器分离。先增加接口契约测试，再拆大文件；不要仅为减少行数搬函数。
