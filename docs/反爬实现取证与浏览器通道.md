# 反爬实现取证：ssts 三端怎么过站点风控

本文是对同类开源/闭源项目 **ssts（随身听书）** 三端产物的逆向取证记录，目的有两个：

1. 说清楚「过人机验证 / 拿到需要 JS 环境的直链」这类能力，业界在 **Windows / macOS / Android** 上分别是怎么实现的——尤其是 Android，我们以后要做 Android 端时直接照着排。
2. 给出 HanCast 当前的差距清单和补齐路线，避免把「多写几个请求头」误当成反爬。

所有结论都来自产物二进制与随包脚本，不是推测。文末附**可复现命令**。

## 1. 最重要的一条结论：三端共用同一份 JS 层

apk 根目录的 `prelude.js`、apk 里另存的 `prelude_apk.js`、mac bundle 的 `Contents/Resources/prelude.js` 三份**逐字节相同**（6878 B，`cmp` 与 `diff` 都为空）。插件源码也是同一套 `ShunSources/*.js`。

这意味着它的架构是：

> **反爬逻辑写在共享 JS 里，平台差异只在「宿主向 JS 开放哪些能力」。**

JS 侧靠能力探测降级，宿主没实现的功能就绕开：

```js
// prelude.js（节选）
render: function (url, o) { return un(j.render(String(url), opt(o), fn(o, 'parse'))); },
sniff:  function (url, o) { return un(j.sniff(String(url), opt(o), fn(o, 'validate'))); },
webViewUA: function () { try { return j.webViewUA ? String(j.webViewUA() || '') : ''; } catch (e) { return ''; } },
```

`fn(o, 'parse')` / `fn(o, 'validate')` 说明**宿主会回调 JS 函数**：插件把一个 JS 回调交给原生侧，原生侧在页面加载完/嗅到候选地址之后再调它。这是我们实现 `host.render/sniff` 时可以直接抄的形状。

宿主向 JS 暴露的能力口（三端一致，来自 `prelude.js` 的 `__makeHost`）：

| 能力 | 作用 | HanCast 现状 |
|---|---|---|
| `getString/getHtml/getJson/getStrings` | HTTP（含并发批量） | ✅ 有 |
| `fetch/status/finalUrl` | 拿状态码、跟重定向 | ✅ 有 |
| `parseHtml` | HTML 选择器 | ✅ 有（`host.select`） |
| `cookies(url)` | 读 Cookie 罐 | ✅ 有（v2.3.6 起，包级 `cookies.json`） |
| `md5/sha256/base64/uuid` | 基础摘要 | ✅ 有 |
| `aesEcbDecrypt` | AES-ECB 解密 | ✅ 有（v2.3.6 起还补齐了 HMAC/AES-CBC/RSA） |
| `getPref/setPref/readCache/writeCache/cacheAge` | 插件私有配置与缓存 | ✅ 有 |
| `log/toast/progress/sleep` | 反馈与节流 | ✅ 有 |
| **`render(url, {parse})`** | **真起浏览器渲染页面，回调 JS 提取** | ❌ 缺 |
| **`sniff(url, {validate})`** | **嗅探页面里的媒体直链** | ❌ 缺 |
| **`webViewUA()`** | **拿真实 WebView 的 UA** | ❌ 缺 |
| `playsAnyDownload` | 下载的文件无扩展名也能播 | ✅ 有（本机代理） |

一个值得注意的事实：**加密算法它基本不让宿主做**。宿主只开 `md5/sha256/base64/uuid/aesEcbDecrypt` 六个口，SM3、RC4、secp256k1 全在 JS 里手写（mac bundle 里能看到 `Resources/secp256k1.js`）。这跟我们 v2.3.6 的思路一致——沙箱给签名原语，站点特有的算法交给规则包作者。

## 2. macOS 端：JavaScriptCore + WebKit，嗅探靠「往页面注入 monkey-patch」

产物：`/private/tmp/sstsmnt/随身听书.app`

- **universal Mach-O**（`lipo -archs` = `x86_64 arm64`）
- `otool -L` 显式链接 **`JavaScriptCore.framework` + `WebKit.framework`**（current version 625.1.29）→ 插件跑在 JSC，浏览器是 WKWebView
- 宿主用 `__bridge.host(sourceId, name)` 造桥，注入 JSContext 的原生函数名是 `__n_*`：

```
__n_rend(render)  __n_snifH(sniff)  __n_cook(cookies)  __n_requ(requestAll)
__n_fetc(fetch)   __n_stat(status)  __n_fina(finalUrl) __n_parsH(parseHtml)
__n_md5  __n_sha2H  __n_base64Decode/Encode  __n_aesEcbDecrypt  __n_slee
__n_log  __n_toas  __n_prog  __n_readH/__n_setPH/__n_getPL(prefs)  __n_cachH
__n_locaL/__n_htmlH
```

- **嗅探机制 = 注入脚本 + 原生消息回传**。二进制字符串里能直接看到注入体：

```js
if (window.__tsSniff) return; window.__tsSniff = 1;
// …挂钩 HTMLMediaElement 的 play / src setter、XMLHttpRequest.open、window.fetch，
//   再用 400ms 一次的 performance.getEntriesByType('resource') 轮询兜底，
//   并扫描 audio,video 元素（扫到就静音，避免外放）
try { webkit.messageHandlers.tsSniff.postMessage((el ? 'E' : 'R') + u); } catch (e) {}
```

  `'E'`/`'R'` 前缀区分「元素上抓到的」和「资源时间线里捞到的」两类来源。回传通道是 WebKit 的 `messageHandlers`，**不受页面 CSP 限制**（原生注入不是页面自己的脚本）。
- 签名：adhoc + hardened runtime，沙盒 entitlements 里带 `network.client`，`LSMinimumSystemVersion` = 14.6。

**给 HanCast 的直接启示**：macOS 上我们不需要自己绑 WKWebView 的原生 API——Tauri 2 的 `WebviewWindowBuilder` 建出来的窗口在 macOS 上就是 WKWebView，`webview.eval()` 注入、`on_page_load` 等页面加载完、再用 `window.__TAURI_INTERNALS__.invoke(...)` 把结果送回 Rust，链路和 ssts 等价。

## 3. Android 端（重点：以后做 Android 端照这里排）

产物：`ssts-v5.apk`，包名 `com.wang.ssts`。

### 3.1 技术栈

| 层 | 选型 | 证据 |
|---|---|---|
| UI | Kotlin + **Jetpack Compose** | `ui/AppRootKt`、`ui/WebScreen$$ExternalSyntheticLambda0`、`androidx/compose/runtime/Composer` |
| JS 引擎 | **Rhino**（Mozilla） | `classes3.dex` 里 `org/mozilla/javascript/Context` 出现 **93 次** |
| 浏览器 | **`android.webkit.WebView`** + `androidx.webkit`（support_lib_boundary，即 Chromium WebView 兼容层） | `WebSettingsBoundaryInterface`、`WebViewCookieManagerBoundaryInterface`、`ServiceWorkerWebSettingsBoundaryInterface` |
| HTTP | **okhttp3** | `okhttp3/OkHttpClient` 22 次；另有 `java/net/HttpURLConnection` 兜底 |
| 插件宿主 | `plugin/PluginEngine`、`plugin/Bridge`、`plugin/HostApi`、`plugin/HostEnv`、`plugin/JsFactory`、`plugin/JsElement`、`plugin/Plugins`、`plugin/LoadedPlugin` | dex 类名 |
| HTML 解析 | `plugin/JsElement` + `JsFactory`（把 `parseHtml` 抽象成 JS 可见的元素对象，支持 `first()/absUrl()`） | 见 §3.4 调用点 |
| 内置源 | `assets/builtin/CloudDrives`、`assets/builtin/Radio` | apk 目录 |
| 统计 | 友盟（`lib/*/libumeng-spy.so`） | so 名 |

对照：**HanCast 的契约是「程序不携带任何内置规则」**，ssts 反而随包内置了 CloudDrives/Radio 两类源。这是设计取向差异，记录在此以免以后误抄。

### 3.2 嗅探：Android 不注入，走 `shouldInterceptRequest`

三个 dex 里 `tsSniff` **命中 0 次**，而 `WebViewClient.shouldInterceptRequest` 在 `classes2.dex`、`classes3.dex` 各出现一次。

也就是说 mac 那套 monkey-patch 注入脚本在 Android 上**根本没有**：Android 用原生 `shouldInterceptRequest` 拦截 WebView 发出的每一个子请求（拿得到 URL 和请求头），再交给 JS 侧的 `validate` 回调判定是不是要的媒体。

两种机制的取舍，直接决定我们 Android 端要不要写注入脚本：

| | mac：注入 monkey-patch | Android：`shouldInterceptRequest` |
|---|---|---|
| 覆盖面 | 能抓到 **blob:/MSE** 类不落网络的播放（挂 `HTMLMediaElement.src` setter） | 只能抓到**真的发出 HTTP(S) 请求**的资源 |
| 实现量 | 要维护一份注入 JS（hook `play`/`src`/`XHR.open`/`fetch` + 资源时间线轮询） | 原生回调，几行代码 |
| 抗改版 | 站点改播放器实现就可能失效 | 只要还是 HTTP 拉流就稳 |
| 拿请求头 | 拿不到（只有 URL） | **能拿到**（Referer/Cookie/UA 一并可见） |

结论：Android 端首选 `shouldInterceptRequest`，blob/MSE 站点再补注入 hook。

### 3.3 `core/WebViewService`：单个懒获取 WebView + 轮询取结果

dex 里能看到这几个合成类名，等于把实现结构写在了脸上：

```
com/wang/ssts/core/WebViewService$obtain$view$1$1
com/wang/ssts/core/WebViewService$obtain$view$1$3
com/wang/ssts/core/WebViewService$render$poll$1
com/wang/ssts/core/WebViewService$sniff$poll$1
```

- `obtain$view`：**懒获取并复用一个 WebView 实例**（不是每次新建，WebView 冷启动几百毫秒起）
- `render$poll` / `sniff$poll`：render 和 sniff 都是 **挂起 + 轮询** 拿结果——因为 WebView 回调在主线程、插件 JS 在 Rhino 线程，中间必须跨线程等

这套模型我们 Android 端可以直接照抄：**一个常驻隐藏 WebView + 请求 id 表 + 轮询/挂起等待 + 超时**。HanCast 现在的 Python sidecar 在 Android 上跑不了（没有 CPython 运行时），所以 Android 端要么把解析层用 Kotlin 重写，要么走 Termux 式打包，这是比「嗅探怎么做」更早要定的架构问题。

### 3.4 Cookie：三个 Store + WebView/HTTP 双罐同步

```
core/CookieStore          （接口）
core/MemoryCookieStore    （内存罐）
core/WebViewCookieStore   （WebView 罐）
android.webkit.CookieManager / androidx.webkit 的 WebViewCookieManagerBoundaryInterface
java.net.CookieManager    （给 okhttp / HttpURLConnection 用）
```

**关键设计点**：浏览器里的 Cookie 和 HTTP 客户端的 Cookie 是两套存储，必须双向同步，否则会出现「用户在 WebView 里登录成功了，插件用 okhttp 发的请求却没带 Cookie」——这是所有「WebView 登录 + 原生请求」架构都会踩的坑。ssts 用三个 Store 把它显式化了。

HanCast 现在只有包级 `cookies.json` 一个罐子（v2.3.6），等浏览器通道落地后必须补上「WebView 罐 → HTTP 罐」的同步。

### 3.5 `ui/WebScreen`：给用户的「去登录 / 去验证」门

`ui/WebScreen` 是一个 Compose 界面，把 WebView 直接摊给用户看。用途是站点要求登录或弹人机验证时，让用户在真实浏览器里自己过。插件侧不需要知道这个过程，过完之后 Cookie 已经落进 WebView 罐，同步给 HTTP 罐即可复用。

HanCast 目前完全没有这一环：解析失败就只是失败（v2.3.6 起会记进按域名分类的失败台账）。**「失败台账 → 一键打开浏览器让用户过验证 → 回来重试」是一条完整的产品链路**，比单纯做嗅探更值。

### 3.6 插件真实用法统计（能力不是摆设）

`plugins/ShunSources/*.js` 里 host 能力的调用次数：

```
42  host.getJson(      14  host.parseHtml(     14  host.getString(
 7  host.render(        5  host.sniff(          5  host.cookies(
 3  host.md5(           3  host.getHtml(        2  host.webViewUA(
 2  host.uuid(          2  host.status(         2  host.fetch(
 1  host.finalUrl(      1  host.aesEcbDecrypt(
```

`render` 7 次、`sniff` 5 次、`cookies` 5 次、`webViewUA` 2 次——**浏览器通道是主力能力**。我们的 #51（微博、快手/西瓜）写不出来，缺的正是这四个口，不是算法。

### 3.7 从调用点反推的 API 契约

```js
// cms.js：播放页要执行脚本后才有音频地址
return host.render(url, {
  desktop: true,
  parse: function (html) {
    var src = host.parseHtml(html, site).first('#jp_audio_0').absUrl('src');
    return src.replace('.../nyts.php?uid=', '.../uploads/');
  }
});

// common.js：正则取不到就回退 WebView 嗅探
return host.sniff(url, { desktop: desktop, validate: Shun.containsAudioExt });
```

契约要点（我们实现时照抄）：

- `render(url, opts)`：`opts.desktop` 切桌面/移动 UA；`opts.parse(html)` 由**宿主**在页面加载完后回调，返回值即 `render` 的返回值；没给 `parse` 就返回 HTML。
- `sniff(url, opts)`：`opts.validate(url)` 由宿主对每个嗅到的候选地址回调，返回真值的第一个即结果；不给 `validate` 就按内置规则（媒体扩展名/MIME）。
- `webViewUA()`：宿主没实现时返回空字符串（旧版兼容），插件自己判断要不要降级。

## 5. HanCast 的差距与两条补齐路线

### 已经补上的（v2.3.6）

- 签名原语一整套进沙箱：`md5/sha1/sha256/sha512`、`hmac*`、`aesEcb/aesCbc`、`rsaEncrypt(PKCS#1 v1.5)`、`hex/base64` 互转（`docs/解析插件开发指南.md` §3.5，向量对过 Node 的输出）
- 包级 Cookie 罐：`host.cookies(url)` / `setCookie(url, str)` / `clearCookies(url?)`，落在各包目录的 `cookies.json`（§3.6）
- 设备身份：`host.deviceId()` 恒定 32-hex 存盘（`utils/identity.py`）
- **UA 单一来源**：以前规则里写 Chrome/124、本机代理另写 Chrome/120，同一次投屏向源站报两个浏览器；现在桌面/移动 UA 都走后台参数 `http.ua_desktop` / `http.ua_mobile`
- 解析失败台账（按域名分类，`media/failures.py`）——以后挑站点写规则包的清单来源

### 路线 ①：TLS / JA3 指纹伪造（v2.3.6 已落地）

原问题：请求全走 `requests`（urllib3），JA3 一眼就是 Python 客户端。**统一 UA 只止住了「自己跟自己不一致」，没有伪装成浏览器**——站点拿「UA 声称 Chrome 124 + TLS 握手像 urllib3」这一对差异，反而比 UA 五花八门时更容易判定为机器。

落地：`hancast_sidecar/utils/httpclient.py`。

- `make_session()` 是唯一的会话工厂，解析链路（`share_resolver` 的 `with make_session()`）与沙箱 `host.fetch`（`RuleContext.session` 由同一条链给出）都从这里取；`CurlSession` 可用就走 curl-impersonate（BoringSSL），装不上 wheel 或后台参数关掉就退回 `ResilientSession`（requests），调用方拿到的是同一套 requests 语义。
- **指纹跟着 UA 走，不是写死一个 Chrome**：`fingerprint_for(ua)` 从 `curl_cffi` 的 `BrowserTypeLiteral` 现读版本表（升级即自适应），按「≤ UA 声称主版本里最新的那个」挑 impersonate 目标；Edge/Firefox/Safari/Chrome 与 android/ios 子家族各走各的。认不出版本的 UA（例如 `curl/8.4.0`、`Chrome/60` 这种表里没有的旧版）**不伪装**——宁可露出 libcurl 的指纹，也不要「UA 说 Chrome 60、握手说 Chrome 136」这种新的自相矛盾。
- 四处 `curl_cffi` 与 requests 的真实分歧都在 shim 里补齐（模块 docstring 逐条记了取证）：`Response` 没有 `__enter__/__exit__`；非 stream 时 `iter_content` 直接 assert 报错；`Cookies.__iter__` 给的是名字字符串而不是 `Cookie` 对象（`.domain` 还得从 `Set-Cookie` 头重建，否则 `_harvest_cookies` 收不到带域名的罐子）；异常体系 `RequestException→CurlError→OSError` 与 requests 无继承关系，故按同名翻译成 `requests.exceptions.*`。
- 代理：`proxies={"http":"","https":"","all":""}` 才是 curl_cffi 的「禁用环境变量代理」（空串，不是 requests 的 `None`）；`_proxy_for` 用 `getproxies()/proxy_bypass()` 补 macOS 系统代理，代理坏了一次性改直连。

验证（`tools/probe-tls-ja3.py`，本机回环抓 ClientHello）：

| 路径 | JA3 |
|---|---|
| requests(urllib3) | `cc72499093ca5c378fbce51843faf0eb` |
| `make_session()` + Windows Chrome/124 UA | `73e88c3cd8d86fe0bee8a7f8dffa0ac6`（= curl_cffi[chrome124]，逐字节同指纹） |
| `make_session()` + iPhone Safari/17.2 UA | `d813438e5112e34b9e168dd87244101e`（换 UA 即换指纹） |
| `make_session()` + Chrome/60（表里没有） | `46bef8d0f4876aab35e8e77ae32feace`（不伪装，libcurl 指纹） |

打包：`pyproject.toml` 加 `curl_cffi>=0.16.3`，`scripts/build_sidecar.py` 加 `--include-package=curl_cffi --include-module=_cffi_backend`（漏了 `_cffi_backend` 会打出「能跑但 JA3 仍是 Python」的包，因为顶层 `curl_cffi` 一 import 就要它）。三端 wheel 用 `uv pip install --dry-run --python-platform` 验过（aarch64/x86_64 linux、aarch64 darwin、win msvc 均可解析）。开关：后台参数 `http.tls_impersonate`（默认开，关掉无需重编译）。

遗留（本轮刻意收窄范围，下一轮再并入）：`media/server.py:upstream_get` 与 `jsplugins.py` 的规则包索引/下载仍走 plain `requests`——那是「本机代理转发」和「拉规则包」，不是站点风控判定的现场，指纹露不出问题；真正对站点的两条路（解析 + 沙箱 fetch）已全部走工厂。

### 路线 ②：浏览器通道（render / sniff / webViewUA / WebView Cookie）

做法：Rust 侧用 `WebviewWindowBuilder` 建一个离屏 webview（macOS = WKWebView，Windows = WebView2，Linux = webkit2gtk），装载规则包要的页面 → `on_page_load` 等加载完 → `eval()` 注入嗅探脚本（照抄 ssts 的 monkey-patch 清单）→ JS 用 `__TAURI_INTERNALS__.invoke` 把 HTML/候选地址回报 Rust → Rust 经 stdin 把结果送回 sidecar（sidecar 用 `browser_request` 事件发起、`browser_result` 命令回收，worker 线程上等 `threading.Event`）。

两个已知坑：

- **隐藏页 rAF 不触发**：`visible(false)` 的 webview 里 `requestAnimationFrame` 可能不跑，靠 rAF 加载的站点会永远停在骨架屏 → 用「可见但离屏（坐标挪出屏幕）」而不是真隐藏。
- **回传通道必须走原生 IPC**：让页面 `fetch` 回本机端口会被站点 CSP 的 `connect-src` 拦掉，`new Image()` 回传会被 `img-src` 拦掉；`webkit.messageHandlers` / Tauri IPC 是原生注入，不受页面 CSP 约束。

### 优先级建议

路线 ① 已完成（见上一节，指纹跟随 UA）。路线 ② 才是真正解锁 #51 微博/快手/西瓜的东西，也是 Android 端的前置（Android 上同样要 WebViewService + Cookie 双罐 + WebScreen 这三件）。

## 6. 复现命令

```bash
hdiutil attach -nobrowse -readonly /tmp/ssts-evidence/ssts-mac-5.0.dmg -mountpoint /private/tmp/sstsmnt
APP="/private/tmp/sstsmnt/随身听书.app"

# 架构与框架链接
lipo -archs "$APP/Contents/MacOS/ssts-mac"
otool -L "$APP/Contents/MacOS/ssts-mac" | grep -iE "webkit|javascriptcore"

# mac 的桥函数名与注入脚本
strings -a "$APP/Contents/MacOS/ssts-mac" | grep -E "^__n_|tsSniff" | sort -u

# 解 apk（unzip 即可，dex 用 strings 扫）
mkdir -p /tmp/ssts-evidence/x && cd /tmp/ssts-evidence/x
unzip -o ../ssts-v5.apk > /dev/null

# 三端 prelude.js 是否同一份
cmp prelude.js "$APP/Contents/Resources/prelude.js" && echo IDENTICAL

# Android 的关键判据
cat classes*.dex | tr -c '[:print:]' '\n' | grep -c tsSniff        # 0 = 不注入
strings -a classes3.dex | grep -c "org/mozilla/javascript/Context"  # 93 = Rhino
strings -a classes3.dex | grep -E "Lcom/wang/ssts/(core|plugin|ui)/[A-Za-z]+;" | sort -u

# 插件用了哪些 host 能力
grep -ohE "host\.[a-zA-Z]+\(" /tmp/ssts-android/plugins/ShunSources/*.js | sort | uniq -c | sort -rn

# 路线① 的判据：真实代码路径的 JA3（本机回环抓 ClientHello，不碰外网）
hancast-backend/.venv/bin/python tools/probe-tls-ja3.py --client both
hancast-backend/.venv/bin/python tools/probe-tls-ja3.py --client hancast \
  --ua "Mozilla/5.0 (iPhone; CPU iPhone OS 17_2 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/17.2 Mobile/15E148 Safari/604.1"
```
