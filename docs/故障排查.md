## 1. 三步定位法

1. **先分清是哪一层**：命令名在不在 `commands.ts` → 事件有没有从 `commands.py` 出来 → 端口有没有绑上。三层各有日志面：dev 终端（stdout/stderr）、`<配置目录>/logs/hancast.log`、壳层 `eprintln!`。
2. **再分清是源码问题还是产物问题**：打包版的行为**只以打包版为准**。同一份代码，dev 能过不代表产物能过（`mpv`/`sidecar` 副本、签名、资源 glob 都可能不同；FFmpeg 自 v2.3.11 起不在产物里，见 §6.6）。产物级判据用 `tools/accept-macos-artifact.sh` 这类脚本，不接受「我看源码是对的」。
3. **最后跑对应取证脚本**（`tools/`，索引见 [tools/README.md](../tools/README.md)）。修 bug 前先复现，修完再证明。

配置目录：Windows `%APPDATA%\HanCast`、macOS `~/Library/Application Support/HanCast`、Linux `~/.config/hancast`（`config.py:22-27`）。

## 3. 设备发现类

### 3.1 一台电视都搜不到

**判据**：`python tools/ssdp_probe.py` 能不能看到任何通告；日志有没有 `SSDP bound to port 1900`（`ssdp.py:438`）与 `SSDP listening on port 1900`（`ssdp.py:451`）。

排查顺序：

1. **网卡**：设置页选对接口（`config.network_interface`，`config.py:106-109`）。多网卡/VPN 机器不选，通告会从错误的口出去。`list_network_interfaces` 给出候选。
2. **macOS 本地网络权限**：系统设置 → 网络 → 本地网络。打包版要在 Info.plist 里声明 `NSLocalNetworkUsageDescription` + `NSBonjourServices`（`8eaca95`，v2.2.12），并且**必须 adhoc 深签**才解锁组播（`c983c4e`，v2.2.14）。dev 模式下 `cargo tauri dev` 的临时 bundle id 与产物不同，授权不通用。
3. **组播被拦**：NOTIFY 走组播失败时会自动回退**子网广播**（`ssdp.py:844-851`、`_notify_broadcast` `ssdp.py:860-885`，`ca3e558` v2.2.7）。日志会记本次走的通道（`_notify_channel`，`ssdp.py:171`）与失败的 `errno`。
4. **兜底**：设置页「手动添加设备」，接受 `IP`、`IP:端口` 或完整 `description.xml` URL（`config.py:177-181`，`commands.py:369`）。重启后由 `commands.py:219` 的恢复线程重建（`304a1fa` v2.2.10）。

### 3.2 只搜到部分设备

| 原因 | 处置 |
| --- | --- |
| 设备响应慢 | 调大 `discovery.ssdp_mx`（默认 3s，`params.py`「组播搜索等待上限」） |
| 跨 VLAN / 多层路由 | 调大 `discovery.multicast_ttl`（默认 2，DLNA 惯例只在本地网段） |
| 电视描述抓取超时 | 见 §10.3（代理劫持） |

重试与代际逻辑在 `test_ssdp_discovery_retry.py` 里有契约；`restart` 的串行化与代际守卫见 `e1655bc`。

### 3.3 列表里出现自家 HanCast（幽灵设备）

根因：收到的通告 `LOCATION` 指向本机，被当成外部设备抓走。修法：忽略自家通告回环（`d3f0151`）。替身设备做取证时 **LOCATION 必须写 `127.0.0.1`**，否则会命中这层自通告过滤，看起来「脚本没生效」。

### 3.4 设备下线了还显示在线

现在有三条摘除路径（`87b109b` v2.3.5 补的「只加不减」）：

1. `ssdp:byebye` → 立刻摘除（路由 `ssdp.py:628-629`，处理 `ssdp.py:746-759`）；
2. `ssdp:alive` → 刷新「最近见过」时间戳（包括去重窗口内没重抓描述的那次）；
3. 静默超过 `discovery.device_stale_s`（默认 90s）→ 主动 GET 描述地址探活（`ssdp.py:768`），连续两次失败才判死。

**真机很难造出 byebye**：真 sidecar 被杀时会补发告别通告。要验静默下线只能用替身设备，脚本 `tools/verify-ssdp-offline-eviction.py`（实测死亡→摘除约 147s）。

### 3.5 列表里出现路由器/NAS 这类投不了的设备（v2.3.13 修复）

**先澄清一个误解**：HanCast **不做端口扫描**。设备只来自 SSDP（NOTIFY 与 M-SEARCH 响应，§3.1），逐条去抓 `LOCATION` 指向的 UPnP 描述文件；`_MANUAL_PORTS`（`ssdp.py:1233`）只是「手动添加」时猜端口用的候选列表，不是扫描。路由器/ NAS 自己也跑 UPnP 栈（IGW、MediaServer），所以它们的通告本来就该被收到——问题不在发现，在**准入**。

根因：旧版 `_parse_device_description` 只要描述里有 UDN 就登记成投屏目标。本机日志里的实锤是 `Found device via NOTIFY: 荣耀路由X1 增强版 (192.168.1.250:37215)`——它和电视混在同一张表里，点上去必然失败。

修法（v2.3.13）：准入改成**按投屏服务识别**——整份描述（含内嵌设备、命名空间无关、大小写不敏感）必须出现 `urn:schemas-upnp-org:service:AVTransport:`（常量 `ssdp.py:1095`、判定 `ssdp.py:1097-1111`、门槛 `ssdp.py:1190-1196`）。`deviceType` 只当展示标签，不作门槛：各厂商写法太杂，只有提供 AVTransport 才可能被投屏控制。手动添加走同一条门槛，报错文案点名准入条件（`ssdp.py:1252-1256`），免得用户手输路由器后台地址时以为是自己格式填错。

判据：`hancast-backend/.venv/bin/python tools/verify-ssdp-cast-gate.py --source` 起两台替身——带 AVTransport 的必须进列表，不提供该服务的那台（MediaServer 描述 + XML 注释）必须被挡在门外并留理由。不带 `--source` 则读**已安装产物**的 sidecar 日志，用来证明修复到了打包版（v2.3.12 产物上这一步是 FAIL，正是本次缺陷的复现）。

顺带被这条门槛抓出来的真 bug：lxml 里注释/处理指令节点的 `.tag` 是**可调用对象**而非字符串，早先的服务遍历在其上抛 `AttributeError`，被外层宽 `except` 吞成「描述 XML 解析失败」（`ssdp.py:1102-1105` 的 `isinstance(tag, str)` 守卫 + `test_ssdp_cast_service_gate.py::test_xml_comments_do_not_break_the_service_scan` 回归锁）。**表现是「带注释的合格电视从列表消失」而不是报错**，所以这条必须有独立用例。

日志噪音：路由器每 30s 重播一次 NOTIFY（去重窗口 `fetch_dedup_window`，`ssdp.py:185`），因此拒绝理由按 location 去重——同一地址首次 INFO/WARNING、之后 DEBUG（`ssdp.py:1113-1124`），否则日志面板一天要被它刷掉上万行。

## 4. 发送投屏类

### 4.1 「投屏到电视只成功过一次」

现象：第一次能投，之后控制请求电视回 **500**，但同一份 URI 在第三方 App 里能投。

根因：我们发出的 SOAP 信封缺 `s:encodingStyle`。部分机型（日志里留了型号 **TCL 85T8G Max**）只认带 SOAP 1.1 encodingStyle 的信封，缺了就 500，而它**并不体现在错误文本里**。修法与实测记录：`dlna.py:1174-1180`（`99260b5`，v2.2.15）。

判据：抓一次控制请求的 XML，看 `Envelope/Header/TransactionAction` 上有没有 `s:encodingStyle="http://schemas.xmlsoap.org/soap/encoding/"`。回归看 `test_dlna_control_url.py`。

### 4.2 解析成功但黑屏 / 「Errors when loading file」

根因：本地代理转发时 `_peek_upstream` 为了判类型会**多读最多 1KB**，旧代码把多读的部分裁掉再返回，等于从流中间挖掉约 908 字节。B 站 mp4 的 `moov` 在文件尾，缺这段 mpv 直接报错。修法：原样返回读走的全部字节（`media/server.py:562`，调用点 `media/server.py:483`、`media/server.py:494`，`87b109b` v2.3.5）。

判据：逐字节核对转发总长度（该提交的测试用「peek 窗口跨 chunk」的桩覆盖了这条）；或直接 `curl` 代理 URL 比对源站 `Content-Length`。

### 4.3 投屏卡片封面破图

根因：Tauri 页面是安全上下文（`tauri://localhost`），B 站 `data.pic` 下发的是 `http://` 图，被 WKWebView 按混合内容拦掉。修法：所有封面生产者都过同一个 dataclass，在 `MediaInfo.__post_init__` 里统一升级到 https（`models/media.py:7` `secure_thumbnail`、`models/media.py:35-36`，`87b109b`）。

排错时别在规则包里逐个改——**收口点只有这一处**。

### 4.4 电视拉不到本地文件

根因：投本地文件走 `MediaServer`，如果没选网卡，`base_url` 用的是默认路由 IP（多网卡/VPN 机器上往往不是电视所在网段）。见 `commands.py:69-72` 的注释与 `media/server.py:648`。

判据：日志 `Media server started on <ip>:<port>`（`media/server.py:660`），手动在电视浏览器打开该 `m3u8`/文件的 URL。端口是随机的（`media/server.py:646`），不要按 8080 猜。

### 4.5 进度/Seek 不工作

不是每台设备都实现 `Seek`/`GetPositionInfo`。前端有进度模拟（`stores/cast.ts`），停止只由 `cast_state_changed` 处理、轮询不会摘会话（`pollSessions` `:243-293` 只写状态，`removeSession` 只有停止 `:468` 与事件 `:713` 两条调用路径）。若状态一直不动，看 §5.2 的送达判据。

## 5. 接收投屏类

### 5.1 弹窗没出现 / 点了没反应

判据顺序：

1. 日志有 `Unknown device requesting cast: <ip>`（`guard.py:236-238`）吗？没有就是**根本没走到 Guard**（受信名单命中，直接放行）。
2. 有 `cast_confirm_request` 事件吗？前端订阅在 `src/stores/guard.ts:126`。
3. 同一 IP 的第二个请求会被去重合并（`guard.py:240-242`），不是「丢了」。
4. 超时自动拒绝的秒数来自 `device_guard.confirm_timeout`（默认 15，`config.py:202-209`），弹窗倒计时与它同源。

细节见 [投屏确认.md](投屏确认.md) §2、§4。

### 5.2 停了但电视还在放

这是**送达问题，不是本地没停**。代码会在本地停完之后如实检查设备是否确认，未确认的列进 `control_failed`/`reasons`（`commands.py:553-570`），前端用 `StopWarningBanner` 显示。别把它当 UI bug 关掉——它在告诉你控制请求没生效。取证脚本：`tools/verify-dlna-stop-chain.py`（`95375c8`）；契约测试 `test_stop_cast_delivery.py`。

### 5.3 手机音量键没反应

渲染端要处理 `RenderingControl` 的 `SetVolume`/`SetMute`：`dlna.py:806-813`（此前只挂了服务、动作没落地，`3181082` v2.2.18 一并修）。判据：日志有没有 `SetVolume: <n>`（`dlna.py:808`）。

### 5.4 别人投给我，日志只有 `SOAP error: XML declaration allowed only at the start of the document`

**症状**：手机/另一台电脑往本机投屏，对端报「投不上」，本机既没弹确认框、也没红条；程序日志里只有一行 lxml 原文，连是哪个设备发的都看不到（2026-10-25 现场：14:09–14:14 六次，全在投屏那一刻）。

**根因**：控制点把 `<?xml version="1.0"?>` 前面垫了空格再 POST。XML 规范规定声明必须在文档最开头，libxml 严格照办。**报错的列号能直接反推报文形态**：列 = 声明真实起始列 + 5，所以 `line 1, column 22` = 前面正好 16 个字符（本地用打包同款 lxml 逐个试出来：16 空格 → column 22，17 空格 → column 23，BOM 则根本不报错）。

旧代码在这里是直接炸的：`etree.fromstring` 在 `DLNAProtocol.call()` 里**没有 try**（原 `dlna.py:590`），异常冒到 `server.py` 的兜底 catch，回一个裸 HTTP 500。代价是**动作分发根本没走到**——`AVTransport_SetAVTransportURI` 里的 Device Guard 也就没机会弹框（§5.1），日志里既无 `SetAVTransportURI:` 也无 `Unknown device requesting cast`。

**现在的行为**（2026-10-25 改）：

| 情况 | 处理 | 位置 |
| --- | --- | --- |
| 前导空白 / UTF-8 BOM | 剔掉继续处理，打一条 WARNING 点名对端 IP 与字节数 | `dlna.py:48-68`（`strip_soap_leading_junk`）、`dlna.py:628-632` |
| 剔完仍解析不了 | 回 **SOAP Fault 402**（HTTP 仍 200，body 带 `errorCode`），不再裸 500 | `dlna.py:633-641` |
| 信封之外的意外 | 兜底 ERROR **自带取证**：对端 IP、`SOAPAction`、path、字节数、body 前 200 字符 | `protocol/server.py:178-192` |

前 200 字符只进日志不落盘全文——DIDL 里可能带 URL 和标题。取证的动机是：SOAP 的 Action/Body 原先只在 debug 级（`server.py:159-160`），面板默认 INFO，所以事后什么都不知道，只能拿列号反推。

**判据**：日志出现 `SOAP body from <ip> 带 N 字节前导空白/BOM` = 已容错放行，投屏应当成功；出现 `Unparseable SOAP envelope from <ip>` = 报文真坏了，同一条日志里带 body 前缀可直接定位是哪个客户端。契约测试 `tests/test_dlna_soap_envelope_leniency.py`。

**顺手要排除的混淆项**：如果日志里连这条都没有，那是**入站请求压根没到本机**——查 §3.1（组播/网卡/macOS 本地网络权限）和对端设备列表里有没有本机；如果是本机投不出去，看 §4.1（我们发出的信封缺 `s:encodingStyle` 会让**对端**回 500，症状相反）。

### 5.5 本机解析成功、投 TCL 电视「点了没反应」，投另一台 Linux/HanCast 正常

**症状**（2026-10-28 现场）：粘一条抖音分享文案（`https://v.douyin.com/cAS0o-smMyw/`），解析出直链、日志里 `Created cast session` 都有，但那台 **TCL 85T8G Max** 一次画面都没有；同一时间投给局域网上另一台跑 HanCast 的 Linux 机器（mpv 接收端）能正常播。**全程 0 条 ERROR/WARNING**——因为旧的出站 `_send_action` 成功只打 debug 级，`logger.debug(f"SOAP OUT → …")`（`dlna.py:1184` 附近），面板默认 INFO 看不到（v2.4.5 起成功也打 INFO 一行 `<code>SOAP OUT ← …`，见 §5.6）；`SetAVTransportURI:` / `Play` 这类 INFO 是**入站**处理器日志，不代表我们发出去了。

**根因（真机矩阵锤出来的，判据看服务端有没有出现电视的 GET）**：**这台 TCL 完全无视 DIDL 的 `protocolInfo`，只按 URL 路径后缀决定要不要发起拉流；末尾没有播放器认识的扩展名，它连魔数都不读、一次连接都不发。** 用本机可控信源（同字节 MP4、同 `Content-Type`）实测：`/ext/test.mp4`、`/ext/test.mp4?vid=1`、`/proxy/a1b2c3.mp4`、甚至把 MP4 字节挂成 `/proxy/a1b2c3.ts` 都能拉；换成 `/noext/stream?vid=1`（同字节、带满 DIDL）**零连接**。抖音 CDN 直链路径正是 `…/video/tos/cn/tos-cn-ve-15/<hash>/`（**末尾是斜杠、无后缀**）→ 电视永不拉 → 界面「投不上」。而 B 站直链带 `.mp4`（历史样本 `http://cn-sccd-ct-02-07.bilivideo.com/upgcxcode/…`），Linux 那台用 mpv 不看后缀，所以两边差异全由此解释。

> 排错途中被证伪的两个假设，别再走一遍：① **不是 IPv6**——本机起 IPv6-only 服务，TCL 用 GUA 正常拉流；② **不是空 DIDL**——带 DIDL 与空 `CurrentURIMetaData` 都能播。另外**同一条抖音签名地址反复投喂约 10 次后会被 CDN 判废**，之后电视对 v4/v6 全回 `00:00:00`，所有读数作废——必须换自己完全可控的信源、一次只动一个变量。

**现在的行为**（2026-10-28 改）：交付直链前过一道**后缀门**——`_tv_can_fetch()` 里若 `player_ext_ok(url)` 为假（无后缀也算不合格），改走本机代理，由 `player_safe_suffix(uri, mime)` 给代理路径补上合规后缀（按 MIME 选 `.mp4`/`.ts`…，字节仍是上游原样，播放器靠魔数判型）。例外：正文是播放列表却没被 `_playlist_mime` 认出来的（站点报脏 MIME）维持直链，避免把列表骗成视频文件。顺带修了 `models/session.py` 的 `play()` 丢掉 `mime_type` 的老问题——媒体投屏的 `CurrentURIMetaData` 此前恒为空串，现在按 MIME 生成 DIDL。

| 位置 | 作用 |
| --- | --- |
| `media/server.py:110` `player_ext_ok()` | 后缀白名单（无后缀算不合格），HLS 分片与交付直链同一把尺子 |
| `media/server.py:132` `player_safe_suffix(url, mime="")` | 代理路径补后缀：远端后缀合规就用，否则按 MIME 兜底 `.ts` |
| `media/share_resolver.py:514-515` | 后缀门：`not player_ext_ok(url) and b"#EXTM3U" not in head[:512]` → 改代理 |
| `models/session.py` `play()` | `mime_type` 不再就地丢，按 MIME 生成 `build_didl_item` 的 metadata |

**判据**：日志出现 `直链路径没有播放器可识别的后缀（…），改走本机代理` = 后缀门生效、改走代理；随后 `Proxy request: /proxy/<hash>.mp4 → …`、`Proxy response: status=206`、`Proxy done: N bytes forwarded`，电视 `TrackDuration` 非 `00:00:00` 且 `AbsTime` 前进即成功。契约测试 `tests/test_tv_url_suffix.py`。

### 5.6 电视没反应，日志里又找不到原因：投屏失败台账 + 出站 INFO 日志

**症状**：解析成功、界面点「投屏」也没报错，但那台电视就是不动；事后翻后台日志面板，默认 INFO 级别上一个字都看不到我们到底把请求发给谁、电视回了什么。

**根因（历史痛点）**：出站 SOAP 过去成功只打 DEBUG（`logger.debug(f"SOAP OUT → …")`，`protocol/dlna.py:1184`），而面板默认 INFO；失败也是散在各处、不成台账。COMP-005（无后缀直链电视不拉流，见 §5.5）之所以查了大半天，就是因为整条出站链路无痕。

**v2.4.5 起的三处改进**：

| 改进 | 位置 | 说明 |
| --- | --- | --- |
| 出站动作收成 INFO 一行 | `protocol/dlna.py:1256-1258` | 每次出站动作成功都打 `<code>SOAP OUT ← <status> | <action> | <device> | <ms>ms`，面板默认 INFO 直接可见 |
| 投屏失败台账 | `media/cast_failures.py`（132 行） | 「解出来了、发出去了，但没成功」时记一条：设备 / 阶段 / 错误原文 / 目标地址 / 时间；阶段见 `STAGES`（connect / set_uri / play / stop / media_ready / cast）。只写本机配置目录 `cast_failures.json`，**不外发、不进日志**（里面是用户投过的地址） |
| 直链有效性预检 + 自动重解 | `commands.py:826`（`_probe_url`）+ 前端 `MediaInput.vue:601` | 历史条目重投前先 `probe_url` 探一下直链是否还在（过期/被 CDN 判废会提前暴露）；历史里的 url 条目重投自动回来源页重解 |

**看哪里**：后台日志面板新增「**投屏失败台账**」区（`components/LogsPanel.vue`，命令 `cast_failure_list` / `cast_failure_clear`，中英双语文案 `logs.castFailures*`）；出站 INFO 就在它上方的日志流里。

**判据**：面板「投屏失败台账」出现条目 = 电视那侧断在某个阶段——`connect` 控制地址不可达、`set_uri` SetAVTransportURI 被拒、`play` Play 被拒、`stop` Stop 未送达、`media_ready` 媒体加载超时（电视没开始缓冲）、`cast` 其他异常；再对照上方 `SOAP OUT ← <status>` 的 HTTP 码与耗时定位。契约测试 `tests/test_cast_failures.py`。

### 5.7 队列 / 播完即停 / 睡眠定时 / 手机遥控器 / 字幕，出问题先看哪里

这五样都是 v2.4.6 新增，绝大多数是**前端状态**，日志里本来就少；判据按“看哪里”分：

| 功能 | 出问题时的判据 / 看哪里 |
| --- | --- |
| 队列追加 + 跨重启持久化 | 前端 `localStorage` 的 `hancast.playlist.queue`（`src/stores/playlist.ts`）。刷新/重启后队列空了 = 该键没写上（隐私模式或磁盘配额），不是投屏故障 |
| 播完即停 / 睡眠定时 | 切集由前端 `castStore` 的 `cast_state_changed` 驱动（`status == 'stopped'` 且当前进度≈结尾）；定时到点调 `stopCast`，失败走既有的“停止未送达”系统通知（见 §5.1）。日志侧只会在真正 stop 失败时出现 `Stop 未送达` 一类告警 |
| 手机遥控器页 | 后端日志 `[Remote] 遥控器页已启动: http://<ip>:<port>/r/<token>/`（`remote/server.py:258`）；起不来是 `[Remote] aiohttp 不可用`（`:221`）或端口全忙（`:245` 逐口 warning）。手机打开 404 = token 不匹配（每次启动新 token，旧链接作废）；页面能开但按钮无反应看 `[Remote] 指令 <action> 失败`（`:339`）与 `[Remote] 取状态失败`（`:322`） |
| 外挂字幕内封 | `[Subtitles] 开始内封` / `[Subtitles] 内封完成`（`media/subtitles.py:99,132`）；失败是 `[Subtitles] 内封失败: …`（`commands.py:811`）+ 前端弹窗显原文。最常见原因：本机没装 FFmpeg（先在「运行依赖」装）、源不是本地文件（网络流不 remux）、字幕格式不在 srt/ass/ssa/vtt。内封完成会重投同一台电视并从原进度继续，重投失败会在日志留 `[Subtitles] 重投后跳回原进度失败`（`commands.py:807`）——那说明**字幕已封好**，只是跳转没成功，可在电视上手动拖回 |

> 队列/睡眠定时/遥控器都**不改投屏协议**：它们只是替前端触发 `start_cast` / `stop_cast` / `seek_cast`，所以电视侧的问题仍然回到 §5.1–§5.6 去查。

### 6.2 没声音

1. **Windows 系统声音**：FFmpeg 没有 WASAPI 输入（上游 ticket #9408 未合并，`pyproject.toml:16-19`），所以走 PortAudio 环回。**静音渲染端点可能整场一个字节都不给**，把 `amix`/HLS 饿死成「超时未生成」。修法是环回按单调时钟补静音（`c97ff52`，v2.2.25）；对照脚本 `tools/verify-win-loopback-feed.cmd`。
2. **到底该选哪个环回**：枚举里标了「当前出声」的那一项（`1a2f862`）。选了不出声的端点等于采静音。
3. **音频顺序**：验收看 `tools/verify-screencast-audio-order.ps1`（分片是否真带声音，内容级判据 `748c501`）。
4. **macOS 系统声音**：走 `screencast/macos_tap.py` 的独立方案（不是 ffmpeg 能力，探测脚本 `tools/probe-macos-systap.py` + `tools/run-macos-tap-probe.sh`）。
5. **浏览器观看页没声音**（v2.3.14 修复）：与采集无关——v2.3.14 前 `www/index.html` 的 `<video>` 硬编码 `muted`，有画面但永远不出声。现在先试带声 `play()`，被浏览器自动播放策略拒绝才静音兜底并在页面出现「点击开启声音」按钮，点一下解除。验收 `tools/verify-watch-page-sound.mjs`（真实 Chromium 双 pass）。
6. **Linux 系统声音**（v2.3.19 起才有这条路）：抓的是输出总线自带的 `<sink>.monitor` 源（`-f pulse`），不装虚拟声卡。两种病态：**下拉是空的**＝本机没有 `pactl`（纯 ALSA，或没装 pipewire-pulse/pulseaudio），前端文案 `screencast.noSystemSoundLinux` 会直说；**有画面但永远静音**＝选到了闲置输出的 monitor（PipeWire 上每块输出各一条，跟 Windows 环回同一个病），认标了「（当前出声）」的那条。机制见 [屏幕投屏.md](屏幕投屏.md) §4.6，量化判据 `tools/verify-linux-wayland-cast.py --with-tone`（默认输出的 monitor 实测 −16 dB 到 −24 dB，闲置 HDMI 的 monitor −91 dB）。

### 6.3 一选麦克风/系统声音就投崩

根因：视频滤镜被写在所有输入**之前**，多输入时滤镜图引用不到后面的流。修法：把滤镜挪到全部输入之后（`68bbb29`，v2.2.23）。相关探针 `tools/probe-win-window-picker.py`、`tools/probe-ts-skin-offset.py`。

### 6.4 停止要等一秒 / 停止把 sidecar 打崩

- `close()` 只等 0.5 秒，静音设备上不再白等（`73a8345`）；
- 环回流改由**读线程**关闭，避免停止链路在主线程 join 打死进程（`05c1033`，v2.2.24）。

### 6.5 「超时未生成播放列表」

先看电视有没有来拉：`screencast.dlna_verify_seconds`（默认 12s）是确认窗口，老电视加载慢就调大它。观众计数按 `screencast.viewer_window_seconds`（默认 15s）内的独立 IP 算。分片粒度：浏览器通道 `screencast.browser_segment_seconds`（默认 1s，关键帧间隔自动跟随）、电视通道 `screencast.dlna_segment_seconds`（默认 2s，调到 1s 部分型号会黑屏——参数说明里写死了这个警告）。

### 6.6 「需要下载运行依赖」弹窗 / FFmpeg 检测不到

v2.3.11 起 FFmpeg **不随包**（`bundle.resources` 里已无 `ffmpeg/*`，CI 也没有下载步骤），运行时由 `utils/ffmpeg_deps.py` 定位。完整机制见 [屏幕投屏.md](屏幕投屏.md) §5.8。

| 症状 | 怎么看 |
| --- | --- |
| 装了却被判缺失 | 检测链是「手动指定（`ffmpeg_manager.py:416-427`）→ 系统已装 → 本程序下载的 `<配置目录>/bin/`」。系统已装那一路**不能只查 `PATH`**：winget 的 `Packages/<带版本号>` 目录从来不在 PATH，`Links` 按代码注释「常常只有新开终端才有」，macOS 上 Apple Silicon 的 Homebrew 在 `/opt/homebrew/bin`——所以有 `_extra_dirs()`（`ffmpeg_deps.py:60-91`）+ `search_dirs()`（`:104`）兜底。新加平台常见目录就改这里。⚠️ 但「PATH 不含」不是普遍成立：`.68` 实测装好的 sidecar 作为子进程时 PATH **已含** `Links`（判据见 [屏幕投屏.md](屏幕投屏.md) §5.8 的验收段），所以要在真机上造「没有 ffmpeg」得连 PATH 一起削。 |
| 刚装完点「重新检测」没反应 | 结果缓存 30s（`CACHE_TTL = 30.0`，`:36`；命中判定 `:199`）。弹窗的「重新检测」传 `refresh=True` 绕过缓存，命令是 `ffmpeg_status`；投屏状态轮询用 `refresh=false` 吃缓存，所以那一屏可能还是旧的。 |
| 只有 ffmpeg、没有 ffprobe | 正常。`REQUIRED=("ffmpeg",)`、`OPTIONAL=("ffprobe",)`（`:43-44`）——macOS 的 ffmpeg-static 产物就只有单文件。ffprobe 只影响本地文件时长探测（`probe_path()` `:254`，找不到退回裸命令）。手动指定 ffmpeg 时，同目录那份 ffprobe 会被自动认成搭档（`:220-225`）。 |
| 候选存在但跑不起来 | 每个候选必须真跑出 `-version` 才算可用（`read_version()` `:142-164`）。装了但依赖坏掉（缺 dylib/MSVC 运行时）会被判不可用——这不是 bug，报「未检测到」比启动后死掉好。 |
| 下载一直失败 | 弹窗里显示的是**原始异常链**，不是「下载失败」四个字：`format_error()`（`:308-323`）把 `__cause__/__context__` 拉直取前 3 段，`_run_download` 的兜底在 `:508-512`。连接失败走 `httpclient.make_session()`（`_open_stream` `:326-341`），与解析链路同一套代理策略——本机代理端口死了时这里同样会遭，日志模块名 `hancast.ffmpeg_deps`（`:29`）。 |
| 下载完却「跑不起来」 | 解包成功但 `ffmpeg -version` 失败 → 明确的 `DependencyError`（`:501-504`），意思是当前平台用不了这份构建（例如 32 位 Windows、或老 glibc），改用弹窗里推荐的安装命令。 |
| 界面停在「下载中...」但按钮禁用 | 轮询定时器挂在组件生命周期上，关面板即断；重新打开时 `resumeDownloadPolling`（`src/stores/screencast.ts:155-170`）会向后端对齐一次。若仍不动，看 `ffmpeg_download_status` 返回的 `stage`：`connecting`/`downloading`/`extracting`/`verifying`/`done`/`failed`（写入点 `ffmpeg_deps.py:493,495,498,506,512`）。**别拿同一份载荷里的 `status` 当阶段看**：它全程是 `pending`，那是任务表的早退闸门（`:450`，`pending` 期间不重复起线程），只有 `done`/`error` 两个终态会改写它。 |
| 升级后还在用旧版随包那份 ffmpeg | ①层优先 + 卸载不清残留：v2.3.11 起不再随包，但 ≤2.3.10 写进 `hancast_setting.json` 的 `screencast.ffmpeg_path` 指的就是当年的随包目录（`.68` 实测 `…\Local\HanCast\ffmpeg\ffmpeg.exe`，6.1.1）。NSIS 卸载不删这个文件，于是路径依然有效、①层优先命中，**系统里新装的那份不会被采用**，版本也停在旧的不会更新。功能不受影响（跑得通），要改用系统版就在弹窗「重新检测」前把路径重填为系统那份；文件一旦真消失，`_configured()` 会自动降级到②③（`ffmpeg_manager.py:425-427`）。 |
| 下载按了但迟迟不到 `done` | 源的体积差异很大，不是卡死 | Windows 走 gyan `ffmpeg-release-essentials.zip` = **114,768,076 字节单包**（`.68` 直连实测 ~18 KB/s，全程要两小时量级）；macOS 是 ffmpeg-static 的单文件 `.gz`（几十 MB，产物层实测 `downloading → extracting → done` 一次跑通）。判据看 `received` 有没有在涨与 `speed` 是否非零，别看百分比进度条；慢线路优先用弹窗里那两条安装命令自己装。 |

| 提示「当前平台没有可用的下载源」 | `download_target()`（`:297-301`）按 `(sys_platform, machine)` 查表，表外（如 win32/x86_64 之外的 arm 组合）返回 `None` → `start_download` 直接抛错（`:452-456`）。这种情况下只能自己装。 |

包体硬上限 `MAX_ARCHIVE_BYTES = 512MB`（`:32`）——正常包 40–200MB，超过说明源站给了别的东西（例如把 HTML 错误页当文件流回来）。下载走**后台任务表 + 前端 1s 轮询**，因为壳层命令循环 `COMMAND_TIMEOUT = 60s`（`src-tauri/src/sidecar.rs:18`）扛不住几百 MB。

### 6.7 Linux/Wayland：投出去全是黑屏，麦克风与系统声音下拉是空的（v2.3.18 的表现，v2.3.19 修复）

**用户报告**：「linux上的电脑投屏全部都是黑屏，然后 麦克风 系统声音页都不可用」（2026-10-17，CachyOS + Hyprland 0.56.2）。两件事是同一次「Linux 侧没做完」的两个面。

**黑屏的机制**：Linux 的视频输入一律是 `-f x11grab -i $DISPLAY`。Hyprland/sway 的 XWayland 以 `-rootless` 启动，**原生 Wayland 窗口不在 X 的窗口树里**，x11grab 连得上（XWAYLAND 那颗 root window 存在）、帧率正常、内容却是空的。这条最贵的地方在于**它不报错**：会话 `ok`、`running` 为真、电视/浏览器都能拉到流，日志一个字都不提。

量化（2026-10-17 同一台机器、同一时刻）：

| 采集方式 | `signalstats` 的 YAVG（平均亮度，0–255） | 判定 |
|---|---|---|
| `ffmpeg -f x11grab -i :1` | **16.03** | 纯黑 |
| `grim`（wlroots `zwlr_screencopy_manager_v1`） | **44.28** | 真实桌面 |
| v2.3.19 的 helper + HLS 分片复测 | 95.1 / 105.5（多次 59.6–105.5） | 有画面 |

ffmpeg 侧无解：n9.0.2 的 `-demuxers` 里只有 `x11grab` / `kmsgrab` / `fbdev`，没有 wayland，pipewire 抓取那条要 portal、官方构建也没编。`kmsgrab` 要 DRM master，跟合成器抢独占，桌面会话里起不来。所以只能自带原生 helper。

**修法**（三个面，机制细节在 [屏幕投屏.md](屏幕投屏.md) §3.4、§4.6、§7.12–§7.14）：

1. **随包 Rust helper** `hancast-wlgrab`（源码 `linux-capture/`，886 行，`wayland-client` + `wayland-protocols-wlr`）：screencopy 的 SHM 路径把帧按紧凑 BGRA 写 stdout，FFmpeg 用 `-f rawvideo -pixel_format bgra -video_size WxH -framerate N -i pipe:0` 接进既有 HLS 管线。帧尺寸取 helper 首行 `HDR` 而不是 `list` 的 mode——缩放屏上两者差 scale 倍，`-video_size` 差一个字节整条流读歪成斜纹，**而且也不报错**。
2. **拿不到 helper 就失败，绝不退回 x11grab**（`capture.py:77-107`）：退回等于把这条原始故障再发一遍。前端同步把「开始投屏」置灰并把 `capture.reason` 写在用户正看着的位置（`ScreenCastPanel.vue:273-276`）。
3. **Linux 音频补齐**：`_list_audio_devices()` 以前在 Linux 直接返回空表——这就是「麦克风、系统声音页都不可用」的真因，界面上两个下拉是空的，不是坏了。现在走 `pactl --format=json list sources` + `pw-dump` + `pactl info` 三层拼装（`screencast/pulse.py`）；PipeWire 在 pactl 的 JSON 里把 `description` 写成字符串 `"(null)"`，可读名必须从 `pw-dump` 的 `node.description` 补。系统声音 = `<sink>.monitor`。

**装机后的复测判据**（`tools/verify-linux-wayland-cast.py`，真机 2026-10-18 00:07 全绿）：helper 可用 → `wl:DP-2`/`wl:DP-3` 单屏条目在列 → `desktop` 标题写明投的是主显示器 → 麦克风 3 条、系统声音 3 条 monitor → rawvideo 命令形状 → 双路 pulse+amix → **真起 HLS 会话**、分片亮度 95.1（非黑）→ 10/10 分片带 aac → 播测试音时 monitor RMS −16.3 dB → 停止后无残留 `hancast-wlgrab` 进程、`running` 归位。`PASS=14 FAIL=0`。

⚠️ 一条判据坑：量分片亮度**不能拿 `seg000.ts`**。产品参数是 `delete_segments` + `hls_list_size=6`（`params.py` 的 `screencast.playlist_size`），会话跑过 6 秒后最早的分片早被裁掉了，只会得到「分片读不出亮度」。要在会话存活期间边跑边把当下完整的分片抄进沙箱再量（脚本里的 `sweep()`）。同理 `ffmpeg astats` 的 `RMS level dB` 行带 `[Parsed_astats_0 @ 0x…] ` 前缀，用 `startswith` 永远匹配不到。

⚠️ 仍未实现：Linux 的**窗口**抓取（Wayland 协议不提供窗口级 screencopy，screencopy 的单位是 output）与 X11 会话下的单显示器选择。

## 7. 粘贴解析与规则包类

### 7.1 解析一直 pending 或超时

- 解析已任务化：`resolve_share` 立即返回 `task_id`，前端轮询 `get_resolve_result`（`commands.py:172` 注册、`commands.py:781` 实现）。同时最多 3 个任务，超了报 `已有 3 个解析任务进行中`（`commands.py:696`）。
- 抓取超时来自 `media.http_timeout_seconds`（默认 30s）。
- 单链接复现：`python tools/share_resolve_probe.py <链接>`（能看到管线在哪一步掉链子）。
- 采集站常见的三类坑（假直链、时效签名、需要浏览器执行 JS）见 [分享解析规则.md](分享解析规则.md) §4；「取不到流的站点」清单在 [解析插件开发指南.md](解析插件开发指南.md) §11。

### 7.2 「检查规则包更新」失败 / 404

0. **先开镜像开关**：设置 → 后台参数 → 「GitHub 加速」分组（section 键是 `network`）的 `github.mirror_enabled`（`params.py:245-253`，默认关）。打开后所有 GitHub 地址（索引、包 zip、更新检查的 api.github.com、FFmpeg 下载源）都前缀走 `github.mirror_prefix`（默认 `https://gh-proxy.com/`，`params.py:254-264`），**镜像失败会自动回落直连**，报错里两路原因用 `/` 拼在一起（所以看到 `直连: ...` 说明镜像那条也已经试过且失败）。改写只发生在唯一入口 `utils/ghmirror.py`，sha256 仍按官方索引校验，镜像换包当场拦下。判据：`HTTPS_PROXY=... python3 tools/verify-github-mirror-live.py`。
1. 索引与 zip 只在 **main 分支的 raw 路径**上有效：`https://raw.githubusercontent.com/pingod/HanCast/main/rule-packs/index.json`（`params.py:21`）。改在特性分支上测必然 404。
2. 超时是后台参数 `rules.index_timeout_s`（默认 40s，`47acc76` v2.3.4）——之前是硬编码，网络慢就整体失败。**走镜像时更新检查的单次预算从 1s 放宽到 3s**（`commands.py:1022`），否则镜像那一跳必然撞超时、看起来像「没有更新」。
3. `rule-packs/dist/*.zip` 必须在 `.gitignore` 的例外里（`!rule-packs/dist/`），一忽略用户就永远拉不到（见 [构建与发布.md](构建与发布.md) §3）。
4. 本机有 GFW 代理时，验证要显式带 `HTTPS_PROXY=127.0.0.1:9565`（死了再试直连）。
5. 升级路径只走产物自己的 `plugin_pull`，别拿仓库源码当已安装包测（zip sha256 校验在 `test_jsplugins.py`）。
6. 已安装版的包内容对不上时：`python tools/pull-rule-packs-installed.py`。
7. 想自建镜像索引（把 `rules.index_url` 指向别处）是另一条路，代价完全不同：那条**要求新索引照抄全部 sha256**，否则包一律拒收。两条路的对照见 [../rule-packs/README.md](../rule-packs/README.md) §2.3。

### 7.3 zip 导入被拒

导入器只收「一层目录（可选）下的 `manifest.json` 与 `*.js`」，其余一律拒收（`jsplugins.py:50`、`jsplugins.py:507`）；必须**恰好一个** `manifest.json`（`jsplugins.py:513-515`）。完整拒收清单见 [解析插件开发指南.md](解析插件开发指南.md) §8。

### 7.4 某站老解不出来，但没人知道

看**解析失败台账**（v2.3.6 新增，`media/failures.py`）：按域名分组记录「粘了但解不出来」的地址、最后一次失败原因与累计次数，设置页可看/可删/可清空。入口藏在 **设置 → 「解析插件（JS 规则包）」折叠区 → 展开后底部**（`PluginSettings.vue`）；v2.3.9 之后，粘贴解析失败时输入框报错下方会就地印出这条路径（`media.resolveLedgerHint`，`MediaInput.vue:808`），不用他自己去翻。它只写本机配置目录，**不进日志也不外发**（里面是用户粘过的链接）。这份清单就是「下一个该写规则包的站点」来源。命令面：`failure_list` / `failure_delete` / `failure_clear`。

### 7.5 粘了个视频页却能点投屏、点了毫无反应

v2.3.10 之前是前端吞掉失败：后端解不出可播源时，只要文本里抠得出链接就「降级透传」原始地址，网页地址于是被当成可播媒体交出去，电视拉到的是 HTML，画面自然什么都没有。现在（`media.ts:142-182`）只有地址**本身带媒体扩展名**（`media.ts:15-19` 白名单：mp4/mkv/m3u8/… ）才透传，其余如实报错、投屏按钮保持禁用。

判据：粘一条网页地址 → 应看到红色报错 + 台账提示，且没有任何投屏按钮；粘一条 `…/movie.mp4` 直链 → 出预览卡片、按钮可用。

若某站点**确实**只能整页交付（服务器对直链也回 HTML 但播放器能自己解析），那是规则包该做的事：按 §7.4 的台账补一条 JS 规则，而不是把前端放行口径改宽。

## 8. 界面与交互类

### 8.1 窗口一片空白

根因：CSP 少了 `unsafe-eval`——vue-i18n 运行时编译模板依赖它。曾被安全收紧顺手删掉，表现为整窗空白（恢复记录 `953801e`）。判据：控制台 `EvalError: Call to eval() ... blocked by CSP`。

### 8.2 点「粘贴」没反应 / 复制失败

剪贴板必须走 Rust：macOS 上 `navigator.clipboard` 不可靠，读走 `read_clipboard`（`d7a7567` v2.2.8），写要有 `write_clipboard` 通道，且 Web API 的 **reject** 也要落进降级（`7413de6` v2.2.9，之前 reject 逃过了 catch）。判据：`commands.ts:1040-1084` 的两级降级是否都走完。

### 8.3 报错只显示前半句（v2.3.12 修复）

症状：粘贴解析失败时，红色错误行停在 `解析失败：https://www.66dpw.vip/…`，后半句「哪个站点、为什么、下一步做什么」看不见——而这恰恰是唯一有用的部分。根因不是后端文案短，是 `.media-input__error` 继承了 `white-space: nowrap` + 省略号截断（`MediaInput.vue:1197-1206` 现在的样式是 `white-space: normal; overflow-wrap: anywhere;`）。长 URL 里没有自然断点，所以只加 `normal` 不够，必须带 `overflow-wrap: anywhere` 才真能折下来。

判据：`node tools/verify-error-wrap-ui.mjs`（先起 `node node_modules/vite/bin/vite.js --port 5199`）。它量的是**几何**——行数与「有没有一行的右边界超出元素盒子」；`textContent` 永远是完整的，只看 DOM 会假阴性。窄窗 420px 是刻意的，宽窗会把老样式也放过。

### 8.4 Wayland：鼠标在界面上晃一晃就出现「透明洞」（v2.3.17 的包，v2.3.18 修复）

症状：窗口正常映射、能点能拖，但光标划过之后**经过的那一条条区域变成透明**，露出后面的桌面（Hyprland 还给它加了模糊），不动就一直那样。用户的第一句描述是「界面完全显示不全」，第二句才是「晃一晃就出现透明洞」——第一句别当成布局问题去改 CSS。

判据要量化，不能凭眼睛：`grim` 抓窗口矩形 → 杀进程 → 同一矩形再抓一张裸桌面 → `ffmpeg -pix_fmt rgba` 转 raw → 逐行求平均绝对差。2026-10-17 真机（CachyOS / hyprland 0.56.2 / webkit2gtk-4.1 2.54.1）800×694 的窗口，用 `hyprctl dispatch "hl.dsp.cursor.move({x=…,y=…})"` 扫一遍之后 **353/694 行与裸桌面一致**（含 198–287、615–680 两条整带），四次复跑落在 25%–51%。差分为 0 的行就是 alpha=0 的洞。注意排除 CSS 假因：`.media-input__overlay` 的 `backdrop-filter: blur(4px)` 只在真拖拽时 `v-if` 存在，`:hover` 没有任何规则把卡片调透。

这套方法已封成 **`tools/verify-linux-window-opacity.sh`**（现读 Hyprland 环境、按 `class` 取矩形、蛇形扫光标、grim 成对截图、逐行差分，最差一轮占比超 `--max-pct` 就 FAIL）。两条现场约束：**背景必须是裸桌面**——同一 workspace 上有别的窗口压住矩形时脚本 `exit 2`，而不是拿它当背景量出假 PASS，桌面正被占用时用 `--workspace auto` 切到一个空工作区再量；**绝不用 `hl.dsp.window.move`**——它作用于「当前焦点窗口」，实测会把用户正在用的终端挪走，切工作区才是安全做法。

根因：§10.6 那条兜底（`WEBKIT_DISABLE_DMABUF_RENDERER=1`）让 WebKitGTK 从 dmabuf 退回**共享图像（SHM）路径**，透明（ARGB）窗口在这条路径上会把 damage 矩形漏提交——那块 surface 从没画过，alpha 保持 0。上游 [tauri#14924](https://github.com/tauri-apps/tauri/issues/14924)（记录时仍 OPEN）是同一现象："persistent ghost pixels from stale SHM buffer regions"，并且明确「**The opaque settings window has no issues**」。同一台真机实测：`WEBKIT_DISABLE_COMPOSITING_MODE=1` 叠加无效，§10.6 那批（`GSK_RENDERER=cairo`/`gl`、`LIBGL_ALWAYS_SOFTWARE=1`）只治启动即没、不治漏提交。

修法（v2.3.18）：Linux 侧**不再要透明窗口**。`src-tauri/tauri.linux.conf.json` 补一份完整的 `app.windows[0]`（Tauri 平台合并是 RFC 7386，**数组整体替换**，只写增量等于没写），`transparent:false` + 不透明 `backgroundColor` `{22,20,50,255}`。为什么是这色：暗色主题 `--bg-primary` 是 `rgba(22,20,50,.95)`，取它的等色；亮色主题下 95% 白叠它只差约 12 个 RGB 单位，看着仍是白底。`wry` 侧对应 `webkitgtk/mod.rs` 的非透明分支 `webview.set_background_color(...)`，`tauri-runtime-wry` 会把 config 的 `background_color` 透下去。代价：Linux 没有毛玻璃观感（Windows/macOS 不变），换来界面不再漏桌面。

顺带排除的假因：346×472 与 716×472 两种尺寸截图核对过首页——`.device-list__items` 自带 `overflow-y:auto`（`DeviceList.vue`），最小尺寸下设备列表照样可滚、`解析 / 准备` 按钮可达。「显示不全」不是布局裁切，就是上面那些洞。

`lib.rs:991` 在非 macOS 上就是刻意回 `Err`）。**同一条路径还会 `raiseIfHidden()`**
（`commands.ts:1556`：窗口不可见就 `show()` + `setFocus()`）。
v2.3.22 那轮**只有这条管用**（横幅没弹，红字靠窗口被带回前台才看见）；v2.3.23 把 UN 排到主线程之后
两条都有真机截图证据，判据见 [构建与发布](构建与发布.md) §6.11。

**macOS 上不弹横幅怎么查**（按顺序，别靠眼睛盯屏幕）：

1. 日志面板**不加模块过滤**（下拉里暂时没有「系统通知」这一项，`logger.py:114-125` 的 `MODULE_LABELS` 还没收它）就能看到 `hancast.notify` 行——`macos_notify::log()` 把 `requestAuthorization` 的
   granted/错误、`getNotificationSettings` 的 `authorizationStatus`/`alertSetting`、
   `addNotificationRequest` 的 completion 错误都写进了**程序日志同一份 `hancast.log`**（见
   [前端 API 参考](HanCast-Frontend-API.md) §6.7 的例外），行格式与 Python logger 完全一致，
   所以 `_LINE_RE`（`logger.py:109-111`）解得开。看到 `notDetermined`/`denied` 就是权限，
   看到 add 报错就是投递。实测痕迹：本机日志里躺着 6 条 `addNotificationRequest 已接受（id=hancast-cast-<ms>）`。
2. **UN 的调用必须在主线程**：v2.3.22 从命令的工作线程直接调，系统判成「不允许通知」，
   `presented` 恒 0；v2.3.23 改成 `run_on_main_thread` 后横幅真弹出来了（判据与截图口径见 [构建与发布](构建与发布.md) §6.11）。
3. **别用 `usernoted` 的 sqlite `presented` 列当判据**：本机量过——走新 API 的第三方 App 是 21 条
   `presented=1`，而 HanCast 每次重新打包（linker-signed 换签名身份）后通知权限都要重授，
   临时 scratch 包甚至直接回调 `granted=false`。判据改成**截图连拍**：
   `screencapture -x` 在触发前后各连拍几张（文件名自己起，落 `/tmp` 下），横幅进没进屏幕一眼可辨。
4. 正文用的是 Sidecar 原文（含电视返回的 500 原文），所以「通知里写了什么」=「后端为什么失败」，
   不要再往中间加包装。

**判据的教训**（这条别再犯）：`tools/verify-cast-ui.cjs` 把 `notify()` 整个 stub 掉，
它证明得了「五条失败出口都会调用」，**证明不了 OS 呈现**——v2.3.21 就是靠这套全绿的测试发出去的。
凡是「最终交付物是一条 OS 副作用」的功能，harness 之外必须再有一条真机判据。

## 9. 设置、后台参数与日志类

### 9.1 设置页读不到后台参数

根因：父进程没给 locale 时，macOS/Linux 的 stdio 也会退回 ASCII 编码——**所有带中文的响应变成 `success:false`**，中文日志行被编码器吞掉。修法是 stdin/stdout/stderr 一律强制 UTF-8，且必须在 `setup_logger` 之前（`main.py:21-28`，`12d6196` v2.2.19）。

判据：`tools/verify-sidecar-utf8-protocol.py`；UI 侧参数表验收 `tools/verify-params-ui.mjs`（它把设置页与 `params.py` **逐键比对**，不写死条数——`9787f2b`）。

### 9.2 改了参数像没生效

参数在**调用点每次读**，不是 import 时读，所以「下一次会话」才生效（`params.py:9`）；投屏进行到一半改分片时长不会追改当前 ffmpeg 命令行。另外只存与默认值不同的覆盖项（`params.py:6`）：想恢复默认，把该项改回默认值即可，配置里不会留旧钉死值。

### 9.3 日志太大 / 找不到日志

5MB × 3 轮转（`logger.py:33-37`）；面板一次读多少由 `logs.tail_mb`（默认 2MB）决定；`set_log_level` 临时提级，`export_logs` 走壳层保存框（`lib.rs:884-903`）。

## 10. 构建与安装类

### 10.1 双击 `hancast.exe` 闪退

依赖缺失：Sidecar 是子进程，直接跑主程序没有 Sidecar（也没 mpv）必然崩。开发用 `npm run tauri dev`；产物问题按 [构建与发布.md](构建与发布.md) §2.4、§4 的资源与验收清单查（`bundle.resources` 的 glob 命中可用 `node scripts/check-resources.cjs` 验）。Linux 上还有一类「资源在包里但位置不对」的崩法，看 §10.5；Wayland 立刻没窗口看 §10.6。

### 10.2 每次升级都要重新授权（macOS）

adhoc 签名让 TCC 授权随版本失效（本地无开发者证书签名，linker-signed 每版换身份）。同时「本地网络」权限也按身份判定（`8eaca95` + `c983c4e`）。这是**发布线限制**，不是运行时 bug。

### 10.3 局域网请求整体超时

这台 Mac 上系统代理是 `127.0.0.1:9565`，非私有网段的地址会被劫持，代理一死全挂。链路内 HTTP（描述抓取、来源页、流代理）**必须显式清空代理**（`65ad943` v2.2.11、`96ab326`）。判据：同一条 URL 分别在带/不带 `HTTPS_PROXY` 下试；日志里出现指向 `127.0.0.1:9565` 的失败即命中。

### 10.4 CI / 发布卡住

先看 [构建与发布.md](构建与发布.md) §4 的逐步骤表和 §7 的常见故障；轮询 CI 用 run id，不要猜 job 名。推 main 被拒通常是本地 main 落后（`git push origin HEAD:main`）。

### 10.5 Linux：装得上、一点就没，sidecar 退出码 127（v2.3.16 的包，v2.3.17 修复）

症状：deb / pkg.tar.zst 安装无报错，启动后主窗口要么起不来要么所有功能空转。Rust 侧日志是 sidecar 退出码 **127**，本机 `ldd /usr/bin/hancast-sidecar` 报 `libpython3.12.so.1.0 => not found`。

根因是**布局被拆成两半**：tauri 的 Linux bundler 把 `externalBin` 装到 `/usr/bin`、`bundle.resources` 装到 `/usr/lib/HanCast`，而 Nuitka standalone 只从**可执行文件所在目录**解析依赖（`libpython3.12.so.1.0` 靠 `DT_NEEDED` + RPATH `$ORIGIN`，`lxml/etree.so` 靠 Python 层按 exe 同级拼出来的绝对路径）。exe 与依赖不同目录时，`LD_LIBRARY_PATH`、工作目录都救不了——`sidecar.rs:205,210` 把 `current_dir` 设成依赖目录是对的，但 `$ORIGIN` 看的是 exe 自己的位置。

修法（v2.3.17）：`src-tauri/tauri.linux.conf.json` 把 `externalBin` 置空、`hancast-sidecar` 作为 `resources` 首项，配合 `flatten_dependencies(..., copy_executable=True)`（`build_sidecar.py:53,122`）在 Linux 上连 exe 一起提升到 `src-tauri/` 根，于是安装后 exe 与依赖同在 `/usr/lib/HanCast/`。Rust 侧不用改：`sidecar.rs:186` 的 `search_dirs` 第一个就是 `resource_dir`，命中即与 `$ORIGIN` 同目录。

真机取证（2026-10-17，CachyOS 上装着 `hancast 2.3.16-1`）：原地跑 `/usr/bin/hancast-sidecar` 仍是 `error while loading shared libraries: libpython3.12.so.1.0`；把 CI 出的 2.3.17 产物 `hancast-2.3.17-1-x86_64.pkg.tar.zst`（51,427,251 字节）`bsdtar -x` 解到 `/tmp` 后，`usr/bin/` 下没有 `hancast-sidecar`、`usr/lib/HanCast/hancast-sidecar` 与 `libpython3.12.so.1.0` 同级，喂 `{"id":1,"cmd":"get_settings","params":{}}` 得到 `{"id": 1, "success": true, ... "version": "2.3.17" ...}`，stderr 61 行里 shared-lib / ImportError / Traceback **0 次**（完整数字见 [构建与发布.md](构建与发布.md) §6.7）。同日装上 2.3.17 之后装机路径同样成立：`/usr/bin/hancast-sidecar`（2.3.16 留下的半份产物，38M）**随 `pacman -U` 消失**，`pacman -Qkk` → 115 全部文件 / 0 变化的文件，主程序日志里 `Found sidecar: "/usr/lib/HanCast/hancast-sidecar"` 且 `Some(127)` 不再出现。**依赖那一层里确实是目录形态**（`certifi/`、`lxml/`、`charset_normalizer/`、`curl_cffi/` 加 `libpython3.12.so.1.0`、`_quickjs.so`、`netifaces.so`、`81d243bd…__mypyc.so`），顶层 `*.so` 抓不到目录里的扩展模块——这就是「bundle.resources 必须逐平台列全」的实测依据。

**为什么 CI 以前是绿的**：v2.3.16 的四条装端检查查的都是「文件在不在包里」，而崩溃源于「在包里的两个不同位置」。现在三层防回归——结构校验 `scripts/check-resources.cjs:179`（Linux 布局：exe 必须在 resources 里、不能出现在 `/usr/bin`）、CI 解包 deb 后**真跑一条协议**（`build.yml:294-343`，喂 `{"id":1,"cmd":"get_settings","params":{}}` 并要求 `"success": true`）、Arch 容器 `pacman -U` 实装后同一条断言（`scripts/build-arch-pkg.cjs`）。

### 10.6 Wayland：图标点一下，窗口闪都没闪就没（v2.3.17 修复）

症状：Hyprland 等 Wayland 合成器上启动即消失，没有窗口、也没有报错弹窗——用户看到的是「图标点一下，什么都没发生」。客户端 stderr 稳定留一行协议错误（2026-10-17 在 CachyOS 真机 `timeout 20 /usr/bin/HanCast` 复现，退出码 **1**）：

```text
Gdk-Message: Error 71 (协议错误) dispatching to Wayland display.
```

同一台机器上更早的一次抓包还看到协议错误的来源行 `wl_display#1.error(wp_linux_drm_syncobj_surface_v1#52, 4, "Missing acquire timeline")`（它由合成器发出，不一定每次都在 stderr 露头，判据以上面那行为准）。

根因：WebKitGTK 2.4x 起给 webview 表面走 `wp_linux_drm_syncobj_*` 显式同步，Hyprland 要求 commit 前必须先绑定 acquire timeline，没绑就判客户端违约并把连接打断。2026-10-17 在 CachyOS（gtk4 4.24.1 / webkit2gtk-4.1 2.54.1 / hyprland 0.56.2）实测：`GSK_RENDERER=cairo`、`GSK_RENDERER=gl`、`LIBGL_ALWAYS_SOFTWARE=1` 全都照崩，只有 `WEBKIT_DISABLE_DMABUF_RENDERER=1`（退回共享图像路径）稳定存活，且仍是原生 Wayland 表面，不必把用户推去 XWayland。

修法：`src-tauri/src/main.rs:29-36` 在任何 GTK/WebKit 初始化之前补这个环境变量，只在 `WAYLAND_DISPLAY` 存在且**用户自己没设过**时生效（留手动调试的口子）。⚠️ 这条兜底本身在透明窗口上还有连带后果（光标划过露桌面），v2.3.18 起 Linux 窗口改不透明，见 §8.4。判据（同一台真机：装着的 2.3.16 vs 装上 2.3.17 之后）：

```bash
WAYLAND_DISPLAY=wayland-1 timeout 20 /usr/bin/HanCast; echo $?   # 2.3.16 装机版 → 1
WAYLAND_DISPLAY=wayland-1 timeout 30 /usr/bin/HanCast; echo $?   # 2.3.17 装机版 → 124（活到超时）
```

装上 2.3.17 后 `hyprctl clients` 里能看到 `Window … -> HanCast:` 且 `mapped: 1 / hidden: 0`——窗口是真的映射出来了，不是无头存活（实测数字见 [构建与发布.md](构建与发布.md) §6.7 装机验收表）。

### 10.7 Linux：随包 mpv 在 Arch 上跑不起来（v2.3.17 起自动让位系统 mpv）

症状：接收端播放没声音/没画面，日志 `MPV status` 却指向包内 `/usr/lib/HanCast/mpv/mpv`。`ldd` 一眼定死（2026-10-17 真机实测，**13 条 not found**；先跑的 `| head` 只截出 10 条，全量 `wc -l` 复核是 13）：随包那份是 CI 的 **Ubuntu runner** 构建，`libavcodec.so.60`、`libavdevice.so.60`、`libavfilter.so.9`、`libavformat.so.60`、`libavutil.so.58`、`libbluray.so.2`、`libcdio.so.19`、`liblua5.2.so.0`、`libmujs.so.3`、`libplacebo.so.338`、`librubberband.so.2`、`libswresample.so.4`、`libswscale.so.7`——在滚动发行的 Arch 上都不存在，那边早已是 ffmpeg 7.x/8.x 的 soname。同一台机器 `which mpv` → `/usr/bin/mpv`，**v0.41.0，与 CI 固定的 `env.MPV_TAG` 同版本**，跑得起来。

v2.3.17 的处理是**运行时兜底**而不是改打包：`mpv_manager.py:56-63` 现在对随包候选先跑一次 `--version`（`_validate_mpv`），跑不起来就带 warning 让位给系统 PATH 里的 mpv（与 FFmpeg 的「本机检测优先」同一套思路，`utils/ffmpeg_deps.py`）。顺序仍是 手动指定 → 随包 → 系统 PATH，只是第二层从「文件在就宣布就绪」改成「真跑一次才算」。测试 `tests/test_mpv_bundled_path.py` 三条覆盖：能跑时 bundled 仍优先、跑不起来时落到 system、两者都没有时才是 NOT_FOUND。真机验证（2.3.17 产物解包直跑）：日志 `Bundled MPV exists but cannot run, fall back to system: .../usr/lib/HanCast/mpv/mpv` → `Found system MPV: /usr/bin/mpv` → `MPV IPC connected OK`，单喂 `check_mpv` 回 `{"status":"ready","path":"/usr/bin/mpv","source":"system"}`；注意 CI 的 deb 冒烟里同一条是 `"source": "bundled"`——构建机上随包 mpv 本来就跑得起来，不是反例。

> 没做的两条更重的路，留作决策：① Linux 不再随包 mpv（`bundle.resources` 去掉 `mpv/*`，包小一点，但干净机器直接没播放器）；② 随包一个自带 ffmpeg 的静态 mpv（Arch 官方 release 无 Linux 资产，要自己跨发行版取货，体积和授权都更麻烦）。当前方案是「包照旧带，坏了就用系统的」。
